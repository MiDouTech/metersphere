# visual-ui-testing 技能升级建议

日期：2026-09-24。评估对象：`C:/Users/midoo/.codex/skills/visual-ui-testing/SKILL.md`。

当前技能适合把方案、页面树和原型转换为页面元素、路由及菜单测试，但不充分覆盖业务端到端执行和知识沉淀。建议保留原有视觉测试能力，增加按任务选择的业务流程测试模式，而不是把所有测试强制扩展为完整业务回归。

本文为升级建议，尚未修改已安装技能。

## 1. 建议保留的能力

- 按方案名称组织测试，并追溯原型位置。
- 登录准备与业务执行分离，复用有效登录态。
- 缺失的真实需求不能通过改断言或跳过伪装为通过。
- 优先验证用户可见元素，修正脚本误报时保留真实缺陷。

## 2. 优先升级项

| 优先级 | 缺口 | 建议 | 本次依据 |
| --- | --- | --- | --- |
| P0 | 测后仅输出统计，没有业务认知文档 | 每次测试交付业务理解文档，包含对象、角色、状态、规则、边界、证据、未知项及认知变化 | 订单生效与交付、开票不同，需要沉淀 |
| P0 | 缺少证据可信程度分类 | 区分实测、需求声明、页面提示、推断及待确认 | 页面金额提示不能当成已验证后端规则 |
| P0 | 缺少负向测试变量控制 | 单因素场景一次只改变一个条件；组合场景明确标记，不做单因素归因 | TC14同时缺步骤及附件 |
| P0 | 缺少逐步记录与回传回读规范 | 记录实际结果、断言、截图、平台ID；上传后回读校验；原始探针与补传分开保存 | 补传后当前详情不能直接代表早期探针 |
| P0 | 容易混淆成功层级 | 分开记录业务结果、脚本结果、上传结果、门禁结果、评审结果 | 接口ok不代表门禁通过 |
| P1 | 只有页面模型，缺少业务状态模型 | 业务模式先建立状态转换表和用户指定终态 | 创建订单需要两次审批 |
| P1 | 错误分类不足 | 区分产品缺陷、脚本时序、环境、权限及测试数据阻塞 | 弹窗关闭动画曾触发脚本误报 |
| P1 | 缺少数据生命周期控制 | 记录测试数据标识、副作用、清理状态；从检查点恢复，避免重跑创建 | 两笔已生效订单留存 |
| P1 | 登录凭据处理过于简单 | 不把密码、验证码或Token写入报告、Git；若使用.env/auth-state，确保忽略规则和受限存储；日志截图按需脱敏 | 登录态和平台Token具有实际权限 |
| P1 | 写死既有visualTest目录及命令 | 先识别项目与执行方式，再选择现有Playwright Test或CLI；不得声称未执行的类型检查通过 | 本次为CLI浏览器任务 |
| P2 | 缺少复测知识变化记录 | 维护版本、证据日期、适用环境、已失效规则和待确认项 | 权限故障调查补充了新的认知 |

## 3. 建议工作流

1. 确认测试模式、环境、账号、范围及完成边界；已有上下文不重复询问。
2. 读取需求或探索页面；没有独立需求时记录证据来源，不虚构需求覆盖率。
3. 建立业务对象、角色和状态表，以及待验证规则。
4. 设计用例及需求—规则—断言—证据映射；负向用例标明唯一变化条件。
5. 执行并逐步记录实际结果；关键状态转换留证；失败分类后再决定修正脚本或报缺陷。
6. 若任务要求平台回传，上传后回读核对；使用metersphere-agent等平台技能承接，不在视觉技能中写死平台实现。
7. 输出测试报告、业务理解文档、证据索引、数据留存清单。
8. 对复测输出认知差异与未解决问题；阻塞任务也输出已掌握知识和阻塞位置。

## 4. 强制交付规范建议

每次有实际执行的测试，无论通过、失败或部分阻塞，都交付：

| 文件 | 内容 |
| --- | --- |
| `test-report.md` | 范围、真实执行数量、结果、问题分类、命令、未执行项 |
| `business-understanding.md` | 业务目的、对象关系、角色、状态转换、规则及证据等级、终态边界、未知项 |
| `evidence-index.json` | 运行ID、用例ID、步骤ID、实际结果、证据路径、平台记录ID、时间与变更条件 |
| `test-data.md` | 新增或修改的数据、用途、当前状态、是否清理及原因 |

小任务可合并证据索引与数据清单到报告，但业务理解必须有独立可链接章节或文件。已有业务认知文档时追加本轮差异并保留历史，不制造重复且互相矛盾的版本。

业务理解建议模板：

```markdown
# [业务名称]业务理解
日期/环境/范围/证据来源：
## 业务目的与本次终态
## 对象及角色
## 状态转换与操作入口
## 规则认知表
| 规则ID | 认知 | 实测/声明/推断/待确认 | 证据 | 限制 |
## 异常与恢复路径
## 测试数据及副作用
## 本轮新增、纠正和失效的认知
## 待确认事项与下一轮验证
```

## 5. 结论与证据规则

- 单条用例通过需有实际执行和断言依据，不根据截图存在或上传成功判定。
- API观察到的返回、页面结果和数据库验证分别表述，不互相代替。
- 无需求或原型时可以进行探索测试，但不能宣称方案符合率或视觉像素一致性。
- 关键终态至少在适用的列表、详情或再次加载后交叉确认。
- 每次回传保存不可变的本地运行记录；使用平台执行历史ID时必须先确认平台确实提供，不能假定可查历史。
- 补传、重试和恢复执行使用单独记录并关联原始运行，禁止抹去负向探针。
- 正式通过、上传成功、门禁通过、评审通过分别统计。
- 涉及辅助技术状态错误时，如使用正常键盘继续验证，应披露缺陷和替代路径，不把绕过后的业务成功当成控件无缺陷。

## 6. 技能改动范围建议

- `SKILL.md`：补充模式选择、业务状态与证据要求、测后业务理解交付、分层结果及真实完成条件。
- `references/business-understanding-template.md`：业务认知模板与证据分级示例。
- `references/negative-test-design.md`：单因素/组合场景、对照组和结论边界。
- `references/evidence-and-writeback.md`：证据索引、补传、回读和平台历史验证。
- `references/test-data-lifecycle.md`：数据标识、恢复检查点、副作用与清理。

以上文件为建议新增位置，并非已创建的技能文件。技能正式实施时应按skill-creator规范校验结构和触发范围。

## 7. 升级验收

用四类代表任务验证新技能：仅视觉对照、业务主流程、缺证据负向探针、登录或环境阻塞。要求输出与任务模式匹配，且：

1. 每次执行后能找到业务理解及证据来源；阻塞时不编造已完成流程。
2. 组合条件失败不被写成单因素结论。
3. 上传结果与业务、门禁结果可以独立核对。
4. 恢复执行不会无意重复创建业务数据。
5. 报告不含凭据，不声称未执行验证通过。
6. 修改脚本后保留原始失败及修正原因。
