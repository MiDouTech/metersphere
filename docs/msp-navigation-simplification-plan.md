# MSP 入口与页面精简改造方案

日期：2026-09-23；状态：已在 v3.2 开始 S0～S1 首批实施，整体部分完成。实现与验收以[实施记录](./msp-navigation-implementation-progress.md)为准；下文“方案阶段”结论保留为设计基线。

## 1. 目标与边界

用户已确定 MSP 的八项业务需求：项目、计划/评审/报告、用例及执行历史、缺陷、接口测试预留、平台模型 API 测试预留、外部 Agent 执行验收闭环、测试资产。

本专项解决“系统略显臃肿”的问题：减少重复入口、混合职责和不适用于当前阶段的配置，让测试人员能顺着工作流程找到功能。它是[综合改造方案](./msp-consolidated-transformation-plan.md)中的产品精简专项，不扩大为新平台建设。

### 改造目标

1. 一个业务对象只有一个主要维护入口，其他位置提供上下文链接。
2. 普通测试人员能完成“找用例 → 建计划 → 发起执行 → 看结果 → 处理问题”，不必先理解 Runner、租约或网关。
3. 当前没有平台模型，默认不展示模型专用操作；仍保留未来接入位置和历史记录。
4. 设置按个人、项目、系统权限归属，避免一个 Agent 页面同时承载全部角色的工作。
5. 删除重复导航，不损失业务能力、版本、证据和审计，不破坏已有 MCP/API。

### 不在本专项中做

- 不删除核心数据表，不改历史状态，不清理无人使用尚未证实的数据。
- 不重写测试引擎、资产服务和缺陷工作流，不接大模型。
- 不把质量门禁页面占位当作已实现审批；门禁后端按综合方案交付后再开放相关入口。
- 不为了“界面变少”把全部功能藏进一个杂乱的“更多”菜单。

## 2. 当前臃肿的具体表现

本轮再次读取 AgentTabs.vue、TestAssetTabs.vue 及相关路由：源码定义了 **12 个 Agent 主标签、10 个测试资产标签**。实际显示数量受权限影响，不能把它们当成每个用户当前都可见的生产统计。

| 问题 | 已有依据 | 用户代价 |
|---|---|---|
| Agent 板块同时管理任务、资源、个人授权、模型及资产 | AgentTabs 的 12 项配置 | 不知道要先配置什么、去哪里执行 |
| 自动化执行与队列重复提供任务入口 | automationExecution、agent/queue；详情 wrapper 复用前者 | 相同任务多个入口，状态与操作容易分叉 |
| 能力与授权页面混有 Token、告警和策略 | 前序读取 capability.vue | 用户角色和问题类型混杂 |
| 资产中再次出现环境、接口、缺陷 | TestAssetTabs 的独立标签 | 不清楚应该在哪里维护主数据 |
| 版本、追溯、证据作为同级主标签 | TestAssetTabs | 与文档、用例这些主对象争夺导航空间 |
| 未接模型却提供模型配置和 Prompt 主入口 | agent/model-profile、prompt-template | 产生“先填完才能用系统”的错误预期 |

资产 Catalog 有版本和追溯能力，因此不能把组件复用或对象重复出现直接判断成无用功能。要删除的是重复的主入口和维护职责。

## 3. 目标导航：业务在前，设置在后

建议保留现有主要板块，**将 Agent 一级板块替换为执行中心**，不额外增加新的一级中心。报告继续放测试计划内，不再另起报告中心。

```text
工作台
测试计划
  计划列表｜评审｜测试报告
测试用例
  用例列表（详情内查看执行历史）
执行中心（替换原 Agent 主入口）
  执行任务｜待审批*
缺陷管理
测试资产
  业务文档｜用例资产｜测试数据（按需）
项目管理
  项目/成员/版本/环境/必要配置
接口测试（预留；已启用项目按原能力访问）
设置
  个人接入｜项目执行设置｜系统运行维护｜扩展能力
```

`*` 待审批只有在后端审批能力验收通过后开放。此前显示任务现有真实状态，不新增可点击的假审批页面。

“平台 AI 测试”预留在设置→扩展能力及执行中心的执行方式中。模型未接入时给管理员看未启用说明，普通用户不出现可执行按钮。需要宣传预留能力时可在帮助说明中展示，不常驻一个空白一级菜单。

配置分组是导航组织，不要求新建四套配置服务。系统与组织范围保留授权边界。

## 4. 截图中入口的精简明细

| 编号 | 当前入口 | 本专项动作 | 迁移后的入口/能力 | 删除条件 |
|---|---|---|---|---|
| N01 | 自动化执行、Agent 队列任务列表 | 合并为一个主要列表 | 执行中心→执行任务；原页面仅保留跳转 | 原有筛选、取消、重试和创建均可用 |
| N02 | Agent 执行详情第二入口 | 删除重复主导航 | 统一执行详情，旧地址重定向 | taskId、projectId、来源和返回路径不丢 |
| N03 | 能力与授权独立页 | 拆分后删除页面入口 | 接入状态→个人/项目接入；告警→运行维护；策略→项目设置 | 所有原功能有明确归宿和等价权限 |
| N04 | 多处 Token 展示/维护 | 只保留一处编辑入口 | 设置→个人接入；执行页只显示连接状态和链接 | 创建/撤销/范围/审计功能完整 |
| N05 | 执行评价独立标签 | 撤销主标签 | 执行列表统计摘要、详情评价区；历史评分保留 | 指标口径一致，评价不冒充审批 |
| N06 | 资产缺陷标签 | 从资产主标签删除 | 缺陷管理；资产详情显示“关联缺陷” | 缺陷和关系记录不删除 |
| N07 | 资产环境标签 | 从资产主标签删除 | 项目管理→环境；资产详情可查看环境引用 | 有权限的环境查看和历史版本仍可达 |
| N08 | Agent 环境执行配置 | 撤销独立标签 | 项目环境详情→执行配置 | 保留环境扩展 ID 和引用关系 |
| N09 | 自动登录配置 | 撤销独立标签 | 项目环境详情→高级设置→登录方式 | 有执行消费者时可配置，原登录配置可查 |
| N10 | 凭据引用 | 下沉管理员/授权人员配置 | 环境详情引用；敏感维护在接入设置 | 不扩大凭据读取权限，不显示密钥明文 |

N01～N07 是优先精简项；N08～N10 涉及配置上下文和权限，放在第二批处理。

## 5. Agent 其余入口怎么处理

| 原标签/子功能 | 处置 | 当前阶段说明 |
|---|---|---|
| Agent 列表 | 改名“执行器管理”，迁运行维护 | 其内容实际为 Runner；不要求外部 MCP 使用者先注册平台 Runner |
| 模型执行配置 | 普通用户隐藏，管理员放扩展能力 | 保留接入位置、历史及未来开关，不连接假模型 |
| Prompt 模板 | 平台模型用途暂缓 | 有外部消费者的模板仍可授权访问；未核实引用前不删实现 |
| Page Object | 从日常导航移除，按需放自动化资产高级区 | 不作为普通 Agent 提交结果的必填前提 |
| 业务流 | 同上 | 已有消费者可继续使用，不强行合并 API 场景执行协议 |
| 执行租约 | 运行维护中的诊断页 | 用户仅看到运行者/断联提示，不需理解租约字段 |
| 调度规则/Webhook | 项目执行设置 | 没有可用消费者时禁用启用动作；保留既有规则和历史 |
| 项目 AI 治理 | 通用规则归项目策略，模型专用规则归扩展能力 | 不将无模型项目绑到模型白名单、回退模型等配置 |

迁移完成后，原 12 个主标签不再整排呈现。普通测试人员在执行中心只看到“执行任务”和真实可用的“待审批”；资源和扩展能力按角色访问。

## 6. 测试资产从十个标签收敛为三类主对象

| 当前标签 | 改造后位置 | 保留内容 |
|---|---|---|
| 业务文档 | 主标签保留 | 上传、阅读、版本、引用、权限 |
| 用例资产 | 主标签保留 | 可复用用例/模板及发布版本，关联用例主对象 |
| 测试数据 | 按项目需求显示的主标签 | 数据内容、版本及任务引用 |
| 测试环境 | 项目环境主入口；资产中仅上下文引用 | 环境身份、快照和版本关系 |
| 资产版本 | 各资产详情→版本 | 比较、发布、废弃、历史；必要时提供高级全局检索 |
| 关联追溯 | 各资产详情→引用关系 | 文档—用例—计划—运行—缺陷关系 |
| 执行证据 | 执行详情→步骤证据；执行列表提供证据筛选 | 原始文件、归属、访问控制、保留期 |
| 缺陷资产 | 缺陷管理；详情→关联缺陷 | 全部关联数据 |
| 接口资产 | 随接口测试能力按需启用 | API 主数据和发布版本，不当前删掉 |
| 公共步骤 | 有消费者时进入高级复用资产 | 原定义和引用；无消费者时隐藏入口 |

主导航从源码定义的 10 项降为通常 2～3 项，这是设计目标，不是已实现结果。高级入口按真实任务提供，例如在引用选择器中查版本，而不是再造一排十个“高级”标签。

用例资产只负责复用和版本引用；项目工作用例由用例管理维护。入口精简先复用既有数据关系，不在本专项偷偷进行用例实体合并。

## 7. 页面内部也要减负

### 7.1 执行列表

默认列：任务名称、所属计划、运行状态、产品结果、验收/审批状态、更新时间、操作。默认筛选：项目、状态、计划、执行者。构建/来源/执行通道放可展开筛选区。

Runner ID、租约 ID、attempt、内部状态码、模型逻辑 ID 不放默认列；需要排障时进入运行详情的技术信息区。用户仍可见业务上必要的“执行者、版本、环境”，不能因简化隐藏结果适用范围。

运行完成但尚未审批，应清楚显示“执行完成，待验收/审批”，不只显示绿色成功。

### 7.2 执行详情

建议最多四个业务标签：

1. 概览：任务范围、环境、构建、执行者与各阶段状态。
2. 步骤与证据：预期、实际、附件并列。
3. 验收与审批：规则结果、批准/驳回理由和补正动作；能力未上线前不展示假操作。
4. 历史：尝试、提交版本、状态变化和关联缺陷。

技术日志、租约、内部事件和回写错误在运维可见的展开区。不要为每一个数据表生成一个标签。

### 7.3 创建执行任务

从计划发起时自动带入用例范围和项目；用户主要确认环境、构建和执行方式。当前默认外部 Agent，平台模型执行未启用时不要求选择模型。

接入管理员事先维护默认执行配置。使用已有可用配置时，不要求测试员依次建立 Token、模型、Prompt、Page Object、业务流和 Runner。若当前后端创建逻辑仍强制模型配置，此项依赖综合方案 BE01/BE24 完成，不能只隐藏前端字段。

## 9. 路由兼容、权限及数据处理

### 9.1 路由映射建议

| 旧路径 | 新目标（拟议） | 参数规则 |
|---|---|---|
| /case-management/automation-execution | /execution/tasks 或 /execution/tasks/:id | 有任务 ID 则到详情，无 ID 则列表；保留项目与允许的筛选参数 |
| /agent/execution/detail | /execution/tasks/:id | 从旧 query 取任务 ID；缺失时回列表并提示 |
| /agent/queue | /execution/tasks；租约/调度跳运行设置 | 按旧标签参数判断，不把调度链接全部导向普通列表 |
| /agent/evaluation | /execution/tasks 的统计视图 | 保留能映射的日期/执行者过滤 |
| /agent/access | 设置中的个人接入入口 | 保留当前账户和项目上下文，不传 token 明文 |
| /agent/capability | 接入状态入口并提供告警/策略导航 | 原页多职责，不能无解释随机导向其中一项 |
| /test-assets/bugs | 缺陷列表或指定资产的关联缺陷 | 只有完成过滤映射才迁移，不能丢引用范围 |
| /test-assets/environments | 项目环境或指定环境详情 | 有版本参数时打开只读快照，不能跳最新版冒充历史 |

目标设置路径在实现时按现有 projectManagement/setting 路由确定，不为给出 URL 而凭空新增一套设置目录。

保留旧地址至少一个发布周期，并根据使用记录决定后续退役；使用 router.replace 避免旧新地址循环进入历史栈。URL 参数只接收白名单，不传播任意回跳 URL。未知或无权对象显示安全错误，不跨项目兜底查找。

### 9.2 权限

测试员访问用例、计划、执行和资产；审批人额外访问待审批；项目管理员维护项目执行设置；系统管理员管理运行资源。不能简单去掉 adminOnly 后让所有登录人访问全部原管理员功能。

Token 的个人主体与项目 scope 保持原验证，环境配置与凭据维护权限分别保留；证据在其他页面能看到链接不等于可以下载。

### 9.3 数据库与后端

**第一批导航精简原则上不增加业务表，也不迁移业务数据。** 主要变动是页面入口、组件复用、权限资源与菜单配置；若菜单/权限持久化，则编写可重复的资源码映射迁移，并保留用户自定义菜单配置的处理规则。

后端领域接口与数据来源保持一致，避免为了移菜单重命名全部 API。能力状态不足、环境上下文不完整、列表需要聚合查询时，可以做必要的服务改造，但需单独列契约与测试。

以下能力依赖综合方案，不能包装为本专项已实现：无模型 external-task 创建、正式门禁、审批、统一执行结果服务、构建级报告。导航可以先统一，相关新按钮必须等待真实能力交付。

## 10. 分批实施与可回滚方式

| 批次 | 范围 | 完成标志 | 回滚方式 |
|---|---|---|---|
| S0 清点 | 实际菜单、角色、深链接、使用记录、隐藏历史能力 | 每个待删入口有替代位置与权限映射 | 无业务变更 |
| S1 重复入口收敛 | N01～N07，任务/详情/Token/资产缺陷环境 | 相同业务只剩一个主入口，旧链接仍有效 | 恢复旧导航配置，数据/API 不变 |
| S2 配置下沉 | 环境、登录、凭据、Runner、租约、告警 | 测试员不再承担管理员配置，管理员功能可达 | 回切旧配置页，复用同一 API |
| S3 资产与界面减负 | 资产主标签、详情版本、证据、列表字段及表单 | 常见任务可用少量清晰步骤完成 | 保留组件切换，不反向搬运数据 |
| S4 观察与退役 | 对照访问/错误/支持反馈，清理无引用组件 | 没有遗漏功能或活跃旧入口 | 延长兼容期；不删除历史表 |

先构建替代入口、验证、再移除原主入口。新旧页面同时可用仅用于短期验证，不能长期并列造成更臃肿。

审批能力未完成时，S1 仍可合并当前真实任务页；不得为了精简专项等待整套门禁开发，也不得用占位审批宣称闭环完成。

## 12. 判断是否真正变简洁

| 指标 | 改造目标 | 说明 |
|---|---|---|
| Agent 主工作区标签 | 从源码定义 12 项收敛为任务与真实可用审批两项 | 资源功能迁设置，不全删 |
| 测试资产主标签 | 从源码定义 10 项收敛为 2～3 项 | 版本/关系/证据在对象上下文访问 |
| 相同任务/Token 的主要维护入口 | 各一处 | 允许上下文快捷入口，但落到同一页面 |
| 测试员创建普通任务前必须填写的高级配置 | 使用已配置环境时不要求填写模型、Prompt、Runner、租约等 | 后端前置条件同步调整，不能只改表单 |
| 旧链接失败、权限扩大、历史数据丢失 | 验收样本中为零 | 需要实际测试证明，不在方案阶段宣称达成 |
| 找入口耗时、重复配置次数 | 试点前后对比下降 | 不虚构现网基线或提升百分比 |

建议用“创建一次任务、查看一次失败、处理一次审批、找到一份文档、配置一个接入”五条路径做用户走查。菜单数量下降只是辅证，任务能否顺畅完成才是最终判断。
