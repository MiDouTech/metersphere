# MeterSphere 模块状态保持与测试用例详情聚合改造方案

> 日期：2026-07-30  
> 范围：全局一级业务模块、功能测试用例列表与详情  
> 文档性质：产品与技术联合改造方案，不包含本次代码实施

## 1. 改造目标

本次改造解决两类问题：

1. 模块切换不再打断用户工作现场。进入页面及相关数据发生变更时自动刷新数据，但刷新过程必须保留树展开、筛选、分页、滚动位置、显示模式和已打开详情等页面形态。
2. 功能用例详情从“多 Tab 分散查看”调整为“详情集中呈现”，补齐最后执行人、文本用例提缺陷、评审/计划摘要和个人执行进度。

## 2. 现状基线与关键结论

| 项目 | 当前实现 | 改造结论 |
|---|---|---|
| 页面缓存 | `page-layout.vue` 已使用 `keep-alive`，但路由离开后会按 `cachePath/toPathName` 清理缓存 | 调整为业务模块常驻缓存，并增加受控刷新，不做全局无条件缓存 |
| 功能用例页面 | 树、表格、筛选已有局部状态；部分组件在 `onActivated` 中重新加载时会重置页面 | 进入/返回模块时刷新最新数据，但将数据刷新与页面形态初始化解耦 |
| 刷新入口 | 部分表格已有 `@refresh`，各模块行为不统一，尚未全局安装 | 所有具备动态数据的业务模块统一安装刷新按钮并接入统一刷新协议 |
| 执行人 | `functional_case.execute_user` 已存在，并已用于列表、筛选和基本信息 | 该字段定义为“责任执行人”，新增独立“最后执行人”字段，避免语义混用 |
| 文本用例提缺陷 | STEP 模式已有 `report-defect` 链路，TEXT 预期结果右侧无入口 | 复用现有缺陷抽屉和权限校验，补 TEXT 入口 |
| 详情 Tab | 仍有用例、依赖关系、评论、用例评审、测试计划等 Tab | 删除指定 Tab；评论内嵌详情；评审与计划改为标题下摘要 |

## 3. 总体交互设计

### 3.1 模块状态生命周期

状态分为两层：

- 组件缓存状态：树展开节点、选中节点、筛选条件、排序、分页、滚动位置、已打开的详情抽屉和详情 Tab。通过 Vue `keep-alive` 保留，切换模块时不销毁。
- 可恢复状态：按“用户 + 组织 + 项目 + 路由”保存核心页面状态。用于浏览器刷新或缓存淘汰后恢复，建议使用 Pinia 持久化或 `localStorage/localforage`。

建议状态键：

```text
ms.moduleViewState.{userId}.{organizationId}.{projectId}.{routeName}
```

状态恢复边界：

- 首次进入页面：自动加载最新数据，并恢复该作用域上次保存的页面形态。
- 切换一级模块再返回：自动刷新最新数据，同时完整保持离开前的页面形态。
- 切换项目、组织：使用对应作用域的独立状态，不串用。
- 数据变更事件：自动刷新受影响区域，保持当前页面形态。
- 主动点击刷新：保留视图状态，重新拉取当前模块全部必要数据并校正失效项。
- 退出登录、权限丢失：清理不可访问作用域的缓存。
- 用例/模块已被其他人删除：刷新后移除失效选中项，回退到最近有效父节点或根节点。
- 创建、编辑、删除、执行结果更新、关联关系变更成功：立即执行相关局部刷新，不等待用户手动刷新。

刷新与页面形态必须解耦：

- “刷新”只替换业务数据，不重新创建页面状态对象。
- 刷新后仍保持已展开的树节点、当前选中节点、筛选条件、排序、分页、滚动位置和展示模式。
- 用户已打开用例详情时，刷新详情数据但不关闭详情，不退回用例列表。
- 用户停留在详情中的某个 Tab、评论区或编辑区域时，刷新后保持当前位置；存在未保存编辑内容时不得被后台刷新覆盖。
- 只有当前对象被删除、权限被撤回、项目/组织作用域变化等导致原形态客观失效时，才执行有提示的降级回退。

### 3.2 统一刷新按钮

在所有具备动态数据的一级、二级业务页面内容区右上角安装统一图标按钮，文案/提示为“刷新”，使用公共组件 `MsModuleRefresh`。不得只在测试用例等少数页面试点后停止铺设。

刷新协议：

```ts
interface ModuleRefreshContext {
  reason: 'initial' | 'activated' | 'data-change' | 'manual';
  preserveViewState: true;
  changedResources?: Array<{
    type: string;
    id?: string;
  }>;
}

interface ModuleRefreshResult {
  refreshedAt: number;
  partialFailures?: string[];
}
```

规则：

- 点击后按钮进入 loading，防止重复提交。
- 页面首次进入、从其他模块返回以及收到本模块相关数据变更事件时，自动调用同一刷新协议。
- 刷新当前模块所需的树、列表、统计和当前打开详情，不重置树展开、筛选、分页与滚动位置。
- 自动刷新与手动刷新共用数据加载逻辑，区别仅在触发原因和刷新范围，不能维护两套结果不一致的实现。
- 若当前页刷新后为空，页码回退到最后一个有效页。
- 同一页面多个接口并行请求；部分失败时展示具体失败区域，并保留旧数据。
- 不采用 `window.location.reload()`。
- 高频数据变更事件需要合并和防抖；页面不可见时记录为待刷新，重新激活后合并执行一次。

必须建立模块安装清单，至少覆盖：工作台、项目管理、测试用例、接口测试、测试计划、缺陷管理、报表、系统设置及其具备独立数据上下文的二级页面。纯静态说明页、无任何服务端数据的页面可以不显示。

刷新按钮全局安装验收以路由清单为准：每个动态页面必须标记“已安装”“复用父级刷新”或“不适用及原因”，不得仅凭抽样页面判定完成。

## 4. 分项改造方案

### 4.1 需求 1：自动刷新最新数据并保持页面形态

前端改造：

1. 修改 `frontend/src/layout/page-layout.vue` 的缓存清理策略。一级业务页进入缓存白名单，普通模块跳转不再删除其缓存；编辑页、创建页、一次性详情页仍按现有规则清理。
2. 为需保持状态的路由增加 `meta.keepModuleAlive = true`，组件 `name` 与路由缓存名保持一致。
3. 梳理各页面 `onActivated`：激活时允许刷新最新数据，但禁止重新执行会清空视图状态的页面初始化。将 `initializeViewState()` 与 `refreshData()` 拆分。
4. 功能用例页建立 `FeatureCaseViewState`，至少包含：

```ts
interface FeatureCaseViewState {
  expandedTreeKeys: string[];
  selectedTreeKeys: string[];
  activeFolderIds: string[];
  includeChildren: boolean;
  filter: unknown;
  sort: unknown;
  page: number;
  pageSize: number;
  scrollTop: number;
  displayMode: 'table' | 'xmind';
  detailCaseId?: string;
  detailActiveTab?: string;
}
```

5. 监听项目/组织变化，切换状态作用域；不复用上一个项目的模块树节点。
6. 建立数据变更事件机制。当前页面创建、编辑、删除成功后直接发布变更；跨页面或跨用户更新可通过事件总线、WebSocket/SSE 或激活时版本校验触发刷新。
7. 列表和详情分别按资源 ID 合并新数据；刷新已打开用例时只更新详情内容，不修改 `detailCaseId` 和详情打开状态。

注意：不建议只依赖 Pinia 保存几个字段。树组件内部展开状态、抽屉和滚动位置仍会因组件卸载而丢失，必须以 `keep-alive` 为主、持久化状态为兜底。

### 4.2 需求 2：每个模块增加刷新按钮

新增公共组件和 hook：

- `frontend/src/components/business/ms-module-refresh/index.vue`
- `frontend/src/hooks/useModuleRefresh.ts`

各模块页面通过 `expose({ refresh })` 或统一事件接入；公共布局根据路由元数据统一渲染按钮，避免每个页面自行复制按钮。功能用例模块刷新范围：

1. 模块树与数量；
2. 当前条件下的用例列表；
3. 当前已打开用例详情、评论、摘要和个人进度；
4. 用户视图/筛选元数据仅在配置变更或接口明确要求时刷新。

刷新完成后展示“刷新成功”，并可显示最后刷新时间。

全局铺设要求：

1. 增加动态页面路由清单及刷新能力注册表；
2. 公共布局负责按钮位置、loading、提示和最后刷新时间；
3. 业务页面只负责声明刷新任务及视图快照/恢复方法；
4. 无刷新实现的动态页面在开发环境给出告警，避免遗漏；
5. 自动化测试逐条遍历路由清单，验证刷新按钮存在且刷新后页面形态不变。

### 4.3 需求 3：新增“最后执行人”

#### 4.3.1 字段语义

必须区分：

| 字段 | 含义 | 是否允许手工修改 |
|---|---|---|
| `execute_user` | 责任执行人/被分配的执行人 | 是 |
| `last_execute_user` | 最近一次实际改变用例执行结果的用户 | 否 |

新增数据库字段：

```sql
ALTER TABLE functional_case
  ADD COLUMN last_execute_user VARCHAR(50) DEFAULT NULL COMMENT '最后执行人用户ID',
  ADD INDEX idx_functional_case_last_execute_user (last_execute_user);
```

不增加外键，保持与现有用户字段及历史用户删除场景一致。

写入规则：

- 用户在功能用例详情、批量执行结果或测试计划内实际提交执行结果时，更新 `last_execute_user = 当前登录用户`。
- 仅分配/修改责任执行人、编辑用例内容、导入用例时不更新。
- 计划内执行结果同步回用例总结果时，同时同步真实操作人；异步回调需显式携带触发用户，不能使用系统账号覆盖。
- 将结果重置为“未执行”也属于一次执行状态操作，记录操作者。
- 历史数据不回填，展示 `-`；若能从可靠执行历史唯一推导，可另做离线回填，不放入发布迁移。

接口与 DTO：

- 列表、详情返回 `lastExecuteUser`、`lastExecuteUserName`。
- 高级筛选增加 `lastExecuteUser` 条件，按用户 ID 过滤，支持“为空”。
- 列表列设置增加“最后执行人”，默认建议显示在“执行人”右侧。
- 基本信息 Tab 在“执行人”右侧或下一行显示“最后执行人”。
- 导出建议增加该列；导入模板不增加，因为该字段不可人工写入。

后端主要改造：

- `FunctionalCase` 领域模型及 MyBatis 生成文件；
- `ExtFunctionalCaseMapper.xml` 查询、排序和筛选；
- 功能用例执行结果更新服务；
- 测试计划执行结果同步服务；
- 列表/详情 DTO、筛选字段定义和导出模型。

### 4.4 需求 4：TEXT 预期结果行增加“提缺陷”

在 TEXT 模式“预期结果”标题行最右侧增加按钮：

```text
预期结果                                      [提缺陷]
```

规则：

- 仅只读/执行态展示；编辑态隐藏，避免与保存操作冲突。
- 权限沿用现有缺陷创建权限；无权限不显示。
- 点击复用 STEP 模式现有 `handleReportDefect` 和缺陷抽屉。
- 自动带入用例 ID、用例名称、前置条件、文本描述、预期结果、当前执行结果、附件和所属项目。
- 创建成功后刷新详情中的关联缺陷数量/列表，不重置当前详情滚动位置。

### 4.5 需求 5：“用例”更名为“前置用例”

仅修改功能用例详情 Tab 的展示文案：

- 中文：“用例” → “前置用例”
- 英文：“Cases” → “Preceding Cases”或产品统一术语“Prerequisite Cases”

内部 key 保持 `case`，组件与 API 不改名，以降低兼容风险。需要确认该 Tab 当前实际展示的是前置关联；若同时包含后置用例，应改名为“关联用例”，不能以文案掩盖业务含义。

### 4.6 需求 6：删除“依赖关系”Tab

前端从默认 Tab、显示设置和详情动态组件中移除 `dependency`。

后端表和接口本期不删除，原因：

- 历史依赖数据仍可能被其他页面、导入导出或旧链接使用；
- “前置用例”功能可能仍依赖关系模型；
- 保留后端便于灰度回滚。

待确认无调用并经过一个发布周期后，再单独评估废弃接口和清理数据。

### 4.7 需求 7：删除“评论”Tab，评论内嵌详情

目标布局：

```text
详情内容
附件
评论（数量）
  评论输入框
  全部用户评论，按时间倒序
  回复 / @用户 / 附件 / 删除本人评论
```

改造规则：

- 从 Tab 设置、动态组件分支和详情底部悬浮评论输入框中移除 `comments`。
- `TabComment` 重构为可内嵌区块，挂在 `TabDetail` 的附件区下方。
- 发布、回复、删除后局部刷新评论列表并更新数量，不重新加载整个用例详情。
- 默认展示最近 20 条，向下滚动或点击“加载更多”分页加载；发布成功的新评论立即置顶。
- 保留现有评论权限、通知、@用户、附件、回复关系与删除规则，后端数据模型无需迁移。
- 原来指向评论 Tab 的链接或事件改为：打开详情 Tab 后滚动并聚焦评论区。

### 4.8 需求 8：删除“用例评审/测试计划”Tab，标题下展示摘要

在标题下、Tab 导航上方增加“关联摘要区”：

```text
评审（CR-1001）：评审中
测试计划（TP-2001）：45%
```

一个用例可关联多个评审和多个测试计划，不能按单值设计。展示规则：

- 每类默认展示最近更新的 2 条，其余以“还有 N 条”展开。
- ID/名称可点击并按权限跳转到对应详情；无权限时仅展示文本。
- 已删除关联不展示；已归档项展示“已归档”标识。
- 评审状态使用当前用例在该评审中的状态，不使用整个评审任务的总状态。
- 测试计划进度定义为：计划内已执行用例数 / 计划内用例总数。若产品更希望展示当前用例在计划中的执行状态，应改为“测试计划（ID）：当前用例状态”，二者不可混称。

建议新增聚合接口，避免打开详情后发起多个串行请求：

```http
GET /functional/case/{caseId}/overview
```

响应建议：

```json
{
  "reviews": [
    { "id": "CR-1001", "name": "登录评审", "caseStatus": "UNDER_REVIEW", "archived": false }
  ],
  "testPlans": [
    {
      "id": "TP-2001",
      "name": "回归计划",
      "progress": { "executed": 45, "total": 100, "rate": 45 },
      "archived": false
    }
  ],
  "personalProgress": {}
}
```

原评审和测试计划 Tab 的后端查询接口保留，前端不再展示入口。

### 4.9 需求 9：标题下增加个人执行进度

#### 4.9.1 统计口径

按需求文字，建议采用“当前项目责任执行人为当前用户的功能用例”口径：

- 分母：当前项目中 `functional_case.execute_user = 当前用户` 且未删除的用例总数。
- 分子：上述用例中 `last_execute_result` 不为空且不为 `PENDING/UN_EXECUTED` 的数量。
- 状态分段：通过、失败、阻塞、跳过、未执行之和必须等于分母。
- 当前查看的用例是否属于某测试计划，不影响个人项目进度。

展示：

```text
个人执行进度：28/40  [绿色 18][红色 4][紫色 2][灰色 4][蓝色 12]
```

颜色：

| 状态 | 颜色 | 建议变量 |
|---|---|---|
| 通过 | 绿色 | `success-6` |
| 失败 | 红色 | `danger-6` |
| 阻塞 | 紫色 | 新增统一状态色或复用产品状态色 |
| 跳过 | 灰色 | `text-n5` |
| 未执行 | 蓝色 | `primary-5` |

进度条每个分段提供 tooltip，显示“状态：数量（占比）”；不能只用颜色表达，需同时支持色弱用户和无障碍标签。

#### 4.9.2 查询实现

个人进度属于“项目 + 当前用户”维度，与用例 ID 无关，建议：

```http
GET /functional/case/personal-progress?projectId={projectId}
```

也可并入 `/functional/case/{caseId}/overview`，但后端内部应按 `projectId + userId` 做 30～60 秒短缓存。用例执行结果、责任执行人或删除状态改变后主动失效。

查询建议一次条件聚合完成：

```sql
SELECT
  COUNT(*) AS total,
  SUM(last_execute_result NOT IN ('', 'PENDING', 'UN_EXECUTED')) AS executed,
  SUM(last_execute_result = 'SUCCESS') AS passed,
  SUM(last_execute_result = 'ERROR') AS failed,
  SUM(last_execute_result = 'BLOCKED') AS blocked,
  SUM(last_execute_result = 'SKIPPED') AS skipped,
  SUM(last_execute_result IS NULL OR last_execute_result IN ('', 'PENDING', 'UN_EXECUTED')) AS unexecuted
FROM functional_case
WHERE project_id = :projectId
  AND execute_user = :currentUserId
  AND deleted = false;
```

具体状态枚举以仓库现有枚举为准，禁止在 SQL、Java 和前端分别维护不同映射。

## 6. 接口、模型与兼容性清单

### 6.1 新增

- `functional_case.last_execute_user`
- 列表/详情 DTO：`lastExecuteUser`、`lastExecuteUserName`
- 用例概览 DTO：评审摘要、测试计划摘要
- 个人执行进度 DTO
- 用例概览与个人进度查询接口
- 通用模块刷新组件和页面刷新协议

### 6.2 修改

- 功能用例执行结果所有写入口统一写入最后执行人
- 功能用例列表查询、排序、筛选和导出
- 详情 Tab 配置、显示设置、评论布局
- TEXT 预期结果布局及提缺陷入口
- 页面缓存策略和各模块 `onActivated`

### 6.3 保留但隐藏

- 依赖关系、评审、计划、评论原后端接口
- 原 Tab key 的兼容解析：旧本地设置中包含被删除 key 时静默过滤，并将非法 activeTab 回退到 `detail`

## 7. 实施拆分与顺序

| 阶段 | 内容 | 预估 |
|---|---|---:|
| M1 | 模块缓存策略、视图状态模型、统一刷新组件；先接功能用例和测试计划 | 3～4 人日 |
| M2 | 最后执行人 DDL、领域模型、所有执行写入口、列表/筛选/详情/导出 | 3～4 人日 |
| M3 | TEXT 提缺陷、Tab 更名/删除、评论内嵌 | 2～3 人日 |
| M4 | 评审/计划概览接口、标题下摘要、个人进度聚合与进度条 | 4～5 人日 |
| M5 | 全模块刷新接入、自动化测试、性能与兼容回归 | 3～5 人日 |

合计约 15～21 人日，建议两名前端与一名后端并行，M1 的缓存协议和 M2 的字段语义先行冻结。

## 8. 测试与验收标准

### 8.1 状态保持与刷新

- 展开多层用例树、设置筛选/排序/分页并滚动后，切到测试计划再返回；系统自动刷新最新数据，但所有页面形态保持一致，且不出现闪烁重置。
- 不同项目分别记忆状态，互不污染。
- 点击刷新后树和列表数据更新，但展开、筛选、分页和滚动位置保持。
- 用户停留在用例详情时发生自动或手动刷新，详情继续打开且仍为同一用例，不退回列表。
- 创建、编辑、删除及跨页面数据变更后自动刷新受影响数据，无需用户手动触发。
- 数据删除导致当前选择失效时能安全回退，无空白页或报错。
- 按动态页面路由清单验收全局刷新按钮，不允许只抽样验证少数模块。

### 8.2 最后执行人

- 责任执行人与最后执行人可为不同用户。
- 修改责任执行人不改变最后执行人；提交执行结果会更新最后执行人。
- 详情、列表、筛选、排序、导出结果一致。
- 历史空值显示 `-`；已删除用户显示保留名称快照或“用户已删除”，不得接口报错。
- 计划内执行、批量执行和直接在用例详情执行三条链路均覆盖。

### 8.3 详情聚合

- TEXT 预期结果右侧可正常提缺陷并正确回填上下文。
- 详情不再出现四个被删除 Tab；旧 Tab 配置不会导致空白内容。
- “前置用例”文案与实际数据语义一致。
- 评论发布后在详情中立即可见，刷新、分页、回复、@、附件和权限正常。
- 多评审、多计划可展开且状态/进度口径正确，点击跳转受权限控制。
- 个人进度分子、分母、各颜色分段与数据库统计一致，五种状态之和等于总数。

### 8.4 性能指标

- 返回已缓存模块的可交互时间目标小于 300 ms；后台自动刷新不得阻塞缓存页面恢复和用户继续操作。
- 高频数据变更事件合并刷新，避免同一页面短时间重复请求主列表。
- 用例概览和个人进度接口 P95 目标小于 500 ms。
- 打开详情首屏不因评论全量加载阻塞；评论必须分页。

## 9. 风险与上线策略

| 风险 | 应对 |
|---|---|
| 页面常驻导致内存增长 | 只缓存一级业务页，设置最大缓存数量；低频页按 LRU 淘汰 |
| 缓存数据过旧 | 页面进入/激活自动刷新、数据变更局部刷新、手动刷新及权限/项目变化强制校验 |
| 自动刷新覆盖页面形态或未保存内容 | 数据刷新与视图初始化解耦，按资源 ID 合并；编辑态暂停覆盖并提示冲突 |
| `execute_user` 被误当最后执行人 | 字段、DTO、文案和写入服务完全分离，并补单元测试 |
| 多评审/多计划摘要接口产生 N+1 | 后端批量查询并聚合，禁止逐条调用详情接口 |
| 删除 Tab 影响旧用户配置 | 读取配置时过滤废弃 key，activeTab 自动回退 |
| 状态颜色枚举不一致 | 复用统一执行状态枚举及前端映射 |

建议使用功能开关分两批上线：

1. 先上线模块状态保持、刷新按钮和最后执行人；
2. 再上线详情 Tab 收敛、概览摘要和个人进度。

## 10. 开发前需冻结的产品口径

本方案已给出推荐默认值，开发评审时需正式确认以下三点：

1. “最后执行人”是最后一次改变执行结果的操作者，而不是当前责任执行人。
2. “测试计划进度”是整个计划已执行数/总数，而不是当前用例在计划中的执行状态。
3. “个人执行进度”按当前项目中责任执行人为当前用户的功能用例统计，不限定当前用例关联的测试计划。

若任一点采用不同定义，应先更新接口字段名和页面文案，再进入开发，避免统计正确但用户理解错误。
