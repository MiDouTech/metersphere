# MeterSphere 统一权限体系改造方案

> 文档日期：2026-08-28
> 文档状态：设计完成，尚未实施
> 适用范围：系统、组织、项目三级角色与权限控制
> 核心目标：将现有业务/API 权限与页面/Tab/按钮权限合并为一套权限数据源和一套授权决策机制

## 1. 背景与问题

当前系统同时存在两类权限数据：

1. `user_role_permission`：控制后端业务接口及部分前端操作权限。
2. `permission_resource`、`user_role_ui_permission`：控制页面、Tab、按钮的可见与可用状态。

两套数据分别配置和计算，容易出现以下问题：

- 前端显示可操作，但后端接口拒绝。
- 前端隐藏功能，但用户实际拥有后端权限。
- 同一业务动作需要在两处配置，容易遗漏或产生冲突。
- 管理员依赖角色 ID 或特殊判断绕过，作用域、启用状态和成员关系校验不统一。
- `permission_member`、`project_member` 等成员角色的默认权限过宽，角色语义不清晰。
- `member`、`permission_member`、`org_member`、`project_member` 等新旧角色并存。

本次改造将权限配置统一为一套，但前端与后端仍承担不同职责：前端负责交互提示和入口控制，后端负责最终授权裁决。

## 2. 改造目标

### 2.1 总体目标

- 一个权限目录：所有页面访问和业务操作使用统一权限编码。
- 一个角色权限关系：普通角色只通过一张角色权限关系表授权。
- 一个作用域角色关系：用户在系统、组织、项目中的角色通过统一关系表达。
- 一个授权服务：所有后端授权判断从统一服务进入。
- 一组共享权限编码：前端入口和后端接口引用同一权限编码。
- 管理员继续在对应作用域内无条件放权。
- 六类必备角色默认存在、不可删除，允许编辑成员。
- 从管理员角色移出的用户自动回落到同作用域的成员角色。

### 2.2 非目标

- 不将前端判断作为安全边界。
- 不通过角色名称判断管理员身份。
- 不允许组织管理员或项目管理员越过所属作用域。
- 不在一次发布中直接删除旧权限表；迁移需要灰度、对比和回滚窗口。
- 不用固定成功、Mock 数据或空实现代替真实授权逻辑。

## 3. 核心设计原则

### 3.1 管理员无条件放权

管理员在其有效作用域内不依赖逐项权限配置：

| 管理员角色 | 放权范围 |
| --- | --- |
| 系统管理员 | 全系统所有组织、项目和系统设置 |
| 组织管理员 | 指定组织及该组织下属项目 |
| 项目管理员 | 指定项目 |

“无条件放权”仅表示不校验权限点，不表示跳过以下基础条件：

- 用户与管理员角色的成员关系有效。
- 角色有效且未被非法篡改。
- 角色作用域与当前资源匹配。
- 组织管理员访问的项目属于其组织。
- 项目管理员访问的资源属于其项目。

管理员判定必须由统一授权服务完成，禁止业务模块自行通过角色名称或零散 `isAdmin()` 逻辑放权。

### 3.2 后端最终裁决

前端的页面、Tab、按钮控制仅用于改善用户体验。用户即使绕过前端直接调用接口，后端仍必须执行相同权限编码和资源作用域校验。

### 3.3 权限编码原子化

权限编码按“作用域 + 资源 + 动作”组织，不使用 `READ+UPDATE` 等组合权限：

```text
SYSTEM.USER.READ
SYSTEM.USER.UPDATE
ORGANIZATION.MEMBER.READ
ORGANIZATION.MEMBER.UPDATE
PROJECT.FUNCTIONAL_CASE.READ
PROJECT.FUNCTIONAL_CASE.CREATE
PROJECT.FUNCTIONAL_CASE.UPDATE
PROJECT.FUNCTIONAL_CASE.DELETE
```

一个按钮可以依赖一个或多个原子权限；一个后端接口也必须声明完成该动作所需的原子权限。

## 4. 默认角色模型

系统必须默认存在以下六类角色：

| 角色 | 作用域 | 管理员级别 | 可删除 | 可停用 | 可改名 | 可编辑权限 | 可编辑成员 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 系统管理员 | SYSTEM | SYSTEM | 否 | 否 | 否 | 否，固定全权限 | 是 |
| 系统成员 | SYSTEM | NONE | 否 | 否 | 否 | 是 | 是 |
| 组织管理员 | ORGANIZATION | ORGANIZATION | 否 | 否 | 否 | 否，组织内全权限 | 是 |
| 组织成员 | ORGANIZATION | NONE | 否 | 否 | 否 | 是 | 是 |
| 项目管理员 | PROJECT | PROJECT | 否 | 否 | 否 | 否，项目内全权限 | 是 |
| 项目成员 | PROJECT | NONE | 否 | 否 | 否 | 是 | 是 |

建议角色表增加或规范以下字段：

```text
built_in       是否为内置角色
required       是否为必备角色
admin_level    NONE / SYSTEM / ORGANIZATION / PROJECT
scope_type     SYSTEM / ORGANIZATION / PROJECT
enabled        是否启用
```

约束要求：

- `required = true` 的角色禁止删除。
- 内置角色的名称、作用域、管理员级别不得通过普通接口修改。
- 管理员角色的权限配置只读，不向 `role_permission` 写入全量权限。
- 默认成员角色按最小权限初始化，禁止以“全部权限”作为默认配置。
- 自定义角色允许新增、修改、停用和删除，但删除前必须处理其成员关系。

## 5. 原“权限控制 → 角色设置”管理员处理

### 5.1 原位升级，不删除重建

原有管理员角色应保留原角色 ID，原位升级为统一权限体系中的内置管理员角色：

| 原角色 | 目标角色 | 迁移方式 |
| --- | --- | --- |
| `admin` / 系统管理员 | 系统管理员 | 保留 ID，设置内置、必备及 SYSTEM 管理员级别 |
| `org_admin` / 组织管理员 | 组织管理员 | 保留 ID，按组织 `source_id` 校验成员关系 |
| `project_admin` / 项目管理员 | 项目管理员 | 保留 ID，按项目 `source_id` 校验成员关系 |
| 名称中包含“管理员”的自定义角色 | 普通自定义角色 | 不获得管理员标识，继续按权限点授权 |

保留角色 ID 可避免成员关系、审计记录、历史数据及外部引用失效。

### 5.2 页面交互

管理员角色在角色设置页面应表现为：

- 显示“内置角色”“对应作用域内全部权限”标识。
- 权限页签只读，可展示权限说明，但不能勾选或取消。
- 成员页签可编辑，可添加或移除管理员。
- 隐藏或禁用删除、停用、改名、修改作用域等操作。
- 修改管理员成员后立即刷新相关用户的权限缓存和登录态。
- 后端必须重复校验上述规则，不能仅依赖前端隐藏按钮。

### 5.3 管理员移除后的回落

成员从管理员角色移除后，自动加入同一作用域的默认成员角色：

```text
系统管理员   → 系统成员
组织管理员   → 相同组织的组织成员
项目管理员   → 相同项目的项目成员
```

业务规则：

- 管理员移除与成员角色回落必须在同一个数据库事务中完成。
- 用户已具有目标成员角色时，不重复写入。
- 单个移除和批量移除使用同一服务逻辑。
- 不允许移除最后一个有效系统管理员。
- 不允许通过直接调用成员接口绕过最后管理员保护。
- 操作成功后失效受影响用户的授权缓存。
- 记录操作者、目标用户、原角色、回落角色、作用域和时间等审计信息。

## 6. 目标数据模型

### 6.1 权限目录 `permission`

统一保存可授权的业务能力：

```text
id
code                 全局唯一权限编码
name                 展示名称
scope_type           SYSTEM / ORGANIZATION / PROJECT
resource_type        PAGE / TAB / ACTION / API_GROUP
parent_id            用于权限树展示
risk_level           NORMAL / SENSITIVE / DANGEROUS
enabled
created_at
updated_at
```

`resource_type` 用于展示和分类，不形成第二套授权关系。页面、Tab、按钮最终都映射到统一 `permission.code`。

### 6.2 角色 `role`

```text
id
name
scope_type
built_in
required
admin_level
enabled
created_at
updated_at
```

### 6.3 角色权限 `role_permission`

```text
role_id
permission_id
created_at
created_by
```

建议唯一约束：`(role_id, permission_id)`。

管理员角色不需要写入全部权限明细；其放权行为由受控的 `admin_level` 规则表达。

### 6.4 用户角色关系 `role_assignment`

```text
id
user_id
role_id
scope_type
source_id
enabled
created_at
created_by
```

建议唯一约束：`(user_id, role_id, scope_type, source_id)`。

其中：

- SYSTEM 的 `source_id` 使用固定系统标识。
- ORGANIZATION 的 `source_id` 为组织 ID。
- PROJECT 的 `source_id` 为项目 ID。

### 6.5 UI 资源映射

若需要保留路由、页面、Tab、按钮的资源树，可保留资源登记表，但它只承担映射职责：

```text
ui_resource.resource_code → permission.code
```

不得继续维护“UI 独立授权结果”。原 `user_role_ui_permission` 在迁移完成后退出授权链路。

## 7. 统一授权决策

建议新增统一的 `AuthorizationService`，输入至少包括：

```text
userId
permissionCode
scopeType
scopeId
resourceType（可选）
resourceId（可选）
```

授权顺序：

```text
1. 校验用户及角色关系有效性
2. 若为有效系统管理员，允许
3. 若为有效组织管理员，校验目标资源属于该组织后允许
4. 若为有效项目管理员，校验目标资源属于该项目后允许
5. 聚合用户在当前作用域内普通角色的权限
6. 判断是否包含 permissionCode
7. 对需要所有者、创建者或数据范围限制的资源继续执行资源级校验
8. 任一条件不满足则拒绝
```

建议后端逐步统一为类似声明：

```java
@Authorize(
    permission = "PROJECT.FUNCTIONAL_CASE.UPDATE",
    scopeType = "PROJECT",
    scopeId = "#request.projectId",
    resourceType = "functional_case",
    resourceId = "#request.id"
)
```

现有 `@RequiresPermissions`、`SessionUtils.hasPermission()`、`@CheckOwner` 不应一次性删除，应先通过适配层转发到统一授权服务，再逐步收敛。

## 8. 前端改造

### 8.1 权限数据

登录态返回当前用户的有效权限编码和作用域管理员信息。前端不再分别读取业务权限和 UI 权限决定同一个动作。

建议响应示例：

```json
{
  "permissions": [
    "PROJECT.FUNCTIONAL_CASE.READ",
    "PROJECT.FUNCTIONAL_CASE.UPDATE"
  ],
  "adminScopes": [
    { "level": "PROJECT", "sourceId": "project-id" }
  ]
}
```

### 8.2 页面和按钮

- 路由：使用统一 READ 权限编码。
- 页面内部 Tab：使用对应 READ 权限编码。
- 新增按钮：使用 CREATE 权限编码。
- 编辑按钮：使用 UPDATE 权限编码。
- 删除按钮：使用 DELETE 权限编码。
- 管理员：前端权限工具按当前作用域识别放权，用于展示；后端仍重新裁决。

现有 `v-permission`、`v-visible-permission`、`v-operable-permission` 应逐项迁移为统一指令或组合式函数。迁移期间必须标明 legacy 与 unified，避免重复判断。

### 8.3 状态与错误处理

角色设置及成员维护页面必须覆盖：

- loading
- empty
- success
- validation-error
- permission-denied
- network-error
- server-error

后端权限拒绝使用统一错误协议，并返回用户可理解的信息；技术异常和堆栈只写日志。

## 9. 后端接口建议

以下为目标接口，最终路径可按项目现有 Controller 规范调整：

| 功能 | 方法与路径 | 权限与规则 |
| --- | --- | --- |
| 查询角色 | `POST /permission/role/list` | 按当前管理作用域过滤 |
| 查询角色详情 | `GET /permission/role/{id}` | 校验角色作用域 |
| 新增自定义角色 | `POST /permission/role` | 禁止伪造内置或管理员字段 |
| 修改角色 | `PUT /permission/role/{id}` | 必备角色保护；内置字段不可改 |
| 删除角色 | `DELETE /permission/role/{id}` | 必备角色禁止删除；校验成员迁移 |
| 保存普通角色权限 | `PUT /permission/role/{id}/permissions` | 管理员角色拒绝修改权限 |
| 查询角色成员 | `POST /permission/role/{id}/members` | 按作用域过滤 |
| 添加角色成员 | `POST /permission/role/{id}/members/add` | 校验用户和角色属于同一有效作用域 |
| 移除角色成员 | `POST /permission/role/{id}/members/remove` | 管理员回落；最后系统管理员保护 |
| 查询有效权限 | `GET /permission/effective` | 返回当前用户当前作用域的有效权限 |

所有写接口必须进行参数校验、权限校验、作用域校验、业务规则校验、事务处理和审计记录。

## 10. 数据迁移方案

### 阶段一：盘点与映射

1. 冻结新增的旧权限编码和 UI 独立授权类型。
2. 导出现有角色、角色成员、业务权限和 UI 权限。
3. 建立旧权限到统一权限编码的映射表。
4. 标识冲突：同一动作在业务权限允许但 UI 权限拒绝，或反之。
5. 对成员默认权限进行最小权限评审。

### 阶段二：扩展模型

1. 新建统一权限目录和角色权限关系，或在现有表上完成兼容扩展。
2. 为角色补充 `built_in`、`required`、`admin_level`、`scope_type`。
3. 原位升级系统、组织和项目管理员。
4. 创建或修复系统成员、组织成员、项目成员默认角色。
5. 增加唯一约束和必要索引。

### 阶段三：双写与影子判定

1. 权限配置变更同时写入新旧关系。
2. 正式授权仍读取旧体系。
3. 统一授权服务在影子模式下计算新结果，不影响请求结果。
4. 记录新旧判定差异，但日志中不得泄露敏感数据。
5. 差异达到可接受阈值后进入切换阶段。

### 阶段四：切换后端

1. 后端接口逐模块切换为统一授权服务。
2. 管理员全部改由统一的作用域放权规则判断。
3. 保留旧读开关用于紧急回滚。
4. 对高风险接口优先执行直接调用和越权测试。

### 阶段五：切换前端

1. 登录态返回统一有效权限。
2. 路由、页面、Tab、按钮逐模块迁移。
3. 删除同一动作上的新旧双重前端判断。
4. 完成页面状态和权限错误交互。

### 阶段六：下线旧体系

1. 停止旧表双写。
2. 完成至少一个稳定版本观察期。
3. 备份旧权限数据。
4. 删除旧读取逻辑和废弃指令。
5. 最后删除或归档 `user_role_ui_permission` 等旧表。

## 11. 异常与边界条件

- 删除必备角色：拒绝，提示“系统内置角色不可删除”。
- 停用管理员角色：拒绝，提示“内置管理员角色不可停用”。
- 修改管理员权限：拒绝，提示“管理员在对应作用域内固定拥有全部权限”。
- 移除最后一个系统管理员：拒绝，且不修改任何成员关系。
- 移除管理员后成员回落失败：整个事务回滚。
- 重复添加成员：幂等成功或返回明确提示，不产生重复记录。
- 组织管理员访问其他组织：拒绝。
- 项目管理员访问其他项目：拒绝。
- 组织已删除或项目归属变更：失效或重新计算相关角色关系及缓存。
- 用户禁用或删除：所有有效授权立即失效。
- 缓存刷新失败：写操作不得伪装成功；应回滚或使用可靠事件补偿，并提供 traceId。
- 自定义角色命名为“系统管理员”：仍按普通角色处理，不得获得管理员放权。

## 12. 测试与验收

### 12.1 需求追踪表

| 需求 | 前端入口 | 前端实现 | 后端接口/服务 | 数据或配置 | 测试 |
| --- | --- | --- | --- | --- | --- |
| 合并双权限体系 | 权限控制、所有受控页面 | 统一权限指令和有效权限缓存 | `AuthorizationService` | `permission`、`role_permission` | 新旧判定对比、接口授权测试 |
| 管理员作用域内无条件放权 | 角色设置、业务页面 | 管理员权限说明及作用域展示 | 管理员分支统一判定 | `admin_level`、`scope_type` | 系统/组织/项目正反向越权矩阵 |
| 六类默认角色不可删除 | 角色设置 | 隐藏或禁用删除、停用和改名 | 写接口强制保护 | `built_in`、`required` | UI、接口绕过、数据库约束测试 |
| 默认角色可编辑成员 | 角色成员页签 | 添加、移除、批量操作和状态反馈 | 成员增删接口 | `role_assignment` | 单个、批量、重复操作测试 |
| 管理员移除后回落成员 | 管理员成员页签 | 成功后刷新角色成员和权限状态 | 同事务移除及回落 | 唯一约束、审计记录 | 成功、已存在、失败回滚测试 |
| 原管理员原位升级 | 原角色设置 | 保留角色入口和成员 | 兼容原角色 ID | 数据迁移脚本 | 迁移前后成员及权限一致性测试 |
| 最后系统管理员保护 | 系统管理员成员页签 | 禁用或提示 | 服务端计数与事务锁保护 | 必要索引/锁策略 | 并发移除测试 |

### 12.2 权限矩阵测试

每类核心资源至少覆盖以下主体：

- 系统管理员。
- 同组织的组织管理员。
- 其他组织的组织管理员。
- 同项目的项目管理员。
- 其他项目的项目管理员。
- 拥有权限的普通成员。
- 不拥有权限的普通成员。
- 无任何角色的用户。
- 已禁用用户或失效角色关系。

每个主体至少验证 READ、CREATE、UPDATE、DELETE，以及需要的数据所有者限制。

### 12.3 必须执行的验证

实施完成后必须执行并记录：

- 数据迁移前向、回滚及幂等验证。
- 后端单元测试和权限集成测试。
- 前端权限工具单元测试。
- 前端类型检查、lint 和生产构建。
- 后端编译、打包及相关模块测试。
- Docker 镜像构建、容器启动和健康检查。
- 系统管理员、组织管理员、项目管理员和普通成员的核心 E2E 冒烟测试。
- 直接绕过前端调用接口的越权测试。
- 权限缓存刷新及多会话一致性测试。

## 13. 发布、监控与回滚

### 13.1 发布开关

建议提供短期迁移开关：

```text
permission.unified.write-enabled
permission.unified.shadow-read-enabled
permission.unified.enforce-enabled
permission.legacy.read-enabled
```

开关只用于灰度和回滚，不得长期形成新的双权限体系。

### 13.2 监控指标

- 新旧授权判定差异数量和比例。
- 403 数量及按权限编码、接口、作用域分布。
- 管理员成员变更成功率和回落失败率。
- 权限缓存失效延迟。
- 无角色用户、孤立角色关系和跨作用域异常关系数量。

### 13.3 回滚

- 切换期保留旧权限数据和旧读逻辑。
- 发生严重误拒绝或越权时，关闭统一强制判定，恢复旧读。
- 双写阶段的统一表变更保留，不立即反向覆盖旧表。
- 管理员成员迁移必须可根据审计记录恢复。
- 旧表仅在稳定观察期结束、备份验证通过后才能删除。

## 15. 完成标准

只有同时满足以下条件，统一权限改造才可标记为“完成”：

- 所有受控前端入口与后端接口使用统一权限编码。
- 后端不存在绕过统一授权服务的管理员特殊判断。
- 六类必备角色存在且不可删除，成员可正常维护。
- 原管理员角色 ID 和成员关系迁移正确。
- 管理员作用域放权和跨作用域拒绝均有自动化证据。
- 管理员移除后的成员回落、事务回滚和最后管理员保护通过测试。
- 旧 UI 独立授权关系退出实际授权链路。
- 数据库迁移、单元测试、集成测试、类型检查、lint、前后端构建全部通过。
- Docker 构建、启动、健康检查和核心 E2E 冒烟通过。
- 不存在未披露的 TODO、占位实现、Mock 授权或固定成功结果。

在上述条件全部满足前，项目状态只能标记为“部分完成”或“阻塞”。
