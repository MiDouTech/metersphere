# 质量门禁修复与完善方案

日期：2026-10-19。状态：评审后修订方案，工程改造尚未实施。

本次补充：明确发布版本内容来源、项目身份校验、受限解码、错误响应、复核事实保存、完成与回写状态、协议兼容、分批退出标准及制品验证。文中的新增字段、状态和协议均为目标设计，不代表当前接口已提供。

## 1. 目标和事实边界

首要目标是解除有效用例被误报缺少步骤的阻塞，再完成“完整证据放行、不完整证据拒绝、结果可追溯”的端到端验收。不能通过关闭准入、修改数据库压缩格式或开放旧直接回写接口规避问题。

已确认：用例内容采用 ZIP 压缩存储；可执行性检查使用 SQL CAST 而未解压；在本地真实 MySQL 的三个有步骤样本中复现转换为 NULL。远端 TC12 有两条步骤和预期、已发布，仍仅报 CASE_STEPS_OR_ASSERTION_MISSING。远端原始数据库字节及实际部署包尚未比对，需在上线修复前补充确认。

下文区分三类内容：已确认缺陷、代码审查发现的风险、建议新增能力。代码风险不等于线上已发生故障。

## 3. P0：修复内容读取误判

### 3.1 修改位置和方案

主要修改 AgentCaseExecutabilityService.listMissingItems；复用或提取统一的用例内容读取服务，避免另写一套与详情页不同的解码逻辑。

读取过程改为：

```text
解析并校验项目内用例身份
→ 取得待执行的已发布版本及内容来源
→ 若来源为数据库 BLOB，则按存储格式解压
→ UTF-8 严格解码
→ 解析 STEP/TEXT 内容
→ 校验操作和预期
→ 返回结构化检查结果
```

实施要求：

1. 删除 `CAST(b.steps AS CHAR)` 及同类压缩内容转换逻辑。正式预检、步骤生成和合同冻结统一消费预检选定的已发布版本内容；工作用例不再作为该次执行的内容来源。原始 BLOB 解码用于发布内容构建、诊断和明确标记的历史格式适配，不得在发布快照缺失或损坏时自动回退到当前工作副本。
2. 明确输入来源和是否已经解压，避免重复解压。现有 TestAssetCatalogService.decodeBlob 及 MyBatis 机制仅作为存储约定参考，不能直接作为严格校验实现；CompressUtils.unzip 会吞异常且未限制展开大小，decodeBlob 的普通 UTF-8 转换也不能识别全部非法编码。严格读取适配器应独立实现，不在热修中全局替换 MyBatis 压缩插件。
3. ZIP 识别为压缩格式后，如果损坏或无法解压，应报内容损坏，不得回退成普通文本。旧版非压缩数据只在合法 UTF-8 和结构校验通过后兼容。
4. 解压增加大小、条目数和资源限制；只处理约定条目，不把压缩包写到文件系统。限值应参考现有用例容量及实际样本制定。
5. 不改写现有 BLOB，不批量重建用例，不要求用户重新填写本来正确的内容。基础读取修复原则上不需要数据库迁移。
6. 校验结果不能只看字符串非空。`[]`、`null`、只有空 HTML 标签、只有描述没有预期，都不能因此判为可执行。

### 3.2 STEP 与 TEXT 的规则

|类型|应检查的内容|失败提示|
|---|---|---|
|STEP|数组非空；步骤标识/顺序有效；每步动作非空；需要断言的步骤有可验证预期|指出具体步骤及缺失字段|
|TEXT|确定性预检分别检查描述与预期的有效内容；结构化规划阶段再判断能否生成合法动作与断言|不能把两段 CONCAT 后非空当作完整；无法结构化时提示人工确认，不伪报内容缺失|
|辅助动作|若允许无业务断言，应在用例合同明确步骤类型及规则|不得由 Agent 在执行时临时声明豁免|

最低修复沿用现有业务规则，不在热修中增加不相关的准入门槛。富文本使用安全解析后的有效内容判断，不能仅靠去标签正则，也不能误删图片/附件等已有有效内容。没有持久步骤 ID 的合法历史用例，可在冻结时按稳定顺序生成执行步骤 ID，不要求作者重新编辑。辅助动作豁免本轮默认不开启；只有合同和策略均明确支持后才能启用。

“表述清晰”“截图关键状态可辨认”属于人工或模型复核，不能作为热修新增的主观硬门槛。内容结构检查、结构化规划和执行后复核必须分别记录阶段及失败原因。

### 3.3 修复错误分类

移除吞异常后统一设置 content=null 的处理。下面为建议的业务错误分类，最终名称接入项目现有错误码机制：

|建议分类|用户提示|处理人|
|---|---|---|
|CASE_CONTENT_MISSING|第 N 步缺少操作/预期，请补充并重新发布|用例作者|
|CASE_VERSION_NOT_PUBLISHED|用例尚未发布，请发布后重试|用例负责人|
|CASE_CONTENT_FORMAT_INVALID|用例内容格式无法解析，请检查版本内容|资产维护人员|
|CASE_CONTENT_DECODE_FAILED|用例内容读取失败，请联系管理员，附 traceId|平台维护人员|
|CASE_CONTENT_READ_FAILED|暂时无法读取用例，请重试或提供 traceId|平台维护人员|
|CASE_CONTENT_LIMIT_EXCEEDED|内容超过安全读取限制，请联系管理员核对容量，附 traceId|平台维护人员|
|ENVIRONMENT/CREDENTIAL 问题|明确环境或角色对应的缺失项|环境管理员|

日志保存异常、用例/版本/项目 ID、检查器版本和 traceId，避免记录凭据与整段敏感用例。前端展示安全描述，不显示 SQL、堆栈或压缩字节。

### 3.4 项目身份与受限读取边界

- `resolveCaseId` 改为接收服务端授权后的 projectId，在该项目内解析明确行 ID 或 refId；显式行 ID 不得被无条件替换成另一历史行，refId 的解析规则须固定并返回最终 caseRowId、stableAssetId。
- `listMissingItems`、单条 check、batchCheck、save/config 及其 MCP 调用均校验用例未删除，环境、配置和发布版本属于同一项目；先授权再查询内容、创建检查配置。对不存在或不可访问对象返回统一安全提示，不泄露其他项目资产信息。
- 工作副本用于解析身份和展示编辑状态，不参与本次发布版本的步骤内容判定。全局策略对所有项目一致，不意味着执行对象取消项目隔离。
- 读取适配器使用服务端确定的来源类型：RAW_BLOB、DECODED_BYTES、PUBLISHED_SNAPSHOT。客户端不能通过来源字段要求跳过解码、哈希或结构校验。RAW_BLOB 识别 ZIP 后不允许失败回退；DECODED_BYTES 只严格解码一次；PUBLISHED_SNAPSHOT 按其版本化结构读取。
- ZIP 按现有写入约定只接受一个名为 `zip` 的文件条目；拒绝重复、额外、目录条目、损坏流及 CRC 错误，必须读取到条目结束再接受。全程内存流处理，不落盘、不根据包内路径访问文件。
- 建议初始压缩输入和累计展开上限各为 8 MiB、文件条目数为 1，并使用受限流及明确的取消/超时机制。该数值是待容量核对的配置初值：实施前统计合法存量大小及发布接口容量，必要时统一调整，形成最终配置与边界测试；不能上线后才发现有效大用例被拒绝。超过限制返回安全的 `CASE_CONTENT_LIMIT_EXCEEDED`，不当作内容缺失。
- 解码使用 UTF-8 decoder 的 REPORT 行为；非法字节、截断序列须显式失败。检查读取器不会改变既有数据库压缩格式或原始字节。

### 3.5 前后端错误契约及批量行为

保留现有响应封装和 `missingItems: string[]`，增量增加结构化 `issues`；旧客户端仍可显示稳定错误码，新页面优先展示 issues。禁止把 JSON 对象字符串塞进 missingItems。

每个 issue 至少包含 `code、stage、caseId、caseVersionId、stepId/stepIndex、fieldPath、message、suggestion、retryable、traceId`；不适用的字段可为空。版本、checkerVersion 和 contentHash 放在检查结果层，不能仅写在日志中。返回的索引明确为一基展示序号，fieldPath 使用 JSON Pointer；技术日志另行记录内部定位，不回传原始 SQL/压缩数据。

|情况|HTTP 与结果语义|批量处理和页面行为|
|---|---|---|
|缺操作/预期、未发布|请求处理成功，结果 NOT_READY，issues 指向具体项|检查其余用例，保留成功和失败项；不允许整批任务创建|
|单个版本格式错误、解码损坏或超限|结果 NOT_READY，区分 FORMAT/DECODE/LIMIT，不归责为作者未填写|检查其他用例；该项展示联系资产维护人员及 traceId|
|认证、授权或对象范围不合法|沿用统一 401/403/安全的不存在或不可访问响应|中止请求，不能先创建其他项目的检查配置；401 正常失效，403 局部提示|
|数据库/依赖暂时故障|统一 5xx 安全错误，标注可重试及 traceId|中止并回滚本次批量检查写入；不能返回部分 READY 冒充整批完成，也不覆盖既有记录为内容缺失|
|预检过期、已消费或版本/协议不兼容|沿用现有冲突语义或统一映射到 409|提示重新预检；不自动替换版本后继续创建|

前端覆盖 loading、空结果、NOT_READY、系统错误、403、401、网络失败和重试；提交失败保留环境/用例选择，不把旧 READY 状态用于新的创建操作。更新 `AgentCaseExecutabilityDTO`、前端 ai-execution.ts 和 cases.vue，以及创建任务预检展示；旧错误码可兼容读取，新检查不再产生笼统的 CASE_STEPS_OR_ASSERTION_MISSING。

### 3.6 P0 验收

- 原 TC12 不修改内容，重新预检正确识别两条步骤；其他前置条件正常时可创建任务。
- 压缩 STEP、压缩 TEXT 及合法历史非压缩内容均能正确读取。
- 空数组、缺操作、缺预期、损坏 ZIP、非法 UTF-8、查询失败分别返回正确原因。
- 通过真实 MySQL 集成测试；禁止仅用 Mock 返回明文就宣称问题已修复。
- 现有版本内容不被改写，历史执行不被重算为通过。
- 跨项目 caseId/refId、环境错配、已删除用例、单条/批量/配置保存全部拒绝越权，不新建无权配置。
- 已解压内容不重复解压；多条目/重复条目 ZIP、CRC 错误、展开超限和非法 UTF-8 都有边界用例。
- 一条内容损坏时可返回逐项结果；数据库故障时整批写入回滚、页面不误用旧 READY；新旧客户端错误展示均验证。

## 4. P0：保证完整受管链路正确

### 4.1 统一执行依据

当前 `AgentExecutionService` 在 prepareSnapshot 后调用 assertFrozenCaseVersion 比对工作用例快照与预检保存的发布 hash。只修改 listMissingItems 的读取源仍可能导致“预检成功、任务创建失败”。本次须同时调整 `AgentExecutionSnapshotService` 和任务创建链路，使步骤直接从预检冻结的发布内容生成。

预检保存 `projectId、caseRowId、stableAssetId、caseVersionId、contentHash、contentSchemaVersion、checkerVersion`，以及环境、凭据引用、执行资产等依赖快照。沿用已发布版本现有哈希算法和被哈希内容边界，不直接重算覆盖旧 hash；新规范化方案必须另加版本标识。

|变化|明确行为|
|---|---|
|预检后只编辑草稿|仍按冻结发布版本创建；草稿不影响内容或步骤|
|预检后发布新版本|未过期的旧预检仍使用原版本；用户选择新版本必须重新预检，不重新查询 latestPublished 替换|
|用例删除、项目访问撤销、环境/凭据停用或过期|创建/认领时重新校验实时安全条件并拒绝，不因有快照而绕过撤权|
|预检过期、已消费或并发重复创建|沿用原子消费约束；最多产生一个任务，其余返回冲突|
|旧预检缺少必要版本/检查器字段|使其失效并要求重新预检，不从当前工作副本补齐|
|发布快照损坏、哈希不符或解析版本不支持|明确拒绝并关联 traceId，不能回退工作副本|

checkerVersion 在本轮升级，允许在已有 JSON 快照中增量存储；若需新增数据库字段，再提供扩展迁移。系统不能为了“读取通过”把原已发布的非法结构自动修成不同执行内容。历史执行仅回看原快照，不重算为通过。

全局门禁策略仍在执行尝试认领时绑定，独立于预检的用例内容快照；本次不将两种绑定时点混为一谈。无有效全局策略不能认领成功；发布与认领并发时，每次尝试绑定一个完整、可追溯的版本。

### 4.2 区分三个阶段

|阶段|关注的问题|界面和报告应显示|
|---|---|---|
|准入预检|能否创建任务|通过/阻塞，版本、缺失项和处理建议|
|步骤结果接收|证据和事实是否符合提交要求|接受/拒绝，对应步骤、规则和证据|
|任务完成及回写|是否满足结束条件，正式结果是否同步|执行结果、门禁结论、计划同步结果分别显示|

业务结果与证据质量分开：业务失败可以是一条真实、证据完整的失败记录；证据不足不能被写为通过；预检失败不能算证据门禁命中。

正式界面不允许通过标记 SUCCESS 绕过提交步骤；服务端对网页、MCP、Runner 等入口统一执行这些约束。未纳入认领、冻结合同和证据提交链路的外部执行，仅作为明确标记的观察资料，不能混入正式通过率；已完整接入受管协议的外部执行器适用与 Runner 相同的判定。

### 4.3 事实接收、门禁结论及同步状态

下表为目标状态模型，实施时映射到现有枚举并提供新增字段的迁移，不能直接假定现有数据库已经支持这些状态。执行结果、质量结论、同步状态必须分字段保存与展示。

|输入/事件|服务端处理|业务结果 / 质量结论 / 正式同步|
|---|---|---|
|证据完整、冻结断言满足，申请成功|接受规范化步骤事实|SUCCESS / PASS / 待完成汇总|
|证据完整、冻结断言不满足，报告业务失败|接受实际值，服务端比较并记录业务断言失败|FAILED / 事实符合质量要求 / 可按失败结果汇总；不能显示测试通过|
|实际不满足但声称 SUCCESS|拒绝该成功申请，记录拒绝审计|无新增成功事实；执行器以新的请求标识提交真实失败事实|
|缺步骤/断言、证据未 commit、伪造范围或错误类型|拒绝结果提交或完成，显示对应规则|质量拒绝 / 不产生本次正式通过；保留诊断记录|
|浏览器崩溃、截图不可取得|接受最小失败诊断，记录明确原因和可用证据|FAILED 或 BLOCKED / INCOMPLETE / 只可同步相应非成功结果|
|完成校验通过，计划同步暂时失败|冻结最终事实并重试同步|业务结果不变 / 门禁结论不变 / PENDING 或 RETRYING；不能显示“已同步”|
|计划同步成功|回读目标并核对版本/结果|同步 SUCCESS；仅业务 SUCCESS 且门禁 PASS 才计入正式通过率|

需要把事实结构/证据校验与业务断言真假判定分开，不能为了接受真实业务失败直接跳过证据和身份校验。FAILED/BLOCKED 必须校验最小诊断结构及合法原因；缺截图豁免仅用于如实记录非成功结果。Runner 的 catch 分支须提交失败事实，而不只是写事件；网页和 MCP 适用同样规则。

### 4.4 完成与回写一致性及恢复

现有 `AgentExecutionCaseWritebackService.writeback` 使用 REQUIRES_NEW，不能承诺整项任务与所有计划结果天然同事务。采用“先冻结和判定最终事实，再按用例持久化同步、最终汇总状态”的恢复模型：

1. 完成操作先在事务内校验有效租约、当前 attempt、步骤结果和证据，锁定/乐观更新该尝试的版本，冻结最终评估及同步意图。未通过完成校验时不得创建新的正式成功同步意图。
2. 同步工作读取已冻结事实，不重新选择可变的最新步骤结果。目标用例/计划结果更新、该用例幂等记录和同步状态必须在同一事务中完成；跨服务时使用持久化 outbox 与幂等消费者，不能仅靠内存队列。
3. 唯一同步键包含 taskId、executionId、目标用例/计划关系及最终事实版本。并发完成、重复消息、响应丢失只产生一次有效副作用；失败重试原同步项，不生成另一份互相冲突的事实。
4. 新 attempt 启动、旧回调和同步消费者使用当前尝试版本校验/隔离栅栏，禁止旧尝试覆盖新尝试结果。租约过期后拒绝新事实；已成功接收的原请求仅允许通过受授权的只读结果查询确认，不能因此重新开放旧租约写权限。
5. 所有必要同步项成功后才显示任务“正式结果已同步”。进程在部分用例提交后崩溃，重启扫描持久化未完成项恢复；已提交项不重复写，历史结果不靠手工回滚业务数据恢复。

审计所有结束、重试、恢复、人工接管、审批及回写入口。补充故障注入：最终评估后崩溃、第一条计划结果更新后崩溃、目标服务超时、响应丢失、重复 complete、同步期间启动重试、旧 attempt 延迟回调。人工审批不能替代缺失的步骤事实和证据，也不能覆盖原评估记录。

### 4.5 复核事实保存完整性（提升到 P0 第二批）

当前成功校验后会对 assertionResult 脱敏并截断保存，完成时又读取该字段复核。此项先于完整正向验收修复，不能留到展示增强批次。

- 为请求字节数、断言数量、嵌套深度、单值长度和规范化结果 UTF-8 字节数设置与接口网关、应用和数据库一致的上限；超过上限在任何步骤成功状态更新前明确拒绝，禁止截断 JSON 后保存。
- 解析一次、规范化一次，校验与复核使用同一份不可变规范化事实并保存 hash；不能先校验原文、保存另一份脱敏文本，再把两者当作相同事实。
- 展示摘要与复核事实分开。复核事实只保存合同所需最小值；敏感值需要受限访问和适当加密存储，禁止写入普通日志。若某敏感字段不允许保存，合同阶段明确拒绝该类断言或采用经评审的专用比较机制，不能靠不可逆脱敏后继续比较。
- 新请求失败不覆盖旧有效结果；历史结果若已截断、无法解析或无法验证，标记不可复核并要求新尝试，不补造通过。
- 测试覆盖临界长度、多字节字符、超深 JSON、脱敏关键字、持久化往返一致性，以及步骤接受后最终复核结果一致。

## 5. P1：增强证据与断言可信度

### 5.1 证据完整并不代表业务真实

已有文件哈希、类型和归属控制应保留。进一步验证图片实际可解码、前后角色正确、步骤绑定正确；关键状态是否可辨认通过明确标记的人工/模型复核判断，并记录服务端接收时间和客户端采集时间。跨执行复用、重复截图可作为异常信号，不能把相同哈希一律判失败：无页面变化的合法步骤也可能有相同图片。

客户端实际值仍由执行器提交。即使服务端重新比较 actual 与冻结 expected，也不能单独证明 actual 来自真实页面。建议将 actual 关联到 evidenceId、页面 URL、定位信息和采集时间；逐步增加可信 Runner 或抽样复核。截图存在不得被宣传为绝对防伪。

### 5.2 断言身份、类型与协议版本

新合同/结果协议定义为 v2；在合同生成并冻结时为每条断言生成稳定 assertionId，绑定 contractHash 与 stepId。同一冻结合同的重试保留 ID，新合同重新生成；不得由执行器临时发明 ID。发布源内容已有断言 ID 时保留来源关联，未结构化的历史用例不要求重新编辑。

v2 结果按 assertionId 严格匹配，拒绝重复、缺失、未知 ID 和错误 stepId；数组换序不影响匹配。冻结 operator、expected、dataType、比较规则、时区和误差，执行器仅上报 actual 及采集引用，不能覆盖预期或运算符。

金额使用带 `dataType=DECIMAL` 的十进制字符串作为传输格式，服务端按严格十进制语法解析 BigDecimal；这属于显式类型协议，不是字符串与数值隐式混用。冻结精度、scale、单位/币种、上下界包含性和容差；拒绝 NaN、Infinity 及超出声明精度的值。Runner 不得先用 JavaScript Number 转换金额再发送。字符串、布尔、整数和日期各有独立类型及规范化规则；EQUALS 是否忽略小数末尾零由类型规则确定，不靠浮点近似。

|迁移对象|兼容策略|
|---|---|
|历史已结束的 v1 合同|保留原位置关联和原评估，不能重新解释为 v2 通过|
|升级时仍在途的 v1 尝试|由兼容 v1 的消费者完成，或在切换前明确终止后新建尝试；禁止中途按 v2 解析|
|新 v2 合同|只派发到声明 v2 能力的 Runner/执行器；无兼容消费者时明确阻塞，不降级为位置匹配|
|旧客户端结果提交|仅能提交匹配其冻结 v1 合同的结果；不能向 v2 尝试提交省略 ID 的位置数组|
|服务混合部署|先部署双协议读取/校验，再升级消费者，最后开放 v2 创建；回滚到支持已产生协议的兼容制品|

修改范围必须包括合同 schema、DTO、规划校验、GlobalQualityGate、Runner types/client/executor、MCP/网页提交与结果展示，不能只改服务端比较循环。测试覆盖换序、重复/未知 ID、伪造 expected/operator、金额边界和旧合同回看。

### 5.3 提交幂等与并发（基础保护提升到 P0 第二批）

当前方法按 requestId 查重后直接返回旧结果，未比较载荷；需在复核事实保存修复时一并加入基础幂等保护，v2 增强再扩展类型规范化。

- 唯一键采用 executionId、stepId、requestId；核查和复用已有唯一约束，缺少时再迁移，不重复建索引。同键同摘要返回原结果，同键不同摘要返回 409 冲突；并发插入冲突后回读并比较，不返回数据库异常。
- payloadHash 包含服务端验证过的任务/尝试/步骤身份、合同与策略 hash、协议版本、声明状态、规范化断言、证据 ID 集合、输入/输出事实及业务错误原因。排除 leaseToken、traceId、传输重试次数及服务端接收时间等传输元数据；客户端采集时间若用于判断则属于事实，必须保持不变。
- v1 断言保留数组顺序；v2 按 assertionId 规范化。证据集合可按 ID 排序、去重，不能借重排或更换证据绕过摘要冲突。摘要算法及规范化版本要持久化。
- Runner 在创建一次逻辑结果时生成 requestId，并持久保存其待发送内容；网络重试复用相同 ID 和内容。当前每次 stepResult 调用 randomUUID 的行为需同步调整。改变事实或从被拒绝的成功申请改为失败报告，应使用新 requestId。
- 有效租约与授权在查重前校验；完成/过期后的确认使用受授权只读查询，不用幂等重放绕过租约。并发“提交/完成/新尝试”要通过尝试锁或乐观版本保证事实集合冻结后不再变化。
- 迁移前核查历史重复键；已有记录只有在规范化事实完整可信时才能回填摘要，否则显式标记历史摘要不可用并返回可理解冲突，不静默接受不同载荷。

## 6. P1：让用户看得见门禁为什么生效

### 6.1 门禁结果面板

在现有任务详情中增加或补全门禁页签，展示阶段、规则 ID、策略版本、触发时间、用例/步骤、预期要求、实际缺失、处理建议和 traceId。提供到用例版本、步骤事实、证据预览、计划结果的跳转。

用例详情的普通附件标为“资料附件”；受管步骤证据标明 task/execution/step 关联。清楚区分“上传成功”“步骤已接受”“门禁通过”“正式结果已同步”。

复用现有审计设施，不能满足查询需要时新增独立门禁评估记录；至少含 evaluationId、project/task/execution/step、阶段、策略/合同哈希、触发请求及摘要、规则结论、原因、traceId、时间。基础拒绝审计在第二批完成，第三批只扩展可查询面板。拒绝记录不能因主业务事务回滚而完全丢失；按项目现有审计基础设施实现独立审计，并对令牌及敏感值脱敏。

### 6.2 权限一致性

保留 SYSTEM_QUALITY_READ/MANAGE/PUBLISH 和 Agent Token 不可修改全局策略的约束。补测系统管理员、读取人员、维护人员、发布人员、普通成员及 Token 的权限矩阵；前端菜单、按钮、路由与后端 API 使用同一权限语义。

执行人员应可查看其项目任务绑定的策略快照和失败原因，不必因此获得全局编辑权限。权限不足提示缺少哪类能力及联系谁，不展示空白页面。

## 7. P2：策略治理和持续验证

- 发布前进行 schema 校验和影响预览，明确全局作用域、受影响规则及对新执行的影响。
- 策略更新只作用于后续绑定；历史执行保留原快照。恢复旧规则应生成新的发布版本，不能直接改写历史快照。
- 提供基于历史事实的离线试算，但注明试算不改正式结果、不能替代真实执行验收。
- 统计按阶段分布的拒绝率、规则命中、读取错误、证据上传失败及结果同步延迟。准入拒绝和证据拒绝不可合并成一个“拦截成功率”。
- 建立正向完整证据、缺截图、缺步骤、缺断言、错误断言、跨执行证据、旧入口绕过等稳定回归集，发布前运行。

每项保存测试环境、服务/Runner 制品版本、caseVersionId、preflightId、taskId、executionId、策略/合同 hash、traceId 和证据位置。负向测试除指定因素外保持其他条件满足，避免被更早的失败挡住而误判规则已验证。
