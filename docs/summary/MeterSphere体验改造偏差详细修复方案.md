## 2. 修复目标

本次修复不再以“新增公共组件”作为完成标准，而以完整业务闭环作为验收依据。每项能力必须同时满足：

1. 后端有明确、稳定的接口契约。
2. 前端能够完整消费接口字段。
3. 至少一个真实业务页面完成接入。
4. 正常、失败、重试、权限和边界状态均可验证。
5. 自动化测试能够阻止相同问题回归。

## 3. 偏差概览

| D06 | 执行结果没有草稿和自动保存闭环 | 前后端均不完整 | P1 |
| D07 | 异步任务缺少统一协议和公共入口 | 前后端能力分散 | P1 |

## 4. 总体技术路线

```text
后端异常/任务/批量结果
        ↓ 统一 DTO
HTTP 响应与请求编号
        ↓
前端 AppError / AsyncTask / BatchResult 模型
        ↓
公共 Hook 与公共组件
        ↓
真实业务页面接入
        ↓
单元测试 + 组件测试 + E2E + 静态检查
```

实施原则：

- 接口契约先行，组件不得根据 HTTP 状态或历史字段猜测业务语义。
- 公共能力必须与首批业务页面在同一迭代交付。
- 新旧协议允许短期兼容，但必须设定删除旧兼容逻辑的版本。
- 每项能力均提供中文和英文文案。
- 不在本轮引入新的 UI 框架。

## 5. D01：统一错误协议

### 5.1 当前偏差

前端定义了 `retryable`、`fieldErrors` 和 `requestId`，但后端 `ResultHolder` 没有稳定字段；当前通过 `messageDetail` 和 HTTP 状态推断，契约不明确。

### 5.2 目标协议

新增统一错误响应对象：

```java
public record ApiErrorResponse(
        int code,
        String messageKey,
        String message,
        String requestId,
        boolean retryable,
        Map<String, String> fieldErrors,
        Map<String, Object> context
) {}
```

推荐响应：

```json
{
  "code": 500001,
  "messageKey": "api.internalError",
  "message": "Internal server error",
  "requestId": "65e6dbe2-19b0-4e4c-b4c0-e092788f928f",
  "retryable": true,
  "fieldErrors": {},
  "context": {}
}
```

字段定义：

| 字段 | 说明 |
| --- | --- |
| `code` | 稳定业务错误码，不等同于 HTTP 状态码 |
| `messageKey` | 前端国际化 Key；前端不存在该 Key 时使用 `message` |
| `message` | 安全的后端兜底文案，不包含技术细节 |
| `requestId` | 服务端日志追踪编号，同时写入 `X-Request-ID` |
| `retryable` | 是否允许用户原地重试 |
| `fieldErrors` | 字段名到错误 Key 或安全文案的映射 |
| `context` | 经过白名单控制的业务上下文，不允许放异常对象 |

### 5.3 后端任务

1. 在公共 SDK 或公共 Web 模块定义 `ApiErrorResponse`。
2. 调整 `RestControllerExceptionHandler` 返回统一对象。
3. 为所有异常响应生成或透传 `X-Request-ID`。
4. 对 `MSException` 建立错误码到 `messageKey`、HTTP 状态和 `retryable` 的映射。
5. 未识别异常统一返回 `api.internalError`。
6. 禁止将 `Throwable#getMessage()` 放入用户响应。
7. 保留完整异常日志，并记录请求方法、路径、用户、组织和项目上下文。
8. 为旧接口保留一个版本周期的兼容序列化。

### 5.4 前端任务

1. 将 `AppErrorDetails` 改为与 `ApiErrorResponse` 一一对应。
2. 优先使用 `messageKey` 翻译文案。
3. 删除根据 HTTP 5xx 推断 `retryable` 的长期逻辑；兼容期结束后完全移除。
4. 统一抛出 `AppError` 实例，禁止继续拒绝字符串。
5. 保留敏感信息二次过滤，作为防御性措施。
6. `isReturnNativeResponse` 模式也必须保留结构化错误信息。

### 5.5 验收标准

- 任意 4xx/5xx 错误都具有稳定 `code` 和 `requestId`。
- 前端不再从 `messageDetail` 猜测字段错误。
- 任意未知异常不会向用户返回 SQL、堆栈和类名。
- 请求编号能够在服务端日志中准确检索。

## 6. D02：字段错误映射闭环

### 6.1 当前偏差

后端已经返回字段校验 Map，前端也能解析，但没有统一机制把错误绑定到 Arco 表单项。

### 6.2 目标方案

新增 `useServerFieldErrors`：

```ts
interface UseServerFieldErrorsOptions {
  fieldMap?: Record<string, string>;
  focusFirstError?: boolean;
}

interface ServerFieldErrorResult {
  fieldErrors: Ref<Record<string, string>>;
  applyError(error: AppError): boolean;
  clearField(field: string): void;
  clearAll(): void;
}
```

工作流程：

1. 表单提交。
2. 后端返回 `fieldErrors`。
3. `applyError` 将后端字段映射到前端字段。
4. 对应 `a-form-item` 展示错误。
5. 自动聚焦第一个错误字段。
6. 用户修改字段后只清除该字段错误。

### 6.3 首批接入页面

- 创建项目。
- 编辑项目。
- 创建用户。
- 创建测试计划。
- 新建和编辑缺陷。

### 6.4 验收标准

- 字段错误显示在字段旁，不再只显示 Toast。
- 第一个错误字段可自动聚焦。
- 后端字段名和前端模型名不一致时可配置映射。
- 同一错误不会同时显示字段错误和重复全局 Toast。

## 7. D03、D04：错误组件真实接入与反馈去重

### 7.1 改造 `MsErrorNotice`

组件改为直接接收 `AppError`：

```ts
defineProps<{
  error: AppError;
  title?: string;
}>();
```

组件内部统一处理：

- 安全文案。
- 错误编号。
- 请求编号。
- 是否显示重试。
- 复制诊断信息。

禁止页面分别传递 `message`、`requestId` 和 `errorCode`，避免遗漏。

### 7.2 反馈责任规则

| 场景 | `errorMessageMode` | 反馈责任 |
| --- | --- | --- |
| 页面或局部加载失败 | `none` | `MsErrorNotice` |
| 表单字段校验 | `none` | 表单字段错误 |
| 用户触发的短暂动作失败 | `message` | 全局 Message |
| 重要且阻塞的动作失败 | `modal` | 错误弹窗 |
| 后台任务失败 | `none` | 任务状态组件和任务中心 |

### 7.3 首批改造页面

- 测试计划用例列表和详情。
- 项目列表及创建项目。
- 用户和用户组管理。
- 任务中心。
- 接口执行结果。

### 7.4 验收标准

- 同一请求只出现一个主要错误反馈。
- 页面错误能够复制真实请求编号。
- 重试按钮恢复原请求参数和页面上下文。
- 重试成功后自动清除错误状态。

## 8. D05：认证与授权异常脱敏

### 8.1 后端改造

- `ShiroException` 统一返回 `auth.sessionInvalid`。
- `UnauthorizedException` 统一返回 `auth.forbidden`。
- 不再返回 `exception.getMessage()`。
- 401 仅清理会话并引导登录；403 保留当前路径用于授权后返回。
- 服务端日志记录异常详情，但普通认证失败不记录完整堆栈，避免日志噪声。

### 8.2 前端改造

- 401 并发请求只触发一次退出和一次提示。
- 403 页面展示缺失权限和返回入口。
- 登录页认证失败保留业务文案，不展示内部认证实现。

### 8.3 验收标准

- 401、403 响应不含 Shiro 类名或异常内容。
- 多个并发 401 不会重复弹窗或重复跳转。

## 9. D06：执行结果保存闭环

### 9.1 当前偏差

用例详情具备部分自动保存能力，但执行结果仍由 `runFeatureCase` 或 `batchExecuteCase` 一次性提交，没有草稿和恢复机制。

### 9.2 后端接口

新增执行草稿模型：

```text
test_plan_case_execution_draft
├── id
├── test_plan_case_id
├── user_id
├── payload
├── version
├── update_time
└── expire_time
```

接口建议：

```text
GET    /test-plan/case/{id}/execution-draft
PUT    /test-plan/case/{id}/execution-draft
DELETE /test-plan/case/{id}/execution-draft
POST   /test-plan/case/{id}/execution-submit
```

保存请求包含 `version`，服务端使用乐观锁防止覆盖。正式提交成功后删除草稿。

### 9.3 前端实现

1. `ExecuteSubmit` 接入 `useSaveState`。
2. 实际结果、步骤状态、备注和附件变化后触发防抖保存。
3. 持续展示“有未保存修改、保存中、已保存、保存失败”。
4. 保存失败保留本地内容并提供重试。
5. 自动下一条必须等待草稿保存和正式提交成功。
6. 切换用例前检查保存状态。
7. 再次进入时提示恢复草稿。
8. 发生版本冲突时允许重新加载或另存当前内容。

### 9.4 数据安全

- 草稿按项目、计划用例和用户隔离。
- 附件使用临时引用，提交后转为正式关联。
- 草稿设置过期清理任务。
- 删除计划用例时同步清理草稿。

### 9.5 验收标准

- 输入执行结果后刷新浏览器可以恢复。
- 保存失败不会丢失内容。
- “通过并下一条”不会在保存失败时跳转。
- 两个窗口修改同一执行记录时出现冲突提示。

## 10. D07：统一异步任务闭环

### 10.1 统一任务模型

```ts
type AsyncTaskStatus =
  | 'QUEUED'
  | 'RUNNING'
  | 'SUCCESS'
  | 'PARTIAL_SUCCESS'
  | 'FAILED'
  | 'CANCELED';

interface AsyncTaskSummary {
  id: string;
  type: string;
  status: AsyncTaskStatus;
  progress: number;
  totalCount: number;
  successCount: number;
  failedCount: number;
  skippedCount: number;
  retryable: boolean;
  createTime: number;
  finishTime?: number;
}
```

### 10.2 后端改造

- 为导入、导出、执行、解析和报告生成提供统一任务摘要接口。
- 现有任务中心数据转换为统一状态，不要求立即重构底层执行引擎。
- 提供任务详情、取消、重试失败项和下载失败明细接口。
- 明确任务状态转换规则，禁止使用不同模块自定义同义状态。

接口建议：

```text
GET  /task-center/tasks/{id}
POST /task-center/tasks/{id}/cancel
POST /task-center/tasks/{id}/retry-failed
GET  /task-center/tasks/{id}/failures
```

### 10.3 前端改造

- 新增 `useAsyncTask`，负责轮询、停止条件和错误恢复。
- 新增 `MsAsyncTaskStatus`，展示进度、状态和入口。
- 发起任务后当前页面立即展示任务摘要。
- 离开当前页面后可在任务中心继续查看。
- 完成后显示成功、失败和跳过数量。

### 10.4 首批接入

- 功能用例导入和导出。
- 接口和场景批量执行。
- 文档解析。
- 测试报告生成。

### 10.5 验收标准

- 页面和任务中心展示相同状态。
- 部分成功不会显示为完全成功。
- 失败项可以查看和单独重试。

## 11. D08：统一批量结果

### 11.1 后端响应

```java
public record BatchOperationResult<T>(
        int totalCount,
        int successCount,
        int failedCount,
        int skippedCount,
        List<BatchFailure<T>> failures
) {}
```

```java
public record BatchFailure<T>(
        T target,
        String code,
        String messageKey,
        String message,
        boolean retryable
) {}
```

批量停止、删除、移动、导入和关联接口不得继续返回 `void`。

### 11.2 前端组件

新增 `MsBatchResult`：

- 展示总数、成功、失败、跳过。
- 展示失败对象及原因。
- 支持复制或下载失败明细。
- 支持仅重试可重试项目。

### 11.3 首批改造接口

- 任务中心批量停止。
- 任务中心批量删除。
- 用户批量导入。
- 用例批量移动和删除。
- 缺陷批量修改。

### 11.4 验收标准

- 部分成功时结果统计准确。
- 前端不再只显示“操作成功”。
- 重试只包含失败且可重试的对象。

## 12. D09：危险操作影响评估

### 12.1 两阶段操作

危险操作拆分为：

1. 影响评估。
2. 用户确认后正式执行。

接口示例：

```text
POST /test-plan/{id}/delete-impact
DELETE /test-plan/{id}
```

影响响应：

```json
{
  "targetName": "8 月版本回归",
  "affectedCount": 126,
  "runningTaskCount": 2,
  "recoverable": false,
  "warnings": ["删除后将停止正在执行的任务"]
}
```

### 12.2 前端组件

新增 `MsDangerConfirm`：

- 对象名称。
- 影响数量。
- 正在运行的任务数量。
- 是否可恢复。
- 明确确认按钮文案，例如“删除计划”。
- 高风险场景要求输入对象名称。

### 12.3 首批接入

- 删除测试计划。
- 删除项目。
- 删除用户。
- 停止执行任务。
- 批量删除用例。

## 13. D10、D11：存量页面迁移与工程约束

### 13.1 当前存量基线

- 可点击 `div/span`：约 101 处。
- 含中文文本的 Vue 文件：约 478 个。
- 固定像素宽度：约 939 处。
- `console.log(error)`：约 670 处。
- `MsErrorNotice`：只接入 1 个页面。
- `useAutoSaveEditor`：只接入 3 类页面。

### 13.2 检查脚本升级

将 `verify-ui-consistency.mjs` 扩展为四类检查：

1. 非语义化可点击元素。
2. 新增中文硬编码。
3. 新增固定宽度和页面级最小宽度。
4. 图标按钮缺少可访问名称。

改进要求：

- 按“具体出现位置”计数，不按文件计数。
- 将存量问题保存为基线清单，而非只保存一个数字。
- 新增问题直接阻断 CI。
- 修复后的基线只能减少，不能回升。
- 对确有必要的固定宽度使用带原因和到期时间的白名单。

### 13.3 页面迁移顺序

第一批 P0：

- 创建项目和项目成员选择。
- 用户、用户组和组织管理。
- 测试计划用例执行。
- 测试计划详情。
- 任务中心。

第二批 P1：

- 测试计划列表。
- 测试用例列表。
- 接口测试执行和结果。
- 缺陷列表和缺陷详情。
- 用例评审。
- 导入、导出和报告生成。

### 13.4 单页迁移完成定义

每个页面必须同时满足：

- 搜索、筛选、重置和分页符合统一规范。
- 没有页面级横向滚动。
- 操作层级明确。
- 错误、空数据、加载和无权限状态完整。
- 新增文案全部国际化。
- 键盘可以完成主要操作。
- 通过对应 E2E 和视觉回归测试。

## 14. D12：恢复后端测试链路

### 14.1 当前阻塞

`system-setting` 测试编译被 `PermissionControlServiceTests` 引用缺失的 `PermissionControlMapper` 阻断，导致新增异常脱敏测试无法执行。

### 14.2 修复步骤

1. 确认 Mapper 重命名、移动或删除历史。
2. 修正测试导入与 Mock 类型，或恢复对应 Mapper。
3. 确保 `testCompile` 可以独立通过。
4. 执行 `RestControllerExceptionHandlerTests`。
5. 将异常脱敏测试加入 CI 必跑集合。

### 14.3 补充测试

- 未知异常不返回原始消息。
- SQL 异常不返回 SQL 内容。
- 业务异常返回正确 `messageKey`。
- 字段校验返回 `fieldErrors`。
- 401 和 403 不返回 Shiro 异常。
- 响应头和响应体的 `requestId` 一致。

5. 首批批量接口返回逐项结果。

7. P0 页面全部完成一致性迁移。
8. 前后端自动化测试与视觉回归全部通过。
