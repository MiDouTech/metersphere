# MSP 业务里程碑规划

> 文档版本：V1.0
> 规划基准日期：2026-08-26
> 适用范围：测试资产云平台（MSP）
> 规划原则：以解决业务问题和产生可验证的业务结果为里程碑，不以单个技术模块或代码提交作为完成标准。

## 1. 建设愿景

建设测试资产云平台 MSP，将分散的测试资产统一沉淀，把测试任务、执行结果和缺陷处理形成闭环，并通过 Agent 辅助个人测试和 AI 定时巡检，降低重复劳动、扩大测试覆盖、提前发现质量风险，同时保留完整、可信、可追溯的质量证据。

整体演进路径：

```text
测试资产统一
→ 测试任务与缺陷闭环
→ Agent 辅助个人任务执行
→ AI 定时巡检与主动质量预警
```

## 3. M1：测试资产统一沉淀、复用与追溯

### 3.1 要解决的问题

- 用例、产品文档、测试方案和执行证据分散在不同系统、项目或个人文件中。
- 相同业务场景被重复编写，已有资产难以搜索和复用。
- 文档发生变化后，无法识别受影响的测试用例、测试计划和执行任务。
- 用例执行后，无法反向追溯需求来源、历史版本、执行结果和关联缺陷。
- 不同组织和项目之间存在资产归属不清或越权访问风险。

### 3.2 目标业务闭环

```text
产品文档
→ 测试场景
→ 测试用例
→ 资产版本
→ 项目引用
→ 测试计划
→ 执行结果
→ 缺陷与证据
```

### 3.3 核心交付

- 建立统一的测试资产目录和项目空间。
- 统一管理产品文档、测试方案、测试用例、附件和资产版本。
- 支持资产搜索、分类、标签、引用和复用。
- 建立文档、用例、测试计划、执行结果和缺陷之间的关联关系。
- 支持从文档追溯用例，也支持从用例反查需求来源。
- 支持资产变更历史和版本对比。
- 实现组织、项目和角色级的数据隔离与权限控制。
- 完成存量资产迁移，并提供迁移数量及关系核对结果。

### 3.4 验收指标

- 存量测试资产归档覆盖率达到 100%。
- 用例与文档、计划、执行结果和缺陷的关联准确率达到 100%。
- 用户可在 30 秒内通过目录、名称或标签找到目标资产。
- 测试计划可以引用已有资产，且不会产生不可控的重复副本。
- 迁移前后资产数量、归属、版本和关联关系一致。
- 无权限访问、引用或修改其他项目资产的事件为 0。

## 4. M2：测试任务、执行、缺陷和改进闭环

### 4.1 要解决的问题

- 测试任务依赖会议、聊天或口头分配，缺少正式责任人。
- 执行状态需要人工询问和汇总，阻塞问题不能及时暴露。
- 执行结果、截图、附件和缺陷彼此割裂。
- 缺陷缺少统一入口、标准流程和责任追踪。
- 缺陷关闭后没有分析测试用例为什么未能提前发现问题。
- 相同问题重复发生，却没有转化为新的回归测试资产。

### 4.2 目标业务闭环

```text
测试计划
→ 任务分配
→ 用例执行
→ 结果与证据
→ 缺陷创建或关联
→ 缺陷处理
→ 修复验证
→ 用例补充或优化
→ 回归资产沉淀
```

### 4.3 核心交付

- 将测试计划拆分为具有执行人、时间、优先级和状态的个人任务。
- 实时展示整体进度、人员进度、失败情况和阻塞情况。
- 统一记录执行结果、说明、截图、附件和环境信息。
- 建立缺陷集中管理入口和标准化状态流转机制。
- 支持从失败结果创建缺陷，或关联已有缺陷。
- 支持一个缺陷关联多个用例、一个用例关联多个缺陷。
- 支持缺陷修复后的复验及复验结果追踪。
- 建立缺陷遗漏分析机制，判断是未执行、断言不足、场景遗漏还是优先级不合理。
- 对需要补充或优化的用例建立明确任务，并回收到测试资产库。

### 4.4 验收指标

- 测试任务责任人明确率达到 100%。
- 测试计划执行状态能够实时查看，不依赖人工统计。
- 失败用例的有效证据完整率达到 100%。
- 测试发现的缺陷与执行用例关联率达到 100%。
- 生产、验收或巡检阶段发现的缺陷均完成测试遗漏分析。
- 需要补充回归用例的缺陷，用例补充完成率达到 100%。
- 非法状态流转和无权限操作拦截率达到 100%。
- 缺陷修复后的复验结果可以完整追溯。

## 5. M3：Agent 辅助个人测试任务执行

### 5.1 要解决的问题

- 测试周期短、人员有限，无法完整执行所有重要测试场景。
- 大量时间消耗在重复点击、测试数据准备、截图和结果回填等机械操作上。
- 测试覆盖范围受人员数量和执行时间限制。
- 不同人员的执行习惯不同，结果和证据质量不一致。
- 传统自动化脚本建设和维护成本较高，难以及时覆盖变化频繁的业务。

### 5.2 业务定位

M3 采用“人发起、Agent 执行、人处理异常”的协作模式。测试人员仍然是任务责任人，Agent 是个人测试执行助手，不是脱离用户授权和平台管理的自主执行程序。

### 5.3 目标业务闭环

```text
MSP 分配个人任务
→ Agent 通过 MCP 查询待办
→ 用户确认执行范围
→ Agent 读取用例和环境信息
→ AI 辅助执行
→ 自动判断与留证
→ 结果回写 MSP
→ 异常转人工
→ 创建或关联缺陷
```

### 5.4 核心交付

- MSP 通过 MCP 提供标准化任务查询和执行接口。
- Agent 可以查询当前用户授权范围内的待执行任务、测试计划、测试用例、执行环境、历史结果和关联缺陷。
- 用户在执行前确认最终任务、用例范围、目标环境和风险边界。
- Agent 能够完成受控的 Web 页面操作和确定性断言。
- AI 辅助理解自然语言步骤，并在允许范围内处理轻微页面变化。
- 高风险、低置信度或无法确定的操作必须暂停并转人工处理。
- 自动记录步骤结果、耗时、截图、错误摘要、环境和 Agent/Runner 版本。
- 自动回写测试用例及测试任务的执行结果。
- 执行失败时可以生成带完整证据的缺陷草稿。
- Agent 不得擅自修改原始用例或测试预期。

### 5.5 MCP 能力范围

- 查询当前用户待办任务和任务详情。
- 获取用例步骤、历史版本和关联资产。
- 获取允许使用的执行环境。
- 开始、暂停、继续和终止执行。
- 回写步骤、用例和任务结果。
- 上传并关联截图、日志摘要等执行证据。
- 查询、创建缺陷草稿或关联已有缺陷。
- 提交人工接管请求。
- 查询任务最终状态和回写状态。

所有写接口必须具备鉴权、Scope、参数校验、业务规则校验、幂等键和审计记录。

### 5.6 验收指标

- Agent 查询个人任务的权限和数据准确率达到 100%。
- 自动执行结果回写准确率达到 100%。
- 失败步骤证据完整率达到 100%。
- 标准 Web 回归用例的 Agent 辅助覆盖率达到 70% 以上。
- 相比纯人工执行，重复操作工时下降 50% 以上。
- 标准用例人工接管率控制在 20% 以内。
- 20 条标准用例连续执行 10 轮，确定性步骤成功率不低于 95%。
- 结果未知时错误标记为成功的数量为 0。
- 高风险误操作和跨项目越权数量为 0。

## 6. M4：AI 定时巡检与主动质量预警

### 6.1 要解决的问题

- 核心功能依赖人员每天或定期手工检查，成本高且容易遗漏。
- 系统问题通常等到用户反馈或集中测试时才被发现。
- 版本发布后缺少持续验证，不能及时识别功能退化。
- 巡检结果分散，缺少连续趋势、故障现场和恢复记录。
- 异常发生后仍需人工重新操作，才能复现问题和收集证据。

### 6.2 业务定位

M4 采用“平台发起、AI 执行、异常通知、人工处置”的主动质量保障模式。平台调度器通过内部 API 创建 AI 执行任务，复用 M3 已建立的执行、断言、留证和结果回写能力。

### 6.3 目标业务闭环

```text
配置巡检计划
→ 定时、事件或 API 触发
→ 创建巡检任务
→ 调度 Agent 或 Runner
→ AI 执行检查
→ 自动断言与留证
→ 异常聚合
→ 告警与缺陷草稿
→ 人工处理
→ 自动复验
→ 恢复通知
```

### 6.4 核心交付

- 支持创建、编辑、暂停、恢复和删除巡检计划。
- 支持 Cron、固定周期、版本发布后和外部 API 触发。
- 支持配置执行环境、账号、用例范围、通知对象、失败策略和维护窗口。
- 支持可用性、登录权限、核心业务流程、页面元素、API、关键数据和发布后冒烟巡检。
- 支持超时、有限重试、防重复执行和错过任务补偿。
- 支持相同故障聚合、告警降噪和连续失败升级。
- 支持首次失败通知、持续异常升级和恢复通知。
- 异常可以生成带完整证据的缺陷草稿。
- 缺陷修复后可以自动触发复验并记录恢复结果。
- 平台重启后巡检计划不丢失、不重复执行。
- 维护时间窗口内支持暂停执行或静默告警。

### 6.5 首期巡检场景

1. 用户能否正常登录。
2. 项目和测试计划能否正常打开。
3. 功能用例列表能否正常查询。
4. 用例能否加入测试计划。
5. 测试结果能否正常提交。
6. 缺陷能否创建并按照流程流转。
7. 测试报告能否生成和查看。
8. 企业微信通知能否正常投递。
9. MCP 服务能否鉴权并返回个人任务。
10. Agent 执行结果能否正确回写。

### 6.6 验收指标

- 约定核心业务链路巡检覆盖率达到 100%。
- 日常巡检自动执行率达到 90% 以上。
- 巡检异常证据完整率达到 100%。
- 问题发现时间不超过一个巡检周期。
- 相同故障重复告警合并率达到 80% 以上。
- 告警、缺陷和原始巡检任务关联准确率达到 100%。
- 平台重启、Agent 掉线和网络中断后能够恢复。
- 巡检任务重复执行或漏执行数量为 0。
- 自动复验和恢复状态记录准确率达到 100%。
- 高风险误操作和生产数据污染数量为 0。

## 8. 里程碑依赖关系

```text
M1 测试资产统一
│  提供文档、用例、版本及追溯关系
↓
M2 测试任务、执行、缺陷和改进闭环
│  提供任务、结果、证据、缺陷及改进机制
↓
M3 Agent 辅助个人测试任务执行
│  解决测试时间紧、重复劳动和覆盖不足
↓
M4 AI 定时巡检与主动质量预警
   将人工发起的智能执行升级为平台主动持续执行
```

- M1 解决“测试什么、资产在哪里、如何追溯”。
- M2 解决“谁来测试、执行到哪里、问题如何闭环”。
- M3 解决“人手和时间不足时，如何提高执行效率和覆盖度”。
- M4 解决“无人持续检查时，如何提前发现问题并自动留证”。

## 9. 统一证据要求

M2、M3 和 M4 产生的执行记录至少包括：

- 任务来源、触发方式、执行人或执行 Agent。
- 执行时间、目标环境、浏览器和 Runner 版本。
- 用例、步骤和预期结果快照。
- 每一步的开始时间、结束时间、耗时和结果。
- 关键步骤截图和失败现场截图。
- 页面地址、断言结果和安全的错误摘要。
- AI 自愈前后的定位信息及置信度。
- 人工接管、修改和确认记录。
- 最终结果、回写状态、关联缺陷和复验结果。

所有证据必须满足：

- 与任务、用例、步骤、缺陷和报告建立确定关联。
- 对密码、Token、手机号等敏感信息进行脱敏。
- 支持权限隔离、保留期限和自动清理策略。
- 原始证据不可被静默覆盖或替换。
- 技术异常不得直接向普通用户暴露堆栈、数据库错误或内部路径。

## 10. 统一完成定义

每个里程碑只有同时满足以下条件才能标记为“已验收”：

1. 里程碑范围内的业务问题具有对应实现和验收证据。
2. 用户入口、页面、权限、交互和错误处理完整。
3. 每个前端请求都有真实可用的后端接口。
4. 后端接口具备鉴权、参数校验、业务规则和统一错误结构。
5. 数据库迁移、配置、依赖和兼容处理完整。
6. 前后端字段、类型、状态码和错误协议一致。
7. 单元测试、集成测试、类型检查、Lint 和生产构建通过。
8. Docker 镜像可以构建，容器可以启动并通过健康检查。
9. 核心用户路径完成真实端到端冒烟测试，包含至少一个失败场景。
10. 不存在未说明的 TODO、占位实现、Mock 数据或空函数。
11. 业务验收指标达到本文件规定的目标。
12. 已形成验收记录、已知问题清单和回滚或恢复方案。

## 11. 状态管理

里程碑和子项统一使用以下状态：

| 状态 | 定义 |
| --- | --- |
| 规划中 | 范围和验收标准仍在确认，尚未进入实施 |
| 开发中 | 正在实现，尚未形成完整业务链路 |
| 代码完成待验证 | 代码主体存在，但缺少真实环境、集成、容器或端到端证据 |
| 灰度中 | 已通过基础验证，正在受控用户或环境中观察 |
| 已验收 | 所有范围、质量门禁和业务指标均有通过证据 |
| 阻塞 | 依赖缺失、环境不可用或需要外部决策，当前无法继续 |

不得使用“基本完成”“应该可用”等无法验证的状态描述。代码合并、编译通过或页面可见均不能单独作为里程碑完成证据。

## 12. 风险与约束

- 计划日期基于核心团队顺序推进并允许部分底层能力并行建设；人员配置或业务优先级变化时需要重新评估。
- M3 和 M4 依赖 M1 的资产准确性及 M2 的任务、结果和缺陷闭环；前置里程碑未验收时，不应扩大 AI 执行范围。
- AI 输出和页面内容均视为不可信输入，不能绕过权限、业务规则和人工确认边界。
- 生产巡检必须使用隔离账号和可清理数据，禁止对真实业务数据执行不可逆操作。
- 所有自动重试必须区分幂等操作与非幂等操作，结果未知的写操作不得自动重放。
- 预期达成日期是目标日期，不是完成声明；实际状态以可审计验收证据为准。
