# 三、3W 项目定义（黄金圈法则）

## ① Why — 为什么做（价值与初心）★

### 1. 痛点 & 不做后果

当前公司内部测试协作与质量保障场景存在以下核心痛点：

+ **测试资产管理松散：** 测试用例、执行结果分散在语雀、Excel、XMind、群消息与个人本地文件中，无法有效检索、复用与版本追溯，同类场景反复重写，历史资产沉睡
+ **测试过程管理不透明：** 执行进度全靠询问测试人员，测试人员说多少就是多少，缺少可视化、可证明的有力证据；管理者无法基于统一视图判断覆盖、阻塞与发布风险
+ **自动化缺少统一调度与质量门禁：** 没有统一发放任务的平台，缺少强力控制结果质量的门禁机制；AI / Agent 执行结果缺少保管、评价与审批闭环，正式通过结论不可信、不可审计

**不做后果：** 随着业务线与版本节奏加快，分散式文档管理会导致用例重复建设、进度口径不一、发布决策缺少证据；自动化与 AI 执行无法纳入统一治理，结果可随意回写或无法回写，质量结论失真，最终团队人效被「找文档、追进度、补证据」消耗，测试资产无法沉淀为组织能力。

### 2. 遗产（可复用、可沉淀、长期受益）

+ **产品能力遗产：** 一套可自由配置、可扩展的自动化与测试用例管理平台，后续可用于在线巡查其他平台系统，如 BDE、米多星球、IMP 等
+ **流程方法论遗产：** 「用例资产化 + 任务闭环 + Agent 受控执行 + 质量门禁审批」的边界方法论，为公司其他质量与协作系统建设提供可复制范式（正式结果只能由平台受保护服务写入，Agent 不能自行认定通过）
+ **数据资产遗产：** 全量用例、计划、执行证据、缺陷与报告沉淀，形成组织级可检索、可追溯的测试知识库，支撑持续复用、遗漏分析与 AI 赋能
+ **集成能力遗产：** MeterSphere MCP / Agent Token、Browser Runner、企微通知等标准接入能力与插件契约，可复用于后续业务系统对接、CI 触发与多 Agent 协作

### 3. 越级 & AI in All

作为测试工程师主导本产品型项目，从「质量保障执行者」延伸到「测试平台从 0 到 1 落地」，在以下维度体现超出本职预期：

+ **角色跨界越级：** 从测试工程师到产品推动者，独立完成需求调研、方案设计、平台改造与项目推动全链路，突破「只测不建」的职能边界
+ **AI 赋能跨界：** 测试工程师借助 AI 完成产品设计与开发交付，突破技术栈边界；同时在 MSP 全链路嵌入 Agent 辅助（检索用例、受控执行、留证回写、评价门禁），让系统从「测试台账」升级为「可调度、可证明、可治理的智能测试资产云平台」

## ② How — 怎么做（路径与打法）★

**整体节奏：** 周汇报 → 月复盘 → 里程碑验收 → 项目总结

### 1. 行动策略与里程碑

| **序号** | **里程碑** | **目标 / 产出** | **计划时间** |
| :--- | :--- | :--- | :--- |
| 1 | **M1 测试资产统一沉淀、复用与追溯** | 统一资产目录、项目空间、文档与用例管理、标签检索、资产版本与全链路关联；让用例、执行结果从散落文件变为可搜索、可复用、可追溯的组织级资产 | 2026-09-18 |
| 2 | **M2 测试任务、执行、缺陷与改进闭环** | 打通「计划分配 → 在线执行 → 结果留证 → 缺陷关联 → 复验改进」主链路；进度实时可见，替代口头追问；失败证据完整可审计 | 2026-10-23 |
| 3 | **M3 Agent 统一调度 + 质量门禁与结果评价** | 建设统一任务发放与 Agent / Runner 执行通道；结果提交经质量门禁与人工/规则评价后才可正式采用；保管执行证据与评价结论，对外叙事为「可证明的智能测试」，而非可随意改写的电子台账 | 2026-12-04 |

> 说明：M4「AI 定时巡检与主动质量预警」（计划 2027-01-15）作为考核期后的延伸目标，不纳入本期结案硬门槛，但在方案与架构上预留调度、告警与复验能力，确保不推倒重来。

### 2. 是否善用 AI 提升效率或质量？

| **场景** | **如何用 AI** | **收益** |
| :--- | :--- | :--- |
| **规范约束**（.cursor/rules、skills 约束） | 通过 .cursor/rules 定义 MSP 开发规范与边界，通过 skills 封装 MeterSphere Agent 工作流（用例提取、执行回写、缺陷关联等），让 AI 输出始终符合团队规范与技术栈要求 | AI 输出质量可控，符合团队规范，减少返工，降低代码评审成本 |
| **AI 制定功能设计方案** | AI 基于项目背景、业务需求和技术栈，自动生成功能设计方案、接口定义、数据模型与验收矩阵，人工审核调整后落地 | 设计效率提升，方案更全面，减少遗漏，加速从需求到设计的转化 |
| **AI 自动开发修复重构** | AI 辅助代码生成、Bug 定位与修复、代码重构优化；测试工程师也能高效完成平台功能开发与质量保障 | 开发效率大幅提升，测试工程师突破技术栈边界，独立完成功能开发交付 |
| **AI / Agent 执行与评价** | Agent 通过 MCP 领取任务、受控执行、自动留证并回写；平台侧保管原始提交、门禁结论与审批记录，区分「上传成功」与「正式通过」 | 重复执行工时下降；结果可追溯、可评价，避免 AI 结果失控成为噱头 |

### 3. 需要的资源 / 协作

### 4. 主要风险点与应对

| **风险点** | **影响** | **应对措施** |
| :--- | :--- | :--- |
| 存量资产迁移成本高、结构不统一 | M1 延期，复用价值打折 | 优先迁移高频回归与核心链路用例；统一标题/步骤/优先级/标签规范；迁移前后做数量与关联核对 |
| Agent 执行不稳定或结果不可信 | M3 沦为噱头，干系人不买单 | 正式结果必须经质量门禁 + 审批；原始提交与正式采用分离；高风险操作转人工；失败证据必填 |
| 权限与跨项目数据泄露 | 敏感用例/证据泄露，信任崩塌 | 严格最小权限与项目隔离；Agent Token Scope 默认拒绝；操作留痕可审计；越权场景验收清零 |
| 试点部门使用意愿不足 | 「使用」结案门槛无法满足 | 选真实痛点强的业务线先跑通一条端到端计划；周报晒进度与效率数据；主验收人推动纳入版本流程 |

### 5. 过程衡量指标（如何判断进展是否健康）

+ 3 个核心里程碑（M1～M3）按期达成率 ≥ 80%
+ 核心功能模块验收通过率 ≥ 95%
+ 试点期间 P0 缺陷清零
+ 周报、月复盘、里程碑总结按时归档
+ 试点部门周活跃使用率 ≥ 70%
+ 试点计划内失败用例有效证据完整率 ≥ 95%
+ Agent / 人工正式结果回写准确率 100%（抽检）
