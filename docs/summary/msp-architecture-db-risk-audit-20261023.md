# MSP 系统结构与数据库风险审计

日期：2026-10-23；时间口径：北京时间。范围：当前工作区代码、此前两次故障日志、本轮生产库只读元数据与普通 EXPLAIN。未修改生产配置、表结构和业务数据，未在生产重放查询或导入。

## 1. 结论

存在能够放大数据库负载、延长连接占用并使局部数据库异常扩散到登录/查询/调度的设计风险。其中，资产元数据关联与索引不匹配已通过生产库执行计划对照确认；查询超时单位问题通过本地 MyBatis 字节码及 JDK 源码确认；详情逐条补全和事务范围问题由代码确认。

这些发现是具体整改依据，不等同于已确认 10 月 21、22 日故障的唯一根因。第二次故障直接机制已明确为数据库通信异常与可用连接不足，底层数据库资源、锁或网络因素仍未区分。共享实例还承载 imp_db、xxl_job 等服务，不能把全部责任归给 MSP。

## 2. 当前结构与故障传播路径

```text
网页 / Agent / MCP
  → 鉴权（Token 查询、用户及角色权限、Token 使用记录写入）
  → 用例检索 / 详情 / 导入服务
  → 业务 Hikari 连接池
  → 共享 MySQL 实例 → metersphere_prod

Quartz → 独立 Quartz Hikari 连接池 → 同一共享 MySQL 实例
Spring @Scheduled 恢复任务 → JdbcTemplate 等业务数据访问

同一实例另有：metersphere 测试库、imp_db、xxl_job 等
```

业务和 Quartz 是两个池，并非一个池，但共享实例、资源和相同池名称；独立池无法隔离数据库 CPU、磁盘或锁问题。虚拟线程降低线程创建开销，不增加数据库处理能力。

## 3. 发现与整改追踪

### A01：资产元数据关联未利用完整唯一索引（P1，生产计划已确认）

- 入口：用例列表与统计，以及复用列表能力的 Agent 检索。
- SQL：`ExtFunctionalCaseMapper.xml:254` 只按 `project_id, asset_type, asset_id` 关联 `test_asset_metadata`。
- 生产唯一索引：`uk_test_asset_metadata(organization_id, project_id, asset_type, asset_id)`。
- 原关联使用 `idx_test_asset_metadata_source(project_id, asset_type, creation_source)` 的前两列，不能用 asset_id 完成唯一定位。
- 对代表项目的普通 EXPLAIN：用例表估算 895 行；资产表关联为 ref、估算 112 行，并执行剩余条件过滤。这不是实际扫描计数。
- 对照 SQL 从可信项目记录取得 organization_id 后补齐关联，资产表可改用唯一索引，eq_ref、估算 1 行。两份 SQL 未执行 SELECT COUNT，仅生成计划。
- 风险：列表、分页 COUNT 和重复检索叠加时，多余关联检查放大。此前重启后约 11 秒的列表/统计 SQL 与此路径相符，但没有证明全部耗时来自这一个关联。
- 整改：在权限验证后的组织上下文中补齐关联，或评估适配查询的索引；不要未经验证同时加多个索引。组织范围也应纳入语义与隔离回归。
- 验收：真实项目数据上的结果/分页总数一致、计划正确、离线或隔离环境实测耗时和扫描行数下降；覆盖有/无元数据、分类、版本、筛选及多组织。

### A02：SQL 默认超时设置为 25000 秒（P1，本地配置已确认，生产值待核实）

- `commons.properties:57`：`mybatis.configuration.default-statement-timeout=25000`。
- 本地 MyBatis 3.5.19 `BaseStatementHandler` 字节码显示直接将配置值传给 `Statement.setQueryTimeout(int)`；JDK 21 源码明确单位为秒。因此该值约 6 小时 56 分钟，不是 25 秒。
- Hikari 的 `connection-timeout=30000` 是等待取得连接的时间（毫秒），不限制已经执行的 SQL。
- 生产查询得到 `max_execution_time=0`，没有全局 SELECT 执行时间上限；这不表示所有 SQL 都无其他超时，JDBC URL、事务、Mapper 和会话设置可能另有限制。
- 风险：若本地默认在运行环境生效，慢查询可长期占用连接；其他请求等待连接 30 秒超时，形成日志所见的故障放大。
- 整改：核对最终生效配置，为交互 SQL、后台任务、事务、JDBC 网络读取及网关定义分层时间预算与取消行为，不能简单全局把 25000 改成某个短值而不回归批量业务。
- 验收：隔离环境长查询/锁等待测试，确认 SQL 取消、事务回滚和连接归还；测量时间并核对最终绑定配置。

### A03：默认列表逐条读取完整详情，产生查询放大（P1，代码与日志模式相符）

- `AgentFunctionalCaseSearchService.java:74` 默认 includeSteps=true；`:81` 调用 `enrichWithSteps`。
- `AgentFunctionalCaseExportService.java:26` 对列表逐条调用 `getFunctionalCaseDetail`，而非批量读取正文。
- `FunctionalCaseService.java:432` 详情链还查询模板、自定义字段、关注状态、附件、版本、模块和用户；`false` 参数只跳过部分关联数量统计，不会取消这些查询。
- `getById` 即使 includeSteps=false，仍先调用完整详情再清空步骤，不节省前置查询与正文解析。
- 两次 19:30 附近多类详情关联查询成批出现，与此路径一致；不能据此认定具体客户端、任务或请求数。
- 整改：轻量列表与正文分开；按 caseIds 批量补全必要字段，共享模板/模块/用户一次查询；保留明确的正文读取选项。按页面大小、Token 总量及全局并发制定预算，而非仅限制每个 Token 的请求次数。
- 验收：固定 100/500 条数据的 SQL 计数和耗时对照、字段一致、附件权限与多项目隔离回归；复杂度不随每条用例重复读取相同配置而线性膨胀。

### A04：只读检索与导入事务边界偏大（P1，代码确认，生产版本待核对）

- `AgentFunctionalCaseSearchService.java:41` 在类级声明事务；列表查询后又在同一调用中逐条补全详情。慢补全会延长连接占用；readOnly 标记本身也不能消除长事务。
- `FunctionalCaseFileService.java:82` 类级事务覆盖 Excel 预处理、读取和写入；已有连接取得后可能跨解析阶段持有。
- `FunctionalCaseService.saveImportData` 写入后还执行操作日志、通知、逐条默认项目同步及资产变更发布。通知是否跨外部网络、事件监听是否异步，应继续沿具体实现验证，不在本报告武断认定。
- 当前 `FunctionalLegacyImportService` 已有 50MiB、并发槽、项目串行、持久任务及进度等保护；但这些不自动把业务大事务改成短事务，其上线情况也未证明。
- 整改：先明确全量回滚或部分成功语义；解析校验与持锁写入解耦，事务提交后进行可靠异步通知/同步；跟踪任务与业务一致性采用明确协议。
- 验收：导入中断、重试、重复提交、外部依赖失败时无伪成功、无重复写入；实际事务持续时间和连接占用有记录。

### A05：鉴权对数据库与 CPU 的重复消耗（P2，代码确认，实际成本未测）

- `AgentTokenFilter.java:100` 先执行 Token 校验，之后才进入 Token 限流；校验会查询数据库，bcrypt Token 还需逐次验证。
- 无已有身份时执行 Shiro login，请求结束时 logout；用户、角色与权限读取可能随请求重复。
- `:243` 每次请求同步更新 Token 使用信息及 invocation_count，同一 Token 并发请求写同一行存在争用风险，但尚未测得锁等待。
- 风险：数据库异常时鉴权先失败，使原本轻量接口也不可用；多 Token 并发的总成本不能由单 Token 配额完全约束。不能直接降低密码哈希安全强度或取消权限校验。
- 整改：先测每条请求鉴权 SQL 数和 CPU；为进入昂贵校验前的请求设置受控保护，研究可撤销的短期认证缓存、聚合使用计数或独立审计通道，核对现有保护后再设计。
- 验收：撤销/过期/权限变化及时生效，缓存不跨用户/项目泄漏；数据库降级时受控失败；同 Token 高并发无长时间行锁。

### A06：连接池命名重复、容量预算与依赖隔离不足（P1，部分由配置和运行日志确认）

- 本地 `commons.properties:17/29` 主池和 Quartz 池最大分别为 100/50，最低空闲均为 10，两者池名均为 DatebookHikariCP。
- 生产启动日志确有同名 `hikaricp.connections` Gauge 重复注册警告，因此池指标有混淆/丢失风险；不能从一个名称的日志直接判断业务池与调度池。
- 生产数据库 max_connections=500，多个应用和测试库共享。两个 MSP 实例按本地默认最多可请求 300 个连接；这是容量上界示例，不代表生产实际配置或实际用满。
- 整改：各池唯一名称；按实例和工作负载核算总连接预算；对重型 Agent/导入和交互业务设并发隔离。不要因 waiting 增大就盲目加连接。
- 验收：监控能独立看到两池 active/idle/pending、获取耗时和失败；数据库恢复后请求有界恢复；共享其他业务不被压垮。

### A07：排序规则修复存在本地/生产版本差异（P1，历史生产缺陷已确认）

- 故障日志反复报告 general_ci 与 0900_ai_ci 关联冲突。
- 当前本地 `AgentExecutionFinalizationService.java:116` 已改为 BINARY 比较；回写恢复服务也已有退避/告警逻辑。因此不能声称“本地完全没有修复”，也不能声称已部署生产。
- BINARY 表达式关联的索引使用与扫描范围仍需 EXPLAIN 验证，不能默认查询报错消失就代表性能合格。
- 整改：核对实际镜像版本和迁移，统一标识符字段比较语义；验证恢复查询计划及 OR 条件扫描；发布前完成混合排序规则集成测试。

## 4. 结构性判断与实施顺序

不是“表拆分多”本身必然出问题，而是逐条聚合、索引访问路径、事务和连接预算叠加造成放大。当前 4GiB buffer pool、500 连接上限也不足以单独认定 MySQL 内存配置错误；缺少实际内存/CPU/磁盘和并发采样，不能据此要求扩容或迁库。

优先顺序：A01 执行计划整改 → A02 超时预算核对 → A03 批量读取 → A06 连接池标识/预算；并行确认 A07 部署状态。A04/A05 通过隔离环境测量后实施。共享实例的 imp_db、xxl_job 仍需单独审计，本文不能覆盖其代码或归责具体容器。
