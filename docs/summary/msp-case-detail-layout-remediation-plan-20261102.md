## 一、结论及证据边界

五个现象涉及详情请求生命周期、页面高度分配、步骤表列宽、冗余布局和操作按钮定位。不能只通过隐藏错误提示或缩小字体处理。

当前源码已经取消用例列表的固定纵向高度，并删除详情概览侧栏；截图中仍有概览和表格内部纵向滚动，说明实际页面与当前源码表现不一致。可能是未部署对应构建、浏览器资源缓存、访问了不同实例或分支，尚不能确认其中哪一种。首先核对线上 build-manifest.json、静态资源 hash 和部署提交，避免重复修复旧版本。

“110%”是浏览器缩放比例，不是分辨率增加。放大后有效 CSS 视口宽高减少，使固定侧栏和操作列占比上升，暴露布局问题。

截图能证明视觉现象，不能证明失败接口、HTTP 状态、服务端异常或自动重试。本轮未读取生产 Network/HAR、服务日志或在线 DOM，因此有关接口错误根因的判断均需进一步取证。

## 三、逐项分析和修复设计

### R1：进入详情时短暂出现“请求出错，请稍候重试”

截图是详情容器内的红色 alert，不只是全局 toast。通用 ms-detail-drawer 的 loadError 驱动此区域；handleDetailFailure 会清空 detail，转换错误并显示提示；handleDetailLoaded 又清除提示。因此“先错误后内容”与一次失败回调后另一次成功回调相容，但也可能来自首次加载失败后的其他刷新，不能只凭截图认定自动重试。

代码风险点：tryLoadDetail 同时被 immediate watch 和 onMounted 调用；存在直接加载与 PrevNext 子组件加载两条路径。loadDetailDirect 的 loadingDetail 仅保护直接路径，不能证明两个组件间不会并发。需同时审查子组件初始化、activeDetailId 是否已就绪，以及 HTTP 层是否把被取消的旧请求转换成普通错误。

取证顺序：

1. 核对线上构建提交，打开 DevTools Preserve log，清空记录后只点击一次用例。
2. 收集所有失败请求的方法、URL、脱敏参数、状态码、业务 code、响应 traceId、Initiator 和时间顺序；同时记录成功请求。HAR 必须移除 token、cookie、个人信息。
3. 检查是否出现空/undefined ID、重复详情请求、关联接口失败、401/403、请求取消及后端 5xx；用 traceId 对应服务日志。不能用“随后成功”排除真实服务端故障。
4. 在慢网下重复一次，快速执行 A→B→C 和关闭详情，确认旧请求能否覆盖当前用例。

推荐改造：由详情容器统一持有加载状态、请求序号和取消信号；PrevNext 只发出目标 ID，不再独立请求；watch 仅在 visible 且 ID 有效时发起加载，消除 mounted 重复触发。同一 ID 在途复用；切换 ID 取消旧请求，成功和失败均校验当前请求序号。旧请求/主动取消不显示失败；真实当前请求失败必须保留提示和重试入口。主详情失败与评论、统计等辅助请求失败分别展示，辅助失败不能清空已加载的正文。401/403 走原鉴权规则，未知错误提供安全文案和 traceId，不暴露技术栈。

### R2：10 条列表需要滚动才能看全

当前 caseTable 的 heightUsed 为 0、scroll 只含 x:1400，上次调整实现的是“页面滚动访问全部行”，并不等同“一屏显示 10 行”。本次要求比上次的验收更严格，应重新设计密度和高度预算。

截图中多层工具栏、进度区和上下留白占用较大；通用 base-table 又根据视口顶部位置、表头、工具栏、分页扣减可用高度。应确认线上是否仍传入数字 scroll.y，是否重复计算高度、残留滚动位置，不能只把某个常数调小。

推荐：用例列表采用模块内单一纵向滚动容器，避免页面、卡片、表体三重滚动。合并导出/同步和搜索工具栏，进度区压缩为单行，可展开更多信息；批量操作默认只保留计数和主要操作；标准行高建议 36–40px，表头 36px，分页 36px。按容器真实尺寸统一计算可用高度，不在多层分别扣固定数。

定义验收档位：1920×1080、100% 下，普通单行用例名的 10 行及分页须一屏完整显示；1440×900、100% 作为笔记本优先目标。1366×768、110%/125% 或浏览器工具栏占用较大时，若可用高度小于“工具栏+表头+10×最小行高+分页”，允许一层纵向滚动，不能压到无法点击、隐藏行或暗改成 5 条分页。若业务要求这些低高度下也必须无滚动，需采用专门紧凑模式并进一步折叠工具栏，验收前明确这一取舍。长文本列表保持单行省略和完整内容提示。

### R3：步骤、预期结果在 110% 下逐字竖排

addStep 的表格 scroll.x 为 100%，同时执行相关列存在 180、150、120/160、100、120px 等固定宽度。固定操作列占去主要宽度，文案列缺少足够的最小宽度；截图中概览还进一步挤占正文。上层 break-all 会放大窄列逐字换行的后果。准确列宽分配仍需 DOM computed style 验证。

推荐优先方案：删除概览后，步骤表设置内容最小总宽度，而非强行塞进 100%。步骤描述最小 280px、预期结果最小 280px、实际结果最小 220px；序号、执行状态、提缺陷、操作按实际内容设窄列。总宽度必须按最终启用列累计（执行模式通常需约 1300–1450px），以局部横向滚动兜底，不能让两大文案列承担所有压缩。单元格用正常换行、overflow-wrap:anywhere 处理长 URL，移除从详情根节点无差别继承的 break-all；编辑框宽度填满单元格，长正文纵向自然展开。固定操作列不应遮住文案。

进一步优化：内容区域宽度不足约 1000px 时提供“阅读/执行卡片”视图，每条步骤纵向分区显示步骤、预期、实际和执行控件；保留表格视图切换。断点依据内容容器宽度，不只依据 window 宽度，兼容模块树开合和浏览器缩放。卡片与表格复用同一数据和保存逻辑，切换不丢未保存内容、不重复提交。这一项可作为第二阶段；第一阶段用最小列宽及横向滚动即可阻止逐字竖排。

### R4：删除概览窗口

当前 tabDetail.vue 已无 case-detail-review-summary 的 aside，网格已为单列。截图仍显示侧栏，应先确认实际发布版本。最终只删除该视觉区域及占位 CSS，不应顺带删除其他抽屉或接口使用的业务 overview 数据。发布后验证 CSS、静态资源 hash、刷新及多实例一致性；仅清缓存不能替代正确部署。

### R5：内容编辑与前置条件重叠

当前前置条件操作 span 使用 absolute right-[6px] top-0，脱离文档流；只读文本未为操作区预留位置。长文本、保存状态、锁提示及缩放会与按钮占用同一区域，截图符合这一布局风险。

推荐改为正常文档流：前置条件标题、自动保存状态和编辑操作独立一行，使用 flex/grid，操作区不收缩，正文下一行铺满宽度。窄容器允许操作行换行；不要通过固定右 padding 猜测按钮宽度。保留编辑权限、禁用态、锁状态和重试入口。备注若共用同类绝对定位需一起排查，但不扩大到无关页面。
