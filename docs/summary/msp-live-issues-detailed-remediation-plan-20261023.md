### 1.2 当前源码可直接确认的原因

1. `frontend/src/views/test-plan/testPlan/components/planTable.vue`的`onActivated`仅在无数据时调用`fetchData()`；已有数据的缓存列表回到前台不会依此钩子刷新。这与“进入即刷新最新数据”的新需求不符。
2. `TestPlanFunctionalCaseService.syncPlanCases()`只逐行比较结果和时间；`ExtTestPlanFunctionalCaseMapper.updateSyncStatus`仅更新`last_exec_result`、`last_exec_time`；之后调用`TestPlanDefectSyncService`补缺失缺陷关联。它不是全内容同步服务。
3. 计划列表SQL同时读取源用例的最后执行人、计划关联的执行结果和时间；计划详情则先读源详情，再覆盖计划的结果，并可能叠加计划执行历史。多个数据来源拼接，可能出现结果、执行人、时间、步骤实际结果不属于同一执行的问题。
4. 缺陷同步只有INSERT缺失关系，没有来源标识；无法安全区分“从源用例同步来的关系”和“计划手工关联”。源侧取消关联后，现逻辑不会清理对应同步关系。
5. 普通附件经`FunctionalCaseService.getFunctionalCaseDetail()`调用附件服务读取，计划详情复用该详情。附件列表过旧必须先判断是接口没重取、权限/来源过滤，还是另一类计划执行附件，不能先做文件复制。
6. 评论冲突由`FunctionalCaseCommentAccess.conflict()`抛出“评论已变更，请刷新后重试”，但`AgentSafeErrorMapper`按“评论已被更新，请刷新后重试”匹配，落入内部错误兜底。该原因在当前源码可确认。
7. 项目创建DTO不含requestId，而MCP通用写入层要求幂等键；自动生成的严格schema因此无法表达原生客户端必须提供的参数。

### 1.3 仍不能确认的事项

在线前端主文件与本地记录产物哈希不同；当前源码已经存在部分路由重定向、分页选项、详情请求序号隔离和删除确认路由，但在线表现未达到要求。因此，LIVE-01～05/07～09/13/14不能统一下结论为“源码完全没写”。必须先核对发布清单、静态文件、缓存和实际路由注册。LIVE-12的真实异常栈也未取得，不能仅凭安全错误提示推断具体SQL错误。

## 3. 新增需求的产品契约

### 3.1 刷新和同步分别解决什么

- **刷新**：把服务器当前有效数据展示出来。进入列表、详情、子页，浏览器返回/前进，缓存页激活、项目切换，均应检查并加载最新数据。已有筛选、分页、展开和滚动可保留，旧记录不能冒充新对象。
- **同步**：让计划读到与源用例一致的共享内容及状态；同时修复需要持久化的计划关联、来源关系和统计。不能依赖用户先点击一次手工同步。
- **手工全量同步**：用于主动校准和故障恢复，覆盖同一套共享内容；不是自动同步的唯一触发点，也不是把所有项目用例自动加入计划。

本方案将新诉求解释为“当前共享状态一致”。源侧新执行成功/失败后，已关联活动计划应采用同一次最新有效执行的结果、执行人、时间、步骤实际结果和证据；不得只更新一个结果字符串。

### 3.2 范围与优先规则

1. 默认自动作用于**已关联、未归档计划**。原计划关联范围、执行集合、排序、负责人分派仍由计划管理；未关联用例不因同步而自动加入。
2. “所有状态/所有内容”覆盖下表的源用例共享项。计划文档、计划评论、历史执行、计划独立附件和分派信息是独立业务记录，保留但清晰展示来源；不得删除或伪造历史。
3. 归档计划、已生成报告、历史执行事实保持其绑定版本。此为沿用原方案的历史冻结规则；不因本轮“同步全部”改写历史。若后续要求归档计划也追随最新值，应作为独立产品变更处理。
4. 固定版本用例读取其绑定版本定义；不得把v2定义与v1执行事实拼接。对于允许追随最新版本的计划，版本升级必须显式校验、记录迁移，不可按“latest=true”把旧版本关系静默删除。
5. 多个计划执行同一源用例时，最新执行按服务端提交序号确定，不能按客户端时间覆盖。已有计划执行路径会更新源用例，应统一进入同一变更链路，避免双向循环。
6. 源侧取消关联/删除内容必须同步可见变化；只撤销本系统生成的同步关系。计划手工关系和仍被历史引用的文件保留。

### 3.3 全量同步矩阵

| 数据项 | 当前来源/风险 | 目标行为 |
| --- | --- | --- |
| 名称、编号、描述、前置条件、预期 | 计划多为读取源定义 | 采用同一绑定版本最新定义，列表/详情/搜索一致 |
| 步骤定义及顺序 | 源步骤；可能叠加计划历史 | 按稳定stepId匹配，内容变更后旧执行事实不冒充当前版本结果 |
| 等级、评审状态、标签、自定义字段 | 源字段 | 刷新后全部一致，枚举和值转换一致 |
| 源模块/版本/需求关系/前后置关系 | 源信息与计划集合不同 | 源模块、版本和关系最新可见，保留计划集合与排序 |
| 总执行状态 | 源与计划关联各存一份 | 统一有效执行来源，列表、详情、筛选、通过率同一口径 |

| 计划统计/模块计数/通过率 | 可能缓存/关联行派生 | 与当前列表口径一致，同步完成后重算或失效；不出现“用例失败、计划仍0条执行” |
| 删除、恢复、版本替换 | 现代码会移除非latest关系 | 区分软删除、恢复、版本固定；保留可恢复关联和历史，不按latest简单删关联 |

## 4. 刷新与同步的整体实现

### 4.1 统一读取模型，先消除混合来源

新增拟议`PlanCaseEffectiveViewService`，供REST计划列表、详情、统计和MCP计划查询共用。基本数据仍引用现有源用例、版本、附件，避免重复快照和大文件复制。有效状态采用同一`executionRef`，一次性返回结果、执行人、时间、步骤事实、证据与来源。

建议DTO新增以下兼容字段，现有字段继续返回，但全部由统一模型映射：

```json
{
  "caseId": "源用例ID",
  "testPlanCaseId": "计划关联ID",
  "definitionVersionId": "当前绑定定义版本",
  "sourceRevision": 42,
  "appliedRevision": 42,
  "executionRef": { "type": "DIRECT_SUBMISSION", "id": "提交ID" },
  "syncState": "CURRENT",
  "lastExecuteResult": "ERROR",
  "attachments": [],
  "bugRelations": []
}
```

空集合仅表示实际没有对应内容，不能用空数组掩盖读取失败。`executionRef.type`实际枚举需覆盖普通用例执行、计划执行、个人直提、受管任务；历史数据无法确定来源时标记`LEGACY_UNRESOLVED`，不能凭最新时间猜测证据归属。

读取策略：共享定义、附件及源缺陷以有效源关系为准；必要的计划状态副本、关系来源和统计由同步器维护。同步器延迟时，查询依然依据源revision返回正确有效内容，并标记`PENDING`，不返回旧值假装CURRENT。GET不得隐式执行整个项目的写同步。

### 4.2 源变更的可靠通知

所有写入入口在原业务事务内统一记录“用例变更”：网页保存/执行、批量执行、MCP创建更新、个人直提发布、附件关联删除、缺陷关联取消、缺陷状态变化、评论墓碑、导入提交、删除恢复。单靠前端事件总线无法覆盖MCP和其他浏览器。

推荐在现有数据库内补充增量版本及outbox，不新增Kafka/Redis作为本需求必需依赖：

- `functional_case_sync_state`（拟新增）：按caseId保存递增revision和最近有效executionRef。定义更新、关系更新与执行更新均递增；用updateTime不能覆盖附件/缺陷等关联表变化。
- `case_change_outbox`（拟新增）：eventId、组织/项目/caseId、revision、changedDomains、createdAt、state、attempts、nextRetryAt、leaseOwner/leaseUntil、safeErrorCode。与原业务变更同事务提交。
- 多副本使用数据库领取租约；按caseId/revision幂等。原事务回滚不得留下已发布事件。
- 缺陷状态变化会影响多个caseId，按实际关联分批派发；不是全库广播。源事件和同步派生事件用origin/correlationId区分，派生更新不得递归产生同一源事件。
- 合并连续版本，源revision=43可直接覆盖尚未应用的42；较旧事件不得把已应用43回退到42。每批建议100条，单worker起步，通过压测再调，不同时启动多套基础设施。

此方案增加可靠补偿，不承诺只靠消息推送保证正确。轮询/事件丢失后，进入页面仍通过源revision读到正确内容。

### 4.3 同步应用服务

拟新增`PlanCaseSynchronizationService`，统一自动同步、手工同步及定时校准。输入为项目、caseId范围、目标计划范围及请求标识。核心步骤：

1. 校验组织/项目/源用例/计划归属、当前权限、归档状态；后台消费者使用受限系统执行身份并保留原始触发者，不能依赖线程中的网页Session。
2. 按caseId分页加载当前有效数据，批量查目标关联；不再对每个计划重复全项目扫描。
3. 锁定必要关联行并比较revision。每批或每计划独立短事务，禁止一个HTTP请求长事务锁住整个项目；失败不吞掉。
4. 使用统一执行适配器更新结果、执行人、执行时间及执行引用；步骤事实和附件沿用原执行引用，不重造历史执行记录。
5. 对同步缺陷、附件等关系按来源做差异校准：新增缺失、撤销失效、保留手工/历史引用、去重。源共享读取无需复制关系的域，校准其版本与派生缓存即可。
6. 更新统计失效标识、appliedRevision和同步时间，提交后发出前端失效通知。只有全部目标域成功才标记CURRENT。
7. 失败记录安全错误码、traceId及失败域；任务支持重试失败项。重试同revision不会重复插入文件、关系或执行历史。

当前`syncPlanCases()`把非latest源记录当无效关联移除的行为须调整：版本固定不等于已删除。历史关联保留；删除恢复策略与回收站对齐。

### 4.4 附件与缺陷来源设计

附件优先复用现有fileId/associationId。确需新增计划关系时引入`origin=SOURCE_SYNC|MANUAL|EXECUTION_HISTORY`和`sourceAssociationId`，同一计划关联+源关系唯一。**唯一性应作用于新增来源映射，不直接给历史表加可能失败的唯一索引。**

缺陷建议新增来源映射表`plan_case_source_relation`（名称待实现确认），记录relationType、testPlanCaseId、sourceRelationId/sourceBugId、sourceRevision、active。允许同一bug同时存在源同步和计划手工两个来源，但展示和计数只算一个bug。撤销源来源后若仍有手工来源，继续展示。

历史关系无法可靠区分来源时标记LEGACY，不按确定性ID前缀猜测后批量删除。首次迁移只补映射和必要关联；历史清理必须有预览、数量对账及备份。

物理文件删除继续受全部当前和历史引用保护，附件查看、缩略图、下载分别校验权限；不能因为拿到源fileId就越权下载。长期留存沿用原附件保留/备份规则，不将“今天能读”当作长期验证证据。

### 4.5 前端刷新策略

复用并完善`useListRefresh.ts`、`listRefreshGate`，不另写多套轮询：

- 页面首次加载、onActivated、组织/项目/计划/版本变更、浏览器返回/前进、focus/online时刷新；可见且有权限时接收业务失效事件。
- 计划列表不能再以“已有数据”作为不刷新条件。调用`refreshPreserveState`保留筛选、分页、排序、树展开；数据减少导致页码越界时回退合法页。
- 详情身份键为`organizationId/projectId/planId/caseId/testPlanCaseId/versionId`；切换身份先清空旧内容、计数、附件和操作上下文，渲染loading，禁用保存/删除/执行。所有响应含请求序号和身份校验；旧响应丢弃。
- 定义`refreshPlanContext()`并协调标题、统计、用例树、当前表格、缺陷和执行摘要刷新；只刷父标题不算完成。
- 父子页共享一次刷新调度，同一key并发刷新合并；退出页面取消或失效请求。先刷新权限/身份再展示资源。
- 用户编辑中的表单/文档不能被后台响应覆盖。允许无编辑的计数与列表刷新；草稿区提示“源数据已更新”，保存时版本冲突，提供比较/重载。离开保护继续保留。
- 对外部MCP变更：有现成通知通道则订阅按项目授权的失效事件；无通道时可见页30～60秒检查revision，恢复焦点/进入时立即检查。验收标准建议同浏览器写成功后2秒内可见、页面重进首次查询即可见，跨客户端持续可见页不超过60秒；这些是本方案验收目标，非当前已测性能保证。
- 网络失败保留同一身份旧数据并显式标识过期/重试；新身份失败不得回显旧对象。空状态、无权限、会话失效、参数错误、网络与服务端错误分别处理。

### 4.6 手工同步接口与页面

保留两个现有入口：

- `POST /test-plan/functional/case/sync/project/{projectId}`
- `POST /test-plan/functional/case/sync/plan/{testPlanId}`

当前旧客户端读取同步计数，不得静默把原响应改成taskId。新增版本化异步入口（拟议）`POST /test-plan/functional/case/sync-jobs`，由新版网页使用；旧入口短期保留原响应和限制，复用同一应用服务，不接受部分失败后固定成功。

拟议创建参数：projectId、可选testPlanIds、scope=ASSOCIATED_ACTIVE、requestId；不接受客户端自定义SQL、任意changedDomains或越权计划列表。完整同步域由服务端定义，不能只传RESULT偷减范围。

任务状态查询建议`GET /test-plan/functional/case/sync-jobs/{jobId}`，返回QUEUED/RUNNING/SUCCEEDED/PARTIAL_FAILED/FAILED/CANCELLED、各域计数、扫描/变更/跳过/失败数、目标revision及失败明细分页；停止和重试通过同资源子路径。接口名称为设计稿，实施时登记到前端API定义与OpenAPI/MCP契约。

按钮可保留原名称并增加“同步内容”说明，或改名“同步全部用例数据至测试计划”；确认框明确仅当前项目已关联未归档计划，列出附件、执行摘要/步骤/证据、缺陷及共享字段，保留计划独立数据。重复点击复用同请求，刷新页面可恢复任务进度；部分成功必须显示失败对象和重试，不只提示“同步完成”。

## 6. 数据迁移、兼容和发布

### 6.1 迁移策略

实施前检查实际Flyway最大版本，新增后续迁移，不覆盖已应用脚本。为同步状态、outbox、来源映射及手工任务建立最小必要表/索引；组织/项目/caseId/计划关联等标识字段与现表collation一致，避免重现关联字段规则冲突。

发布清单绑定git SHA、前端主资源名/摘要、后端镜像digest、数据库迁移版本、能力配置。提供只读release-info（复用已有版本接口扩展，避免暴露主机路径/密钥），部署后分别读HTML引用和实际资源、后端版本及健康状态。

### 6.3 开关和回滚

建议按依赖顺序控制新有效视图、自动同步消费者和异步全量同步；迁移先加后删，旧字段保留兼容。灰度先仅隔离项目，然后扩大。

回滚消费者时保留outbox和任务状态，停领取不删除事件；旧前端可继续访问旧同步接口。新业务已产生来源映射后，回滚需保留兼容读，不能靠回退镜像让旧代码误删新来源关系。发现统计或版本错位，立即停止扩大灰度，保留事实与错误记录。
