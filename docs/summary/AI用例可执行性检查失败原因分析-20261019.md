# AI 用例可执行性检查失败原因分析

## 结论

已定位并通过本地真实 MySQL 数据复现一个足以导致本次现象的实现缺陷：功能用例内容按 ZIP 压缩存储，可执行性检查却用 SQL CAST 直接转换为字符。UTF-8 连接下，压缩字节不能作为合法文本解码，转换可返回 NULL，检查随即错误返回 CASE_STEPS_OR_ASSERTION_MISSING。

本次远端 TC12 有步骤、有预期且已发布，仍仅报此缺失项，与该机制一致。尚未直连远端测试数据库核对该行原始字节及连接字符集，因此“压缩读取缺陷已确认并复现”与“远端具体记录的数据库级闭环尚待验证”须分开表述。

不建议修改业务用例或删除准入检查；应修复读取与校验实现。

## 代码链路与原因

1. FunctionalCaseInterceptor.java 第 21–23 行为 steps、textDescription、expectedResult 配置 zip/unzip。正常 MyBatis 读取会解压，因此详情页面能显示内容。
2. AgentCaseExecutabilityService.java 第 81 行使用 JdbcTemplate 直接读取，并执行 `CAST(b.steps AS CHAR)`；它绕过 MyBatis 解压，不调用 CompressUtils.unzip。
3. ZIP 数据以十六进制 504B0304 开头，包含任意二进制字节。它不是 UTF-8 文本，CAST 不等于解压。
4. UTF-8 连接下 MySQL 可返回 NULL 和 Warning 1300（Invalid utf8mb4 character string）。第 82 行随即把 NULL 解释为步骤或断言缺失。
5. 第 81 行同时存在 `catch(Exception ex){content=null;}`，会把其他读取异常也映射为同一缺失错误。这是额外的错误分类缺陷；本地已复现的 NULL 路径无需依赖 Java 异常即可触发。

因此，“详情正常、资产发布正常、可执行性失败”并不矛盾：它们的内容读取方式不同。TestAssetCatalogService.decodeBlob 已显式调用 CompressUtils.unzip，可作为复用方向。

## 修复建议及验收条件

1. 通过统一的内容读取/解压服务获取用例内容，或读原始 byte[] 后解压，再按 UTF-8 解析；不要 SQL CAST 压缩内容。
2. 按 STEP/TEXT 分别进行结构化校验。当前仅 isBlank，不能识别 `[]`、只有动作没有预期、损坏 JSON 等情况；文本模式 CONCAT 也不能保证描述和预期都存在。
3. 区分内容真正缺失、格式错误、解压失败、数据库读取失败；技术异常保留日志与 traceId，用户提示不得统一归责为用例未填写。
4. 尽量与本次执行冻结的已发布版本使用同一内容来源，避免发布版本和工作副本的校验不一致。
5. 回归压缩 STEP/TEXT、合法非压缩兼容数据、空步骤数组、缺描述/预期、损坏压缩数据、读取异常，以及完整的预检→创建任务链路。
6. 部署后以远端 TC12 原有内容复检，确认不修改用例也可正确读取；随后补做门禁完整正向及四类独立负向场景。
