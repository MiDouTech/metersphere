## 结论

反复出现的不是已证明的同一个容器故障，而是多类启动和运行缺陷反复越过发布检查。大改动同时改变服务依赖、数据库、配置与业务路径，现有检查却主要证明能编译、局部测试通过或探针健康。历史修复没有全部变成发布必经的自动检查，导致新变化仍可能在部署后首次暴露。

开发与验收责任在交付方。本轮虽然有本机真实镜像、容器和浏览器验证，但遗漏了后台任务持续异常，并且未取得实际部署环境的验收证据。不能将此归咎于用户没有提供足够验证，也不能将“部分完成”用作可部署性验证不足的理由。

## 为什么已有测试没有拦住

### 1. 发布流水线主要验证构建，不验证可运行

`.github/workflows/cnb-build.yml` 的后端步骤使用：

```bash
./mvnw -B clean package -DskipTests -DskipAntRunForJenkins=true -pl '!frontend'
```

随后直接构建并推送镜像、发布版本信息。该工作流没有迁移唯一性检查、真实数据库升级、完整应用启动、运行观察及业务冒烟的必经步骤。即使本地测试存在，流水线也不强制运行它们。镜像构建成功不是 Spring 启动成功。

工作流使用 clean 并清理解包目录，因此不能把此次问题无证据地归因于该流程残留旧 JAR。它也同时发布版本标签和 latest；若外部部署使用 latest，存在版本追踪风险，但尚未核实现场拉取方式。

### 2. 依赖环防回归覆盖有限

`AgentServiceDependencyCycleTests` 只扫描 `io.metersphere.agent.service` 内的 `@Service`，按直接字段和构造参数类型构图。它不能覆盖完整跨模块依赖、接口实际实现、所有配置工厂与条件 Bean，也不等同于实际 Spring 全量启动。现有 `AgentMcpStartupTests` 的局部上下文和 Mapper 解析有价值，但不能替代生产配置下的真实启动。

新增功能复用既有大服务时，容易引入反向依赖。需要结构性拆分职责，而不是靠允许循环依赖或普遍添加懒加载掩盖问题。

### 3. 数据库验证缺少历史与配置差异

版本唯一只排除一种失败。历史库字段、排序规则、数据库默认值、迁移中断后的部分 DDL、实际历史表名都可能不同。本轮仅验证已有隔离库升级，没有完成干净安装和完整恢复验证。

已确认：V99 创建 `ai_execution_case_sync` 时没有显式 COLLATE；隔离 MySQL 中其 ID 字段为 `utf8mb4_0900_ai_ci`，而 `ai_execution_task` 关联字段为 `utf8mb4_general_ci`。迁移记录成功，但后续 JOIN 报错。证明“DDL 执行成功”和“业务 SQL 可运行”是两项检查。

### 4. 健康检查没有覆盖持续运行

`scripts/verify-quality-environment.ps1` 验证 readiness、迁移记录、一次数据库事务及基础设施连接；没有将新增持续 ERROR、任务重试失败、重启次数增长纳入失败条件。`verify-msp-remediation.ps1` 的浏览器用例也没有覆盖这次后台回写重试。

因此 250 项后端、16 项 Node、14 项浏览器测试通过是真实的，但覆盖范围不足以证明整个部署稳定。健康检查需要保留其明确语义，不能把所有可选业务故障都变成重启条件；发布验收必须另外观察并验证后台任务。

### 5. 可选能力与主进程耦合放大故障范围

`deploy/run-with-wecom-bridge.sh` 在 Java 启动前处理密钥并启动 Bridge；Bridge 退出后会终止 Java。这是代码中明确的联动策略，即使功能未启用，运行时仍依赖 Bridge。相关目录权限、Node 或 Bridge 故障可能影响整个平台可用性。

这是需评估的架构风险，不是本次 502 的已确认根因。调整应明确启用条件和故障隔离策略，不能简单吞掉错误或降低核心安全要求。

### 6. 本机验证与目标部署之间缺少闭环

本机记录了 JAR/镜像摘要，但没有核对目标运行容器的摘要、外部配置、挂载及升级前数据库状态；没有取得故障时段退出日志。目标 CI 又重新构建制品，本机通过不能自动转移为该目标制品验收通过。

发布检查不能依赖每次对话中的自觉执行。必须记录“源码提交 → 候选镜像摘要 → 迁移验证 → 启动及业务验证 → 实际运行摘要”，并使未通过者无法晋级正式版本。

## 建议形成的强制发布检查

| 阶段 | 必须验证 | 阻断条件 |
|---|---|---|
| 开发/合并 | 迁移版本唯一、历史迁移不可意外改写、依赖结构和相关回归 | 重复版本、未经说明的历史变更、测试失败 |
| 候选制品 | 对正式 Dockerfile 产出的同一镜像执行全应用启动 | Bean/Mapper/资源/配置初始化失败 |
| 数据库 | 干净安装、代表性旧库升级、异常中断恢复；执行实际关联 SQL | 迁移失败、字段/排序规则不兼容、数据校验失败 |
| 部署契约 | 只读配置、持久化密钥、运行用户、依赖版本、资源限制 | 缺少必要配置或权限，不得带问题切流 |
| 稳定性观察 | 超过启动宽限期，至少覆盖关键定时任务多个周期；检查 restart/OOM 和新增异常 | 进程退出、重启增长、关键后台任务失败或未解释的重复异常 |
| 业务验收 | 登录、项目/用例读取、Token/MCP、附件、门禁拒绝路径、结果回写 | 任一核心路径失败 |
| 发布晋级 | 固定提交与镜像 digest，前后端版本匹配，核对目标运行摘要 | 未知或不一致制品，候选镜像未经验证 |
| 故障恢复 | 留存日志和数据库变更记录；验证旧应用与新 schema 的兼容性 | 不得盲目删除迁移记录、改校验和或直接恢复数据库 |

不把所有 ERROR 都机械视为故障：已知的负例测试和可预期拒绝应结构化标识；新出现且无法解释的后台异常不得作为通过。

优先顺序：先接入强制 CI 启动与迁移验证、补后台观察及回写集成测试；再完善历史数据库矩阵和目标摘要核对；随后治理跨模块依赖与 Bridge 故障隔离。大改动按独立可验收批次交付，每批保持可部署，不能仅在最后一次集中验证。
