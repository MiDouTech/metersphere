## 2. 改造背景

当前平台在缺陷流程生命周期、历史缺陷流程关联、企微岗位同步、缺陷状态展示、Agent 集成说明、用例资产历史数据同步和文件导入等方面存在实现缺口或前后端规则不一致。同时，测试资产、测试计划、自动化执行和 Agent 调度规则等多个页面持续出现“服务暂时异常，请稍后重试（requestId）”，影响功能正常使用。

本次改造需要同时完成业务规则闭环、前后端实现闭环、历史数据兼容、异常根因修复和可验证交付，禁止仅调整前端展示、仅隐藏错误或仅完成单侧实现。

## 3. 已确认需求

### 3.1 缺陷流程删除与归档

1. 未关联任何缺陷、没有流转历史且不是当前使用中流程的流程允许删除。
2. 已关联缺陷或存在流转历史的流程不得物理删除，只允许归档。
3. 当前使用中的流程不得删除或归档，必须先开启另一个流程。
4. 已归档流程仍需支持历史缺陷状态展示、合法流转和审计查询。
5. 删除、归档必须由后端重新校验引用情况，不能仅依赖前端判断。

### 3.2 Agent 集成

1. Agent 集成页面参考“个人信息 → Agent 集成”的布局和交互进行统一改造。
2. 顶部保留“创建 Token”“下载技能包”“搜索框”。
3. MCP 技能包说明仅以普通文字形式放在“我的 Agent Token”标题下方。
4. 不保留独立 MCP 卡片、边框、Alert、折叠区、地址块、Scope 列表等完整模块结构。
5. 系统设置入口和个人信息入口应复用同一个 Token 管理组件，避免两处实现不一致。
6. 下载按钮根据技能包 manifest 状态控制；技能包不可用时禁用并显示明确说明。

说明文字如下：

> MCP 技能包<br>
> 下载技能包交给 AI（如 Cursor），使其学会调用本平台 Agent/MCP 接口。平台侧只需：下载技能包 + 创建 Token。<br>
> 技能包暂不可用，请联系管理员重新打包部署<br>
> AI 技能包用于指导 AI 连接远程 MCP，不包含 Token。创建 Token 后复制 MCP 配置到对应客户端。<br>
> 内置平台地址<br>
> 测试环境：https://msp.ebcone.net<br>
> 正式环境：https://msp.ebcone.cn<br>
> 常用 Scope（创建 Token 时选择）<br>
> 全部 Agent 权限：包含查询、执行、用例、计划、评审、缺陷和项目相关能力，仍受本人 RBAC 限制。<br>
> 项目查看：允许检索和查看可访问项目；迁移期 FUNCTIONAL_READ 仍临时覆盖本权限。<br>
> 测试用例管理：用例读取、结果提交、测试计划和评审相关操作。<br>
> 缺陷管理：缺陷检索、详情查看、创建和更新。

### 3.3 多页面服务异常

1. 不仅调整前端提示，必须通过 requestId 和服务端日志定位后端真实异常。
2. 必须修复导致异常的代码、SQL、迁移、权限、数据或服务依赖问题。
3. 修复后需要保证对应页面及操作真实可用。
4. 禁止通过返回空数组、吞掉异常或隐藏 Toast 伪装修复完成。

### 3.4 用例资产

1. 同步历史业务项目对应的资产目录。
2. 同步已有历史测试用例，不能只创建空目录。
3. 同步过程必须幂等，不得重复生成资产用例。
4. 修复 Excel、XMind 文件导入失败问题。
5. “新建用例”“导入测试用例”“刷新”“补建历史项目目录”“新建用例项目”整体向左移动约 100px，并兼容窄屏。

### 3.5 企微岗位同步与管理员能力

1. 在“系统设置 → 系统 → 权限控制 → 流程控制”的流转规则区域增加“同步企微岗位”按钮。
2. 将平台已同步企微组织架构中的真实岗位同步为缺陷流程角色。
3. 岗位同步必须幂等，并区分企微同步岗位和人工创建的岗位关键词规则。
4. 具有系统管理员身份的角色可以绕过流程角色限制修改状态。
5. 管理员只能选择当前状态的合法下一步，不能跳过流程拓扑。
6. 管理员强制流转必须填写原因并写入审计记录。

### 3.6 缺陷状态修改

1. 缺陷列表和详情继续保留状态修改入口。
2. 状态修改必须遵循当前缺陷所绑定流程版本的合法下一步和角色权限。
3. 不可操作时必须显示具体原因，不能无提示隐藏。
4. 历史缺陷可通过流程控制页面的“关联历史缺陷”按钮手动批量关联到当前使用中的流程。

### 3.7 缺陷状态中文显示

1. 缺陷列表、详情、回收站、关联缺陷、报表等位置统一显示中文状态名称。
2. 不得直接显示内部英文编码或数据库状态 ID。
3. 原始状态值仅用于接口提交和内部定位。

## 4. 当前实现与需求偏差

| 模块 | 当前实现 | 偏差 |
| --- | --- | --- |
| 流程删除 | 后端仅允许删除非默认草稿；前端对所有非默认流程显示删除 | 前后端规则不一致，且未按缺陷引用判断 |
| 流程发布 | 发布新流程时自动归档旧流程，并自动将新流程设为默认启用 | 不符合“手动开启、手动归档” |
| 历史缺陷 | 已有迁移预检和批次框架，但默认面向全部未绑定缺陷，入口名称为“迁移历史缺陷” | 缺少人工筛选、勾选和“仅关联到当前使用流程”的约束 |
| Agent 说明 | 系统入口和个人入口均存在独立 MCP 说明组件 | 不符合仅插入普通文字的要求 |
| 历史用例 | “补建历史项目目录”只创建目录关系 | 未同步历史测试用例 |
| 用例导入 | 前后端导入接口和异步任务已存在 | 实际调用失败，需按日志修复真实原因 |
| 企微岗位 | `user.position` 已保存企微岗位；流程支持手工职位关键词 | 缺少岗位预览、同步入口、来源标识和精确匹配 |
| 管理员流转 | 系统管理员绕过角色限制、原因审计逻辑已经存在 | 需要补充两端入口回归和角色范围校验 |
| 状态修改 | 列表、详情已有专用流程流转组件 | 历史数据、岗位匹配或接口异常时无法正常操作 |
| 状态显示 | 列表部分使用旧状态字典，详情缺少统一名称解析 | 出现中文、英文编码和状态 ID 三种展示结果 |
| 服务异常 | 前端统一展示 100500 和 requestId | 尚未完成逐接口根因定位和修复 |

## 5. 总体设计原则

1. **生命周期与投入使用分离**：发布不等于开启使用，停止接收新缺陷不等于归档。
2. **流程版本不可变**：已发布和已归档版本不允许原地修改，只能复制为新草稿。
3. **新旧缺陷隔离**：新建缺陷绑定当前使用流程；历史缺陷仅通过人工批量操作关联。
4. **单一使用流程**：同一时间全局只能有一个用于新建缺陷的流程。
5. **历史流程可运行**：旧流程停止接收新缺陷后，已绑定缺陷仍按原版本运行。
6. **后端最终校验**：删除、归档、开启、关联和状态流转都必须由后端重新校验。
7. **错误必须修根因**：不得以提示优化代替功能修复。
8. **共享组件和共享接口**：相同业务入口复用实现，避免前后端和多入口能力分叉。

## 6. 缺陷流程生命周期设计

### 6.1 状态定义

建议将流程生命周期和投入使用状态拆分：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `lifecycle` | `DRAFT` | 草稿，可编辑 |
| `lifecycle` | `PUBLISHED` | 已发布、配置不可变，可选择是否投入使用 |
| `lifecycle` | `ARCHIVED` | 已归档，不再投入使用，但保留历史运行能力 |
| `active_for_new` | `0/1` | 是否用于新建缺陷，全局最多一条为 1 |
| `enabled` | `0/1` | 流程运行时是否有效；已关联缺陷的流程不得随意禁用 |

原 `default_flow` 可在兼容期映射为 `active_for_new`，但后续业务代码不能再混用“默认”“启用”“投入使用”三个概念。

### 6.2 状态流转

```text
新建流程
  ↓
草稿
  ↓ 手动发布
已发布、未使用
  ↓ 手动开启使用
已发布、使用中
  ├─ 新建缺陷自动绑定
  ├─ 手动关联历史缺陷
  └─ 开启另一个流程后变为“已发布、未使用”
        ↓ 手动归档
      已归档
```

### 6.3 发布

发布仅执行：

1. 校验唯一初始状态、结束状态、状态可达性、流转角色和全局作用域。
2. 固化流程版本。
3. 将生命周期从 `DRAFT` 更新为 `PUBLISHED`。
4. 保持 `active_for_new=0`。
5. 不修改当前使用流程。
6. 不归档任何旧流程。
7. 不关联任何历史缺陷。

### 6.4 开启使用

增加 `开启使用` 操作：

1. 仅已发布流程允许开启。
2. 使用事务和行锁保证全局唯一。
3. 将原使用中流程的 `active_for_new` 更新为 0，但生命周期仍为 `PUBLISHED`。
4. 将目标流程的 `active_for_new` 更新为 1。
5. 新建缺陷只查询 `PUBLISHED + active_for_new=1 + enabled=1` 的流程。
6. 开启操作不影响任何已有缺陷的 `workflow_id/workflow_version`。

确认提示：

> 开启后，新建缺陷将使用此流程。已有缺陷不会自动切换，原使用中流程不会归档，仅停止接收新缺陷。

### 6.5 手动归档

1. 当前使用中的流程不能归档。
2. 已发布未使用流程可手动归档。
3. 归档后 `active_for_new=0`。
4. 归档流程仍允许已绑定缺陷查询状态、流转规则和审计记录。
5. 已归档流程不可重新开启；需要复制为草稿后重新发布。

### 6.6 删除与引用分析

增加流程影响分析接口，返回：

```json
{
  "associatedBugCount": 12,
  "transitionHistoryCount": 36,
  "activeForNew": false,
  "deletable": false,
  "archiveRequired": true,
  "reason": "该流程已关联缺陷，只能归档"
}
```

删除规则：

| 条件 | 结果 |
| --- | --- |
| 当前使用中 | 禁止删除，先开启替代流程 |
| 已关联缺陷 | 禁止删除，只能归档 |
| 存在流转历史 | 禁止删除，只能归档 |
| 无引用、非使用中 | 允许删除 |

引用判断应包含正常缺陷、软删除缺陷和状态流转历史，避免删除后无法恢复历史数据。

## 7. 关联历史缺陷设计

### 7.1 入口

路径：

```text
系统设置 → 系统 → 权限控制 → 流程控制 → 关联历史缺陷
```

按钮仅在当前流程同时满足以下条件时可用：

1. 生命周期为 `PUBLISHED`。
2. `active_for_new=1`。
3. 当前用户拥有权限控制更新权限。
4. 存在 `workflow_id IS NULL` 的历史缺陷。

### 7.2 数据范围

默认只关联尚未绑定流程的缺陷：

```sql
bug.workflow_id IS NULL
```

已经绑定旧流程的缺陷不得通过该入口重新绑定。跨版本重新绑定属于另一类流程迁移能力，需要单独设计和授权。

### 7.3 人工选择

弹窗支持：

- 按项目筛选；
- 按原状态筛选；
- 按创建时间筛选；
- 按缺陷 ID 或标题搜索；
- 分页勾选并跨页保留；
- 选择当前筛选结果全部关联；
- 展示总数、已选择数量和未映射数量。

### 7.4 状态映射

历史状态可能为英文编码、旧状态 ID 或第三方状态值。自动映射顺序：

1. 状态编码相同；
2. 中文名称相同；
3. 去除 `bug_` 前缀后匹配；
4. 无法匹配时由管理员手工选择。

存在未映射状态时禁止正式执行。

### 7.5 批次执行

1. 先执行预检，输出影响数量和状态映射。
2. 创建关联批次和逐项记录。
3. 分批更新缺陷的 `workflow_id`、`workflow_version` 和映射后的状态 ID。
4. 并发期间已被其他操作关联的缺陷记为 `SKIPPED`。
5. 支持任务进度、失败原因、失败重试和安全回滚。
6. 记录原状态、原流程信息、目标状态、目标流程、操作人和时间。
7. 关联不发送普通状态变更通知，避免批量企微通知，但必须写审计日志。

## 8. 企微岗位同步设计

### 8.1 数据来源

仅使用满足以下条件的用户岗位：

- `user.wecom_userid` 不为空；
- 用户启用且未删除；
- `user.position` 不为空；
- 岗位名称去除首尾空格并去重。

### 8.2 接口能力

新增：

1. 企微岗位预览接口；
2. 同步岗位到指定草稿流程接口；
3. 同步结果查询接口。

预览返回岗位名称、标准化键、关联人数和是否已存在。

### 8.3 角色模型

同步岗位应增加来源和匹配方式：

```text
role_type   = POSITION
source_type = WECOM_POSITION
source_key  = 标准化后的真实岗位
match_mode  = EXACT
```

人工岗位关键词规则继续使用模糊匹配，企微同步岗位使用精确匹配，避免“测试”错误匹配到不相关岗位。

### 8.4 同步规则

1. 仅草稿流程允许同步岗位。
2. 相同 `source_key` 幂等更新，不重复创建。
3. 企微已不存在的同步岗位标记为失效，不直接删除历史配置。
4. 同步只创建岗位角色，不自动赋予所有流转权限。
5. 管理员在流转矩阵中手动配置岗位的可见和可操作权限。

### 8.5 管理员流转

系统管理员 `admin` 可以绕过角色限制，但必须满足：

1. 拥有项目缺陷更新权限；
2. 目标状态为当前流程的合法下一步；
3. 填写强制流转原因；
4. 写入状态流转历史和操作审计；
5. 不能绕过版本、并发、第三方状态映射和数据完整性校验。

## 9. 缺陷状态修改与展示

### 9.1 状态修改

列表和详情继续使用同一个专用流程流转组件。状态选项必须由后端流转接口返回，不能由前端加载全部状态后自行判断。

不可操作时展示具体原因：

- 历史缺陷尚未关联流程；
- 当前状态没有合法下一步；
- 当前岗位未命中可操作角色；
- 流转规则未配置可执行角色；
- 当前用户没有项目缺陷更新权限；
- 第三方状态无法映射；
- 流程版本不存在或不可用；
- 数据已被其他用户更新，请刷新后重试。

普通编辑接口不得直接修改缺陷状态，所有状态变化统一通过流程流转接口完成。

### 9.2 中文状态解析

建立统一后端状态解析器，按以下优先级处理：

1. 已绑定全局流程：按 `workflow_id + status_item.id` 查询状态名称和编码；
2. 历史本地缺陷：按 `bug_new` 等内部编码查询旧状态字典；
3. 第三方缺陷：按第三方状态选项解析；
4. 无法解析：返回“未知状态（原始值）”，不得只显示裸 ID。

所有缺陷接口统一返回：

```json
{
  "status": "1561199171619528771",
  "statusCode": "bug_new",
  "statusName": "新建"
}
```

前端列表、详情、回收站、关联抽屉、测试报告和工作台统一展示 `statusName`。

## 10. Agent 集成设计

### 10.1 统一布局

以“个人信息 → Agent 集成”为基准，将系统设置入口和个人入口统一为：

```text
我的 Agent Token
说明文字
创建 Token | 下载技能包 | 搜索框
Token 安全提示
Token 列表
```

### 10.2 组件复用

抽取共享 Token 管理组件，统一维护：

- Token 列表；
- 搜索；
- 创建和编辑；
- 启停和删除；
- 下载技能包；
- manifest 状态；
- 权限控制；
- 创建完成后的 Token 和 MCP 配置复制。

两处入口只负责传入布局模式，不各自实现业务请求。

### 10.3 MCP 说明

删除独立 `McpOnboardingPanel` 展示模块。说明文字直接插入现有标题说明区域，通过普通文字和换行展示，不增加独立业务容器。

下载规则：

- manifest 可用：允许下载；
- manifest 不可用：按钮禁用，显示不可用说明；
- 下载失败：显示明确错误和 requestId；
- 技能包中不包含 Token。

## 11. 用例资产设计

### 11.1 历史目录与用例同步

当前“补建历史项目目录”需要升级为幂等同步任务：

1. 扫描当前组织未删除业务项目；
2. 按项目名称创建或合并资产目录；
3. 扫描项目中的历史测试用例；
4. 将尚未进入资产中心的用例复制为资产用例；
5. 记录资产用例与原项目用例的来源关系；
6. 同名目录合并，但不同源用例不得仅按名称去重；
7. 根据源用例 ID 幂等，重复执行不产生重复数据；
8. 输出成功、跳过、失败数量及逐项原因；
9. 支持断点续跑。

建议将按钮修改为“同步历史项目及用例”，或在原按钮弹窗中明确勾选“同步历史用例”。

同步模式采用：首次全量、后续手工增量。业务项目用例与资产用例保持副本和来源关系，不进行双向实时覆盖。

## 12. 多页面服务异常根因修复

### 12.1 排查范围

至少覆盖：

1. 测试计划关联用例；
2. 测试用例自动化执行；
3. 测试资产—用例资产；
4. 用例资产文件导入；
5. 测试资产—测试数据；
6. 测试资产—公共步骤；
7. 测试资产—执行证据；
8. 测试资产—缺陷资产；
9. Agent 调度规则选择用例资产；
10. 测试用例从用例资产导入。

### 12.2 根因清单

为每一个失败请求建立记录：

| 页面 | 接口 | 请求参数 | requestId | 后端异常 | 根因 | 修改文件 | 验证结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |

通过 requestId 查询完整服务端堆栈，重点检查：

- Flyway 迁移成功状态、版本唯一性、缺表和缺字段；
- MySQL 字符集和排序规则冲突；
- Mapper、DTO 和数据库字段不一致；
- 动态 SQL 空集合、错误 JOIN 和分页问题；
- 默认资产项目、目录、模板不存在；
- 用户、组织、项目上下文为空；
- 权限资源未初始化或权限范围错误；
- 异步线程丢失上下文；
- 服务循环依赖、服务未注册或远程调用失败；
- 历史数据不满足新增约束；
- 空值、类型转换和状态映射异常。

### 12.3 修复要求

1. 每一个 100500 必须对应具体根因和代码修复。
2. 参数错误、权限不足、资源不存在、数据冲突应返回明确的 4xx 业务错误。
3. 未知异常保留 requestId，并记录 URI、用户、组织、项目和完整堆栈。
4. 不得在前端吞掉异常。
5. 不得返回空数据伪装成功。
6. 共用接口修复后回归所有调用入口。
7. 多接口并行加载失败时，前端可合并提示，但功能修复仍以接口成功为准。

### 12.4 功能验证

每个页面均需验证：

- 列表加载；
- 搜索、筛选和分页；
- 弹窗和抽屉数据加载；
- 选择和回显；
- 新建、编辑、删除；
- 导入任务执行和结果查询；
- 刷新后数据仍存在；
- 数据库确实产生预期记录；
- 服务端日志无未处理异常。

## 14. 数据库与迁移要求

1. 新增字段或表必须使用新的唯一 Flyway 版本号。
2. 所有新增表统一使用项目约定的 `utf8mb4` 排序规则，避免再次出现 collation 冲突。
3. 迁移脚本必须幂等考虑历史数据，但不得修改已经成功执行的旧版本脚本。
4. `active_for_new` 需要建立全局唯一约束或通过锁和校验保证唯一。
5. 流程引用查询需要 `bug(workflow_id, workflow_version)` 索引。
6. 历史关联批次和逐项表保留原值、目标值、状态和错误信息。
7. 企微岗位流程角色增加 `source_type/source_key/match_mode`，并建立流程内唯一索引。
8. 历史用例同步来源关系对源项目用例 ID 建立唯一约束。
9. 上线前在目标 MySQL 版本执行完整迁移演练和回滚演练。

## 20. 已确认决策

1. 流程或流转历史只要被缺陷引用过，即使缺陷已软删除，也不得物理删除，只能归档。
2. 历史用例采用首次全量、后续手工增量同步，不进行双向实时同步。
3. Agent 集成参考个人信息 Agent 集成布局，MCP 说明仅保留普通文字。
4. 管理员绕过流程角色仅指系统管理员 `admin`。
5. 流程发布、开启使用、归档为三个独立的手工动作。
6. 新流程发布后不自动开启，不自动归档旧流程。
7. 历史缺陷不自动关联，只能通过“关联历史缺陷”人工批量处理。
8. 多页面服务异常必须修复后端根因并完成真实功能验证，前端提示优化不作为修复完成标准。
