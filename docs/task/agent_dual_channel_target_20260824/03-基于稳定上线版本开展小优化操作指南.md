# 基于稳定上线版本开展小优化操作指南

## 1. 目的

当前 `v3.1.0` 工作区包含尚未提交的 Agent 双通道、旧执行通道下线、测试计划同步等改造。本指南用于在不提交、不丢失、不污染这些改造的前提下，从已上线稳定版本创建独立开发环境，完成小范围优化并单独提交。

推荐使用 Git worktree。它可以让同一个仓库同时存在两个互不干扰的工作目录：

- 原目录继续保留尚未提交的改造；
- 新目录从稳定提交创建，用于本次小优化；
- 两边共享 Git 对象，但工作区和分支相互隔离。

## 3. 操作前禁止事项

当前原工作区包含普通修改、已暂存重命名和未跟踪文件。确认完成隔离前，不要执行以下命令：

```bash
git reset --hard
git clean -fd
git checkout .
git restore .
git switch main
git switch v3.1.0
git stash pop
```

这些操作可能覆盖、删除或错误恢复当前尚未提交的 Agent 改造。

仓库中已经存在多条历史 stash，因此不建议把本次隔离建立在 `git stash` 上。

## 4. 确认生产环境实际版本

在生产服务器执行：

```bash
docker exec metersphere_prod cat /tmp/MS_VERSION
```

版本通常包含构建日期和提交短 SHA，例如：

```text
20260825-3eba5a39
```

在本地确认提交：

```powershell
git show --no-patch --oneline 3eba5a39
```

基线选择规则：

1. 如果生产稳定版本显示 `3eba5a39`，且该版本被确认可以作为本次小优化基线，则使用 `3eba5a39f2`。
2. 如果需要排除已经发现不完整的缺陷筛选和预览改造，则使用其父提交 `f40c43bb46`。
3. 如果生产版本显示其他 SHA，以生产版本中的 SHA 为准，并先执行 `git show <SHA>` 确认提交内容。
4. 不要仅凭分支名称判断上线版本，因为分支可能在生产部署后继续前进。

以下示例使用环境变量保存最终确认的基线。若选择 `f40c43bb46`：

```powershell
$stableBase = 'f40c43bb46'
```

若选择 `3eba5a39f2`：

```powershell
$stableBase = '3eba5a39f2'
```

## 5. 创建独立 worktree

### 5.1 检查目标目录和分支名称

```powershell
$sourceRepo = 'C:\SoftWare\JetBrains\metersphere'
$worktreePath = 'C:\SoftWare\JetBrains\metersphere-stable-fix'
$newBranch = 'fix/small-optimization-stable'

Test-Path -LiteralPath $worktreePath
git -C $sourceRepo branch --list $newBranch
git -C $sourceRepo worktree list
```

预期：目标目录不存在，新分支名称尚未被占用。

如果目录或分支已经存在，请改用新的明确名称，不要删除未确认内容。

### 5.2 创建 worktree

```powershell
git -C $sourceRepo worktree add `
  -b $newBranch `
  $worktreePath `
  $stableBase
```

该命令不会清理或移动原工作区中的未提交改造。

### 5.3 验证隔离结果

```powershell
git -C $worktreePath status
git -C $worktreePath log -1 --oneline
git -C $sourceRepo status --short
```

新目录预期显示：

```text
On branch fix/small-optimization-stable
nothing to commit, working tree clean
```

最后一条命令用于确认原目录中的改造仍然存在。

## 6. 在新目录进行小优化

后续编辑、构建和测试均应在以下目录执行：

```text
C:\SoftWare\JetBrains\metersphere-stable-fix
```

每次开始操作前建议检查：

```powershell
git -C $worktreePath branch --show-current
git -C $worktreePath status --short
```

不要从原工作区直接复制整个目录。确需复用单个文件或代码片段时，应逐项比较，避免把 Agent 改造一并带入稳定分支。

## 7. 提交前检查

### 7.1 检查修改范围

```powershell
git -C $worktreePath status --short
git -C $worktreePath diff --stat
git -C $worktreePath diff
```

确认输出中只包含本次小优化。

### 7.2 执行相关验证

根据改动范围执行最小充分验证，例如：

```powershell
# 后端示例
mvn -pl backend/services/<涉及模块> -am test

# 前端示例
Set-Location "$worktreePath\frontend"
pnpm type-check
pnpm lint
```

具体命令应以项目现有脚本和本次改动模块为准。

### 7.3 仅暂存本次文件

不要使用无范围的 `git add .`。建议明确指定文件：

```powershell
git -C $worktreePath add <文件1> <文件2>
git -C $worktreePath diff --cached --stat
git -C $worktreePath diff --cached
```

确认无误后提交：

```powershell
git -C $worktreePath commit -m "fix: <本次小优化说明>"
```

## 8. 推送和合并

推送独立分支：

```powershell
git -C $worktreePath push -u metersphere $newBranch
```

推荐通过 Pull Request 合并到目标稳定分支，并再次确认 PR 只包含本次小优化提交。

检查新分支相对基线的提交和文件：

```powershell
git -C $worktreePath log --oneline "$stableBase..HEAD"
git -C $worktreePath diff --stat "$stableBase..HEAD"
git -C $worktreePath diff --name-status "$stableBase..HEAD"
```

如果后续需要把小优化提交挑选到其他干净分支，可执行：

```powershell
git cherry-pick <小优化提交SHA>
```

不要在当前仍有未提交 Agent 改造的原工作区直接执行 cherry-pick。

## 9. worktree 清理

只有在满足以下条件后才清理：

- 小优化已经提交；
- 提交已经推送或有其他可靠备份；
- 新 worktree 中没有未提交文件。

检查：

```powershell
git -C $worktreePath status
```

移除 worktree：

```powershell
git -C $sourceRepo worktree remove $worktreePath
```

如确认临时分支已经合并且不再需要，再删除本地分支：

```powershell
git -C $sourceRepo branch -d $newBranch
```

不要使用 `-D` 强制删除尚未确认合并的分支。

## 10. 异常处理

### 10.1 提示分支已存在

更换新分支名称：

```powershell
$newBranch = 'fix/small-optimization-stable-2'
```

### 10.2 提示目录已存在

先检查目录内容：

```powershell
Get-ChildItem -Force -LiteralPath $worktreePath
```

不要直接递归删除。确认目录来源后，改用新的 worktree 路径通常更安全。

### 10.3 基线 SHA 在本地不存在

先只更新远程引用：

```powershell
git -C $sourceRepo fetch metersphere
```

然后根据生产 SHA 查找对应提交：

```powershell
git -C $sourceRepo show --no-patch --oneline <生产提交SHA>
```

### 10.4 误在原目录修改了小优化代码

停止继续操作，先通过 `git diff -- <文件>` 区分小优化与 Agent 改造。不要执行整体还原。可使用 `git diff` 生成限定文件的补丁，再在新 worktree 中审查应用。
