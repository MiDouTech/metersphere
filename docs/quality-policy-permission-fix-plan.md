# 平台统一质量门禁策略与权限改造方案

日期：2026-09-24
适用仓库：C:/SoftWare/JetBrains/metersphere；参考环境：https://msp.ebcone.net
状态：已按用户要求修订方案；产品代码、数据库及权限配置尚未实施本方案。

## 1. 修订结论与生效范围

用户已明确：**纯系统管理员也有权限访问；质量门禁对所有项目统一生效，不允许各项目采用不同标准，不以项目约束策略管理权限。**

因此，本方案由“项目级权限修复”调整为“平台统一策略、系统级授权、统一执行消费”。不能仅删除一次项目权限检查便宣称完成。

以下为确定的设计约束：

1. 平台只有一个当前生效的质量门禁策略版本，覆盖现有及以后新建的所有项目。
2. 不提供项目覆盖、组织覆盖、项目开关或按项目选择策略版本的能力；规则不能通过项目 ID 条件变相实施差异化标准。
3. 系统管理员无需组织或项目成员绑定，也无需选择当前项目，即可查看、编辑和发布策略。
4. 项目切换、当前项目停用、无项目可选，不影响平台策略管理权限或生效版本。
5. 任务、用例、证据、缺陷及报告继续按项目隔离。统一标准不授予查看其他项目业务数据的权限。
6. “同一标准”指同一生效时点的全平台标准一致；历史执行保留当时绑定的版本和结果，不能用新规则静默改写历史。

本文替代原方案中的项目级授权、按项目停用控制策略编辑、无需数据迁移等结论。综合改造及导航方案中“项目执行设置→门禁策略”的旧设计在本专项范围内以本文为准；其他需求保持原边界。

## 2. 原故障证据与代码核查

原方案记录：陈启芬具有已启用的 `admin/system` 和项目 `1660836314033823744` 的 `project_admin` 绑定；页面和按钮资源存在，但请求 `GET /api/quality/policies?projectId=1660836314033823744` 返回 HTTP 403、`PERMISSION_DENIED`，traceId 为 `3d794f20-4b4d-4eca-89ad-dbde839ce3be`。本次修订沿用该记录，没有再次登录环境复测。

当前代码存在四层项目依赖：

- `QualityPolicyAccess.require(projectId, permission)` 检查请求项目与当前项目一致，再要求已启用 PROJECT 角色具备显式权限。
- 随后调用 `AgentProjectService.resolveProjectId()`；其项目集合来自组织、项目绑定，不能作为纯系统管理员的全平台访问判定。

- 前端请求携带 `projectId`，页面监听当前项目重新加载；质量策略入口位于项目执行设置。

另已核实：`SessionUtils.getCurrentProjectId()` 优先读请求头 `PROJECT`；通用 `hasPermission()` 会合并多个层级授权。它们不等价于本方案的系统级授权。请求参数与头一致也不构成真实授权证明。

质量策略请求已有 `errorMessageMode: 'none'`，但 HTTP 403 仍会在 `checkStatus.ts` 中触发全局跳转，需要独立控制导航行为。

## 3. 系统级权限规则

系统管理员默认拥有完整管理权限。其他账号采用系统级显式授权，作为本方案的实现默认；不把“无项目约束”解释为所有登录账号均可编辑全平台策略。

| 身份 | 查看 | 编辑、校验草稿 | 发布 | 授权来源 |
| --- | --- | --- | --- | --- |
| 有效系统管理员，含无项目绑定账号 | 允许 | 允许 | 允许 | 已启用 SYSTEM 管理员角色及 `system` 绑定 |
| 组织、项目管理员，仅有本层级角色 | 不自动授予 | 不自动授予 | 不自动授予 | 本层级身份不产生系统级策略权限 |
| 获授系统角色的普通账号 | 按读取权限 | 按管理权限 | 按发布权限 | 已启用 SYSTEM 角色、有效 `system` 绑定及显式权限 |
| 无有效系统授权的账号 | 拒绝管理接口 | 拒绝 | 拒绝 | 不使用其他项目、组织授权兜底 |
| Agent Token，包括系统管理员所有者的 Token | 拒绝管理接口 | 拒绝 | 拒绝 | 不继承所有者的管理能力 |

建议新增独立权限码，避免旧项目授权被自动升级为全平台授权：

- `SYSTEM_QUALITY:READ`：读取平台策略、版本、规则结构。
- `SYSTEM_QUALITY:MANAGE`：创建、更新和校验草稿。
- `SYSTEM_QUALITY:PUBLISH`：发布平台策略版本。

三项独立；管理不隐含发布。普通账号进入管理页面需读取权限，管理或发布接口分别检查对应操作权限。旧 `QUALITY:READ`、`QUALITY_POLICY:MANAGE/PUBLISH` 项目授权及旧 UI 授权不自动转换为新授权。

已有会话中的角色停用、绑定移除也必须生效。复用并验证现有权限会话刷新机制；不能仅通过重新登录验证撤权。平台策略只读管理权限与业务用户查看自己任务的门禁结果分开：后者沿用任务权限，不要求获得系统策略管理权限。

## 5. 后端授权与接口

### 5.1 统一授权入口

将质量策略访问入口调整为 `requireSystem(permission)`，不再接收项目作为授权范围：

```text
验证有效登录身份
→ 拒绝 Agent Token 管理调用
→ 检查已启用的系统管理员及 system 绑定
   或检查有效 SYSTEM 角色的对应显式操作权限
→ 校验草稿、版本和发布业务约束
→ 执行业务事务并记录审计
```

复用 `SessionUtils.isAdminForScope()` 的有效角色判断语义时，只判断系统范围，不传入当前项目或组织；普通角色权限严格限定 SYSTEM 范围。Controller 注解、Shiro 判定和服务层使用同一语义。不得直接使用会让项目/组织管理员自动放行的通用 `hasPermission()` 作为最终系统授权。

不在请求头中新增可信“管理员”标识；不以角色展示名称判断身份。无项目绑定账号的登录、首页跳转、设置父路由、UI 资源和菜单过滤均需核查，避免后端放开而前端仍要求先选项目。

### 5.2 新接口契约

建议显式新增 `/api/system/quality` 命名空间；按现有代理约定同时注册 `/system/quality`。新接口不接受 `projectId` 作为策略选择条件，客户端不再发送该字段；携带已废弃项目字段的调用返回明确的参数错误。全局自动附带的 PROJECT/ORGANIZATION 头不参与策略选择或授权。

| 方法及路径（省略 `/api/system/quality`） | 权限 | 契约 |
| --- | --- | --- |
| `GET /policy-schema` | SYSTEM_QUALITY:READ | 平台支持的规则结构 |
| `GET /policies` | SYSTEM_QUALITY:READ | 全局分页列表及唯一当前版本；无项目过滤 |
| `GET /policies/{id}` | SYSTEM_QUALITY:READ | 仅平台策略及其发布记录 |
| `POST /policies/validate` | SYSTEM_QUALITY:MANAGE | 校验 rulesJson，不产生有效版本 |
| `POST /policies` | SYSTEM_QUALITY:MANAGE | 创建全局草稿 |
| `PUT /policies/{id}/draft` | SYSTEM_QUALITY:MANAGE | rulesJson、expectedVersion；不可修改已发布版本 |
| `POST /policies/{id}/publish` | SYSTEM_QUALITY:PUBLISH | expectedVersion、expectedCurrentPolicyId、changeReason |

响应用 `scope: SYSTEM` 表明策略范围，不返回虚构的 projectId。策略 ID 不可在新旧表之间自动兜底匹配。保留分页边界、JSON Schema 校验、版本冲突和已发布不可变约束。

旧项目查询接口仅提供只读历史归档，并保留原项目对象授权；系统管理员可按明确的历史审计权限读取。旧创建、校验、更新、发布接口停止项目策略管理，返回安全的升级指引；禁止把旧项目写请求静默转成全平台写入。此为明确的管理 API 兼容性变更，需列出调用方并配套升级，不能宣称旧写接口完全兼容。

## 6. 全局数据模型与迁移

### 6.1 数据模型

建议新增独立表，保留原项目表作历史归档，避免伪造一个“全局项目”：

| 建议表名 | 内容与约束 |
| --- | --- |
| `execution_quality_policy_global_state` | 固定单例主键 `GLOBAL`；current_policy_id、next_version、row_version；限制其他主键及第二行 |
| `execution_quality_policy_global` | 全局唯一 ID、唯一 version_no、schema_version、rules_json、content_hash、状态、乐观锁版本及操作人时间 |
| `execution_quality_policy_global_publication` | 发布前后版本和 hash、操作者、时间、原因、traceId；成功记录与当前指针同事务提交 |
| `execution_quality_policy_migration_map` | 原项目、原策略 ID、内容 hash、全局候选 ID、迁移批次和处理结论；唯一来源键保证重复执行不重复导入 |

表名为实施目标，迁移编号在实施时按仓库最新序列分配，不修改已经发布的 V91～V94。新草稿分配全局版本号；发布锁定单例状态行，校验预期当前版本及草稿版本后原子切换指针。并发发布只能一方成功，另一方返回冲突，不产生双生效版本。

### 6.2 存量策略处理

1. 只读清点所有项目草稿、已发布版本、当前指针和已有执行引用，保存数量、hash、来源映射及备份。
2. 以规范化规则内容比较差异；名称等元数据单独比较，不能仅按不同项目的版本号推断内容相同。规则内容相同可生成共同候选，但保留每条来源与历史审计。
3. 有差异时输出规则及参数差异表，系统管理员在真实发布页面确定统一草稿。不得默认取最新、最严或某个项目版本，也不得静默覆盖其他项目。
4. 无现存有效策略时，创建待审核草稿；不能生成固定“全部通过”的默认规则。
5. 完成正式发布及消费者验证后，一次性切换全平台读取来源。旧项目策略不再成为当前执行的回退来源，新项目无需复制策略。
6. 迁移可恢复、可重复，归档记录和旧执行引用保持可查；不复制旧项目管理权限到新系统角色，不删除历史数据。

若统一版本尚未确定，或执行消费者尚不能使用它，则阻止统一执行能力上线，状态标记为阻塞，不能在界面显示“已对所有项目生效”。

## 7. 执行链路与版本生效规则

统一配置页不等于统一门禁已执行。R4 必须覆盖实际服务端消费者，不能只在策略 CRUD 中去掉 projectId。

- 在服务端接受一次新执行 attempt 时，从全局状态读取当前版本并保存 `policyId`、版本、内容 hash；与 attempt 建立原子关联。调用者不能指定项目专用或历史策略。
- 发布切换与 attempt 绑定采用统一的事务顺序及锁约定；并发创建必须绑定完整的旧版或新版，不得读取混合内容。
- 同一 attempt 的提交、补传和重复回调沿用绑定版本，客户端不得覆盖；新一次重试属于新 attempt，绑定当时全平台当前版本。历史重算是单独且有审计的操作，不覆盖原判定。
- 同一发布窗口内，项目 A/B 新建执行取得同一标准。在途执行使用其已固定的旧版本属于时间边界，不是项目覆盖；页面清楚展示依据版本。
- 缺少有效全局策略、版本内容不可读取、hash 不一致、规则不受支持或检查异常时，不得正式标记门禁通过、回写正式成功或绕过检查进入批准状态；返回明确的阻塞原因及 traceId。
- 发布端按部署中的执行消费者能力验证规则，未知规则不得以“暂不支持”为由跳过。管理员发布页应显示实际消费状态，不伪造“已应用”。
- 优先由服务端统一判定；MCP/Runner 接收任务时可得到该任务所需的规则合同，但没有策略管理权限，也不能自行决定正式通过。该合同随任务对象授权，不开放 Token 策略管理接口。
- 维护入口清单：网页发起、MCP 外部任务、Runner 提交、重试、批量回写、旧结果写入入口；每项明确消费者和正式结果出口。凡能影响正式门禁结论的入口都必须接通或明确拒绝，不允许旁路。

切换前暂停新 attempt 准入，清点在途且未绑定版本的任务；完成旧任务或终止后按新 attempt 重建，记录原因。不能给已执行任务补造“当时已使用全局策略”的证据。恢复准入前确认全部服务实例使用统一来源；不采用按项目灰度开关。

当前完整门禁/正式回写链路的缺口仍是交付依赖。仅配置管理先完成时只能标记“统一配置已实现，执行生效未完成”。

## 8. 前端入口与错误交互

唯一维护入口调整为“设置→系统设置→质量门禁”，建议路径 `/setting/system/quality-policy`。复用现有质量策略组件，移除项目选择依赖和项目切换自动清空编辑器的逻辑。

- 新增 SYSTEM 范围页面、编辑、发布资源；不能只修改旧资源的 scope 后沿用全部旧授予记录。
- `/execution/quality-policy` 和 `/setting/execution-settings/quality-policy` 使用 replace 跳转新页，丢弃 projectId/pId 等项目选择参数，不携带任意回跳 URL 或 Token。
- 旧链接含项目策略 ID 时进入有明确标识的历史只读归档，不把同 ID 当全局策略；仍校验旧业务对象访问范围。
- 系统权限检查不自动继承项目/组织管理员特权；有系统授权但无项目的用户可进入父菜单和页面。其他项目业务菜单不因本改造放开。
- 展示“全平台统一标准”“当前生效版本”“发布时间”；发布对比展示规则变化、全部项目影响、在途 attempt 版本边界，并要求变更原因。
- 为请求配置增加明确的页面内 403 处理选项，贯通类型、HTTP 拦截器、checkStatus 与本页 API。默认全局 403 行为不变；401 仍按会话失效流程处理。
- 缺少读取权限显示平台权限说明；编辑或发布被拒绝时保留可读页面与未提交草稿。网络和服务失败可重试；冲突展示当前版本并保留本地修改供比较，不能静默覆盖。
- 处理 loading、empty、success、validation-error、permission-denied、network-error、server-error；安全提示携带 traceId，不展示堆栈、SQL 或异常类名。
- 页面退出、重新加载、编辑会话切换后，过期响应不能覆盖新状态或触发全局跳转；项目切换不改变全局策略身份。登出后不得保留敏感编辑内容。

| `frontend/src/views/execution/quality-policy.vue`、权限工具与相关国际化 | 平台语义、发布影响、失败保稿、系统级按钮控制 |
| 后端 `QualityPolicy*Tests`、真实鉴权集成测试、`frontend/e2e/quality-policy.spec.ts` | 授权、迁移、并发、错误、跨项目执行一致性 |

不重写其他模块权限体系，不为方便测试批量授予现有角色全局权限。执行消费者的最终文件清单必须在实现 R4 前补入追踪记录。

## 10. 验收矩阵

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| A01 | 纯系统管理员，无组织/项目绑定且无当前项目 | 菜单、页面、读取、编辑、发布全部可用 |
| A02 | 只有项目/组织管理员身份或旧 QUALITY 项目权限 | 不获得全平台策略管理权限；伪造 PROJECT/ORGANIZATION 头无效 |
| A03 | 系统显式只读；读取+管理；读取+发布；无权限 | 接口与按钮遵循独立权限；发布不隐含编辑，管理不隐含发布 |
| A04 | 管理员/系统角色停用、解绑、撤销单项权限 | 已登录旧会话也失去相应权限；新会话一致 |
| A05 | 管理员所有者的 Agent Token | 所有新旧策略管理写接口拒绝，新管理读取接口也拒绝 |
| A06 | 切换、停用、删除当前项目或无项目可选 | 不改变全局策略身份、标准或系统管理权限 |
| A07 | 项目 A/B 及新建项目的新执行 | 同一生效窗口绑定同一全局版本，不存在项目覆盖 |
| A08 | 伪造 policyId/hash、项目特例参数或旧策略 ID | 拒绝覆盖；旧记录不能充当新全局策略 |
| A09 | 并发发布、并发创建与发布、保存版本冲突 | 单一当前版本，绑定原子一致，失败不覆盖已有版本 |
| A10 | 发布前在途任务、发布后新 attempt、回调重传 | 各自版本边界明确；重传幂等；历史结果不改写 |
| A11 | 无生效策略、hash 错误、规则不支持、判定失败 | 不产生正式门禁通过或成功回写；错误可追踪 |
| A12 | Web/MCP/Runner/批量/旧写入口及重试 | 无结果旁路；相同输入与版本得到一致门禁结果 |
| A13 | 缺证据通过、步骤附件均缺、合法步骤断言 | 不接受违规成功；合法准入不误判；分别覆盖单因素边界 |
| A14 | 存量相同、不同、无策略、混合草稿、重复迁移 | 来源完整、差异可审、无任意生效、幂等、历史计数及 hash 可核对 |
| A15 | 旧 URL、旧项目读接口和旧写接口 | 跳转或明确归档；旧写不改变全局或项目生效指针 |
| A16 | 页面 403、401、409、网络/500及过期响应 | 403 局部处理、401 正常失效、保稿和重试正确、不泄露技术错误 |
| A17 | 跨项目任务、证据、历史详情越权 | 继续按业务对象权限拒绝，统一策略不扩大数据可见性 |
| A18 | 成功发布、拒绝、冲突与回滚 | 操作者、范围 SYSTEM、版本/hash、原因、结果和 traceId 可核对 |
| A19 | 多实例切换及新旧服务混跑 | 恢复准入前全部使用全局来源；旧服务不能继续写项目策略 |

R4/A07～A13 未通过时，不允许声称“全平台门禁已生效”。全部行须关联真实结果及证据位置，不能用 Mock 测试代替真实授权和执行链路验收。

## 12. 发布、审计与回滚

按三阶段交付，阶段不是整体完成的替代：

- P1：新系统权限、全局表、管理 API 和页面、历史归档及迁移预检。可验收“统一配置管理”，不能宣称所有执行受控。
- P2：绑定和判定消费者接通；解决正式结果入口的门禁旁路；完成跨项目一致性和全矩阵隔离验收。
- P3：备份和预检、确定统一版本、暂停准入处理在途任务、全实例切换、核对后恢复准入及现场观察。

发布记录至少包含范围 SYSTEM、操作者、前后版本/hash、原因、时间、结果及 traceId；拒绝和冲突写安全审计日志，不能只记录成功发布。日志不包含 Token、密钥、完整敏感请求内容。发布成功记录与生效指针必须同事务。

区分两类回滚：

1. **规则回退**：复制历史全局版本为新草稿，校验并正式发布新版本；仍是全平台统一切换，不直接修改历史或重置版本号，在途任务保持绑定版本。
2. **程序回滚**：新表及历史映射保留。全局能力启用后，不能直接恢复会继续按项目策略执行的旧程序并开放写入；优先回滚到支持全局模式的兼容制品。不存在兼容制品时保持准入/正式回写关闭，修复后恢复，不默默降级为分项目标准。

扩展迁移、切换状态、备份恢复和读写隔离均需在代表性旧库上演练。本方案涉及数据和契约变更，已废除原“只回滚制品，无需考虑数据”的判断。保留旧表用于审计不代表允许旧版本继续写入或消费它们。
