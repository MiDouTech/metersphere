# AI 开发质量规则

## 完成定义

任何功能只有同时满足以下条件，才允许标记为“已完成”：

1. 每条需求均有对应实现和验收证据。
2. 前端入口、路由、页面、权限和交互完整。
3. 每个前端请求都有真实可用的后端接口。
4. 后端接口具有参数、权限和业务规则校验。
5. 数据库迁移、配置和依赖完整。
6. 前后端字段、类型、状态码和错误协议一致。
7. 单元测试、集成测试、构建检查全部通过。
8. 容器可以构建、启动，并通过健康检查。
9. 核心用户路径已经进行端到端冒烟测试。
10. 不存在未说明的 TODO、占位实现、Mock 数据或空函数。

如果任意一项未满足，必须标记为“部分完成”或“阻塞”，不得声称已经完成。

## 开发前

修改代码前必须：

- 阅读需求和相关现有实现。
- 搜索前端入口、路由、API 调用和后端接口。
- 列出需求追踪表：
    - 需求
    - 前端入口
    - 前端实现
    - 后端接口
    - 数据或配置变更
    - 测试
- 明确异常流程、边界条件、权限及失败行为。
- 优先复用现有组件、错误协议和编码模式。

## 前后端完整性

对每个用户功能检查完整链路：

用户入口
→ 页面/组件
→ 权限控制
→ API 调用
→ 后端路由
→ 参数校验
→ 业务逻辑
→ 数据持久化
→ 响应转换
→ 前端展示
→ 错误处理

链路中任意节点不存在，功能均不得视为完成。

## 错误处理

- 禁止直接向用户展示异常堆栈、异常类名、数据库错误或原始代码报错。
- 后端返回统一错误结构，例如：
  `{ code, message, details?, traceId? }`
- `message` 必须是用户可理解的内容。
- 技术细节只进入日志。
- 前端必须处理 loading、empty、success、validation-error、
  permission-denied、network-error 和 server-error 状态。
- 未知错误显示安全的通用提示，并保留 traceId 用于排查。

## 禁止伪实现

以下内容不得计为实现：

- 只有 UI，没有后端逻辑。
- 只有接口，没有前端入口。
- 返回固定成功结果。
- 使用 Mock 数据冒充真实数据。
- 空函数或仅打印日志。
- 吞掉异常后返回成功。
- 未执行测试却声称测试通过。
- 将计划实现描述成已经实现。
- 存在 TODO/FIXME/占位代码但未明确披露。

## 必须验证

修改后必须按照项目实际情况运行：

- 相关单元测试
- 后端集成测试
- 前端类型检查
- lint
- 前端生产构建
- 后端编译或打包
- 数据库迁移验证
- Docker 镜像构建
- 容器启动和健康检查
- 核心流程端到端冒烟测试

不能执行某项检查时，必须说明：

- 未执行的检查
- 未执行原因
- 因此仍然存在的风险
- 用户可以执行的准确命令

## 完成报告

最终回答必须包含：

1. 需求追踪结果
2. 修改过的文件
3. 前后端对应关系
4. 实际执行的验证命令及结果
5. 未执行的验证
6. 已知风险和遗留问题
7. 功能状态：完成 / 部分完成 / 阻塞

没有测试或运行证据时，禁止使用“完全完成”“可以正常运行”
“已解决全部问题”等表述。
